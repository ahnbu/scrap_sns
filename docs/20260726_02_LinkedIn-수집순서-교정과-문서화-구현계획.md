# LinkedIn 수집순서 교정과 문서화 구현계획

> 2026-07-26 수집분 17건의 `sequence_id`를 실제 화면 순서로 교정하고, 향후 같은 문제를 완화할 2차 정렬을 도입하며, 검증 과정에서 밝혀진 사실을 문서에 반영한다.

## S — 상황 (Situation)

[[20260726_01_LinkedIn-수집기-기존방식-복귀-구현계획]] 롤백 직후 수집한 17건이 뷰어 "로컬 수집순" 정렬에서 뒤죽박죽 표시됐다. 사용자가 "17건 내에서 순서가 반대로 반영된 것 아닌가"라고 제보했다.

`sequence_id`는 `linkedin_scrap.py:423`에서 부여된다.

```python
# crawled_at 기준 오름차순(과거->최신)으로 정렬하여 ID 순차 부여
new_posts = sorted([p for p in self.posts if p.get("sequence_id", 0) == 0], key=lambda x: x['crawled_at'])
for post in new_posts:
    self.max_sequence_id += 1
    post["sequence_id"] = self.max_sequence_id
```

한 번의 실행에서 `crawled_at`은 전부 동일(`2026-07-26T15:29:50`)하다. Python `sorted()`는 안정 정렬이므로 키가 같으면 원래 배열 순서가 유지된다. 즉 **`self.posts` 배열 순서가 곧 `sequence_id` 순서**가 된다.

## C — 문제 (Complication)

### C-1. 수집 배열 순서는 화면 순서와 무관하다 (실측 확인)

Chrome 확장으로 LinkedIn 저장글 페이지 DOM에서 `urn:li:activity` ID를 등장 순서대로 추출해 수집 배열과 대조했다.

| 화면 순서 | 수집 배열 idx |
|---|---|
| 1 | 9 |
| 2 | 0 |
| 3 | 7 |
| 4 | 3 |
| 5 | 1 |
| 6 | 2 |
| 7 | 5 |
| 8 | 6 |
| 9 | 4 |

`9, 0, 7, 3, 1, 2, 5, 6, 4` — **뒤집힘도 부분 정렬도 아닌 무작위**다. 근거 데이터: `tests/fixtures/golden/linkedin/20260726_saved_posts_screen_order.json`

### C-2. 검증 과정에서 배제된 가설 2개

원인 추정 과정에서 두 가설을 세웠고 둘 다 실측으로 배제됐다.

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 배열이 항상 뒤집혀 있다 → 뒤집으면 해결 | 화면 DOM 직접 대조 | ❌ 뒤집힘이 아니라 무작위 |
| 네트워크 응답 도착 순서가 뒤바뀐다 → `start` 오프셋으로 정렬 | 응답별 `start` 값과 도착 시각 계측 | ❌ `start=0→10→20→…→623` 63개 응답 완전 오름차순, 역전 0건 |

묶음 내부 순서도 정상임을 확인했다 — 7/7 Playwright 수집 로그와 OpenCLI raw의 같은 묶음 10건이 9/10 일치(1건 차이는 그 사이 저장글 변동).

**즉 응답은 순서대로 도착하는데 `self.posts`에 쌓이는 과정에서 흐트러진다.** 정확한 원인은 미규명 상태이며 [[BACKLOG]] BL-0726-02로 분리한다.

### C-3. 작성일 정렬로는 실제 저장 순서를 재현할 수 없다

교정 대상 17건을 화면 순서대로 늘어놓고 작성일을 보면:

```
07-22 07-23 07-21 07-19 07-18 07-17 07-13 07-17 07-16 07-16 07-16 07-14 07-16 07-13 07-12 07-10 07-11
  ↑1번    ↑2번이 더 최신
```

화면 1번(7/22)이 2번(7/23)보다 작성일이 오래됐다. 사용자가 7/23 글을 먼저 저장하고 7/22 글을 나중에 저장했기 때문이다.

**작성일 2차 정렬은 근본 해결이 아니라 완화책**이다. "무작위"보다는 낫지만 실제 저장 순서와는 다를 수 있다.

### C-4. 검증 중 문서의 잘못된 서술을 발견했다

`docs/crawling_logic.md:79`:

> "5. 플랫폼 내부 순서를 `platform_sequence_id`로 보존"

실측: LinkedIn 630건 중 `platform_sequence_id` 보유 **0건**. 보존한다고 적힌 순서 자체가 신뢰 불가한 값이다.

### C-5. `--mode all` 스킵 조건이 문서에 없다

`linkedin_scrap.py:305-315`를 읽기 전까지, `all` 모드가 "이미 수집한 글을 건너뛴다"고 오해했다. 실제 조건은 다르다.

```python
if activity_id in self.existing_codes:
    if CRAWL_MODE == "update only":
        ... return                          # update: 기존 글 스킵
    existing_post = self.existing_posts_map.get(activity_id, {})
    if existing_post.get("media"):
        return                              # all: media 있으면 스킵
```

실증: 화면 상단 6건은 전부 `media` 보유 → `all` 실행 배열에서 제외됐다. 배열 맨 앞 3건(7/16)은 `media` 없음 → 포함됐다. 예외 없이 일치한다.

## R — 해결 (Resolution)

### 범위

| 항목 | 처리 |
|---|---|
| 이번 17건 `sequence_id` | 화면 순서로 **직접 교정** (정확) |
| 향후 수집 | 작성일 2차 정렬 도입 (완화) |
| 배열 무작위 원인 | **범위 밖** — BL-0726-02로 분리 |
| 문서 통합 | **범위 밖** — BL-0726-01로 분리 |

### 정렬 정책 정의

`sequence_id` 부여 시 다음 순서로 정렬한다.

1. **1차**: `crawled_at` 오름차순 (과거 → 최신) — 기존 유지
2. **2차**: `date`(작성일) **오름차순** — 같은 `crawled_at` 내에서

2차가 오름차순인 이유: `sequence_id`는 작은 값부터 부여되고 뷰어는 내림차순 표시한다. 따라서 **작성일이 오래된 글이 먼저 낮은 번호를 받아야** 화면에서 최신 글이 위에 온다.

`date`가 없거나 파싱 불가한 경우 빈 문자열로 취급해 맨 앞(가장 낮은 번호)에 배치한다.

### Task 3: 기존 17건 `sequence_id` 교정
