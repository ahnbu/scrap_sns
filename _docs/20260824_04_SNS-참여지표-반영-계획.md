### 8.2 계획에 없던 발견 4건

**① X 참여지표가 기존 게시물에 소급 반영되지 않는 버그** (`twitter_scrap.py:335`)

갱신 조건이 "본문 길이가 늘어난 경우"에만 기존 게시물을 갱신했다. 지표만 새로 채워져도 조건을 안 타서 기존 95건이 영원히 지표를 못 받는 구조였다. `existing.get('like_count') is None and post.get('like_count') is not None`일 때도 갱신하도록 조건을 추가해 백필 가능하게 했다(20건 백필 확인).

**② API 응답 필드 화이트리스트에 지표가 빠져 있었음** (`utils/post_meta.py:META_FIELDS`)

계획서는 `web_viewer/script.js`·`style.css`만 3단계 대상으로 잡았으나, 실제로는 `/api/posts` 응답이 `META_FIELDS` 화이트리스트로 필드를 걸러내고 있어 프론트엔드에 지표가 아예 도달하지 못했다. `META_FIELDS`에 6개 지표 필드를 추가해 해결(AGENTS.md가 API 메타데이터 정본으로 지정한 파일이 정확히 이 파일이었다).

**③ Threads 기존 106건이 구 필드명(`reply_count`/`repost_count`)으로 저장돼 있어 새 코드와 안 맞음**

4단계에서 `thread_scrap.py`의 저장 키를 `comment_count`/`share_count`로 바꿨지만, 이미 저장된 기존 데이터는 옛 이름 그대로였다. `output_threads/python/threads_py_full_20260824.json`(오늘자 파일만, 과거 날짜는 병합에 안 쓰여 미대상)에 대해 일회성 rename 마이그레이션을 수행했다(168개 필드 rename, 백업 후 실행).

**④ LinkedIn 활동탭은 인코딩된 member URN으로 직접 접속하면 리다이렉트가 깨짐**

`https://www.linkedin.com/in/{인코딩된URN}/recent-activity/all/`로 바로 접속하면 `?skipRedirect=true&miniProfileUrn=null`로 잘못 리다이렉트되어 활동 데이터를 거의 못 얻는다(실측: 8건 고정, 매칭 0건). 먼저 프로필 메인(`/in/{인코딩된URN}`)에 접속해 vanity slug로 리다이렉트되길 기다린 뒤, 그 slug로 `/recent-activity/all/`에 접속해야 정상 동작한다(2단계 접속으로 수정 후 34~69건 취득, 매칭 26/252로 개선).

- 파일럿(2계정 또는 소량 저장 게시물 대상)에서 `numLikes`/`numComments`/`numShares` 결측률을 스크립트 출력(수치)으로 확인. 결측률 계산 결과를 스크래치패드에 파일로 남긴다.
- 화면 표시값과의 대조는 2.2절 3차 검증에서 쓴 Playwright headless 스크립트 방식을 그대로 재사용한다("OOO 외 N명이 반응 남김" DOM 텍스트를 정규식으로 추출해 API 값과 스크립트 내에서 assert) — 사람이 브라우저를 직접 보는 방식은 쓰지 않는다.
- `output_linkedin/python/`은 `ls output_linkedin/python/linkedin_py_full_*.json | sort | tail -1`로 찾은 최신 full 파일과, `output_total/`은 `ls output_total/total_full_*.json | sort | tail -1`로 찾은 최신 파일을 병합 후 뷰어 반영 확인(AGENTS.md 완료 기준)
- 파일럿·병합 결과(`output_linkedin/`, `output_total/` 갱신분)는 정식 산출물로 커밋한다. 검증 스크립트와 결측률 로그는 스크래치패드에만 남기고 커밋하지 않는다
