## 2. Complication — 왜 안 채워졌는가

### 2.1 지표는 "재수집 시점"에만 채워진다

기존 데이터에는 원본 API 응답이 보존돼 있지 않아 소급 계산이 불가능하다. 반드시 다시 긁어야 한다.

### 2.2 선행 계획이 백필 전량 실행을 명시적으로 범위 밖에 뒀다

선행 계획의 목표는 *수집 경로 구축*이었고 *데이터 채우기*는 파일럿만 수행했다. Threads의 `source`별 분포가 이를 그대로 보여준다.

| Threads source | 건수 | 지표 보유 |
| --- | --- | --- |
| `network` (선행 세션에서 새로 수집) | 58 | **58 (100%)** |
| `consumer_detail` | 577 | 0 |
| `legacy_migration` | 582 | 0 |
| `initial_dom` / `scroll_dom` | 26 | 0 |

X는 북마크 타임라인 상단 20건만 재수집돼 나머지 75건 미도달, LinkedIn은 작성자 189명 중 **8명(4.2%)**만 파일럿 실행됐다.

### 2.3 🔴 신규 발견 — 코드 수정만으로는 기존 데이터가 채워지지 않는다

`thread_scrap_single.py:496`이 **`is_detail_collected is True`면 대상에서 건너뛴다.**

따라서 `BL-0824-03`(상세수집 경로에 지표 추출 추가)을 구현해도 **기존 1,098건은 자동 제외되어 지표가 채워지지 않는다.** 신규 미수집 50건만 채워진다.

> 백로그 `BL-0824-03`이 "575건 개선"이라 기록한 것은 **코드 수정만으로는 달성되지 않는다.** 강제 재수집(백필) 러너가 별도로 필요하다.

### 2.4 🔴 신규 발견 — 백필 순서를 틀리면 기존 지표가 소실된다

`thread_scrap_single.py:231-233`(`promote_to_full_history`)는 기존 레코드를 **통째로 교체**한다.

```python
merged_data["sequence_id"] = post.get("sequence_id")
merged_data["crawled_at"] = post.get("crawled_at")
new_posts.append(merged_data)   # ← 기존 post의 나머지 필드는 전부 버려짐
```

`merged_data`는 상세수집 파서 출력이고, 현재 파서는 지표를 추출하지 않는다. `utils/post_schema.py:86-91`의 `normalize_post`는 **키가 없을 때만** 기본값을 넣으므로 결과적으로 `like_count: None`이 조용히 주입된다.

**결과**: 지표 추출 코드(웨이브 3-A)를 먼저 넣지 않고 강제 백필을 돌리면, **현재 유효한 network 경로 55건의 지표가 전부 지워진다.** 웨이브 순서는 협상 대상이 아니다.

보존 대상 필드 검증(실측): `legacy_migration`과 `consumer_detail`의 키 집합 차이는 `pk`·`taken_at`·`detail_status` 3개뿐이고, `local_images`는 어느 source에서도 레코드 레벨에 값이 없다(전 source 0건). 따라서 교체로 인한 손실은 **지표 필드에 국한**된다.

뷰어 정렬 옵션은 `작성일순 / 로컬수집순 / 즐겨찾기순` 3개뿐이다(`web_viewer/script.js:2372` `sortPosts`). 지표 기준 정렬·필터가 없어 103건을 사용자가 화면에서 만날 확률이 구조적으로 낮다.

### 2.6 검증 설계의 결함 (재발 방지 기록)

선행 세션의 done-check 2회가 모두 통과한 이유는, headless 검증이 **지표가 있는 게시물을 검색어로 지목해** 확인했기 때문이다. 기본 화면 첫 60장 기준으로 봤다면 5/60이 즉시 드러났다.

- **W1이 먼저인 이유**: 재수집 없이 즉시 효과가 나고, 이후 모든 웨이브의 **검증 도구**가 된다(성과순 정렬로 지표 보유 건수를 화면에서 바로 셀 수 있다).

### 4.5 UI 검증 방식 — headless Playwright 스크립트

**모든 웨이브의 화면 검증은 사람 눈이 아니라 스크립트가 판정한다.** 사용자 요구("완료는 사용자 화면 기준")는 *실제 뷰어를 사용자 조작 순서대로 구동한다*는 뜻이며, *사람이 눈으로 본다*는 뜻이 아니다.

공용 검증 스크립트를 **1개** 만들어 전 웨이브가 재사용한다.

```
$SCRATCH/verify_viewer_metrics.py
```

**요구 동작** (Playwright `chromium.launch(headless=True)`)

1. `http://localhost:5000/` 접속 후 카드 렌더링 대기
2. 인자로 받은 정렬(`date` | `engagement`)을 **DOM 클릭**으로 선택 — `page.click(f'[data-sort="{sort}"]')`. `sort`는 CLI 인자값이며 리터럴 문자열을 하드코딩하지 않는다
3. 인자로 받은 플랫폼 필터를 **DOM 클릭**으로 적용
4. 측정값을 stdout에 한 줄 JSON으로 출력
   - `cards`: 렌더링된 `article.glass-card` 수
   - `with_badge`: 지표 배지(`favorite`/`chat_bubble`/`repeat`/`format_quote`/`bookmark` 아이콘) 보유 카드 수
   - `header_total`: 화면 상단 총건수 표기
   - `console_errors`: 콘솔 error 레벨 메시지 수
   - `script_src`: 로드된 `script.js` URL (캐시버스터 확인용)
5. 스크린샷을 `$SCRATCH/w{N}_{정렬}_{플랫폼}.png`로 저장
6. **인자로 받은 기대값과 대조해 종료코드로 판정** — 충족 `0`, 미달 `1`. 미달 항목명을 stderr에 출력

**done-check 판정 근거**: 이 스크립트의 **종료코드 + stdout JSON**이다. 스크린샷은 보조 증거이며 단독으로 판정 근거가 되지 않는다.

**🔴 반드시 지킬 것 — 2단계 접속**

`output_linkedin`의 `username`은 인코딩된 member URN(`ACoAAE...`)이다. 이것으로 `/recent-activity/all/`에 **직접 접속하면 리다이렉트가 깨진다**(`?skipRedirect=true&miniProfileUrn=null`로 튕기고 8건만 잡히며 매칭 0건).

| 백필 러너가 레포에 없음 | 재현성 | 스크래치패드 전용이라 세션 종료 시 유실된다. 반복 사용이 필요해지면 `scripts/` 로 승격 판단 필요 |

## 7. 검토한 옵션과 기각 근거

| 논점 | 채택안 | 기각안 | 기각 근거 |
| --- | --- | --- | --- |
| 웨이브 순서 | W1(뷰어) 먼저 | 데이터 백필 먼저 | W1은 재수집 없이 즉시 효과가 나고, 이후 웨이브의 검증 도구가 된다. 반대로 하면 매 웨이브마다 headless 스크립트로 세어야 한다 |
| Threads 코드 vs 백필 순서 | W3-A(코드) → W3-B(백필) | 동시 또는 역순 | 역순이면 `promote_to_full_history`의 통째 교체로 기존 55건 지표가 소실된다(2.4 실측 확인). **협상 대상 아님** |
| Threads 백필 규모 | 파일럿 50건 → 게이트 → 전량 | 처음부터 1,098건 | 1,098회 HTTP 요청은 차단·레이트리밋 리스크가 크고, 실패 시 롤백 범위가 전체다. 파일럿 비용은 5% |
| 리포스트 지표 처리 | 버린다 (현행 유지) | ⓐ 원본에 복사 ⓑ `redirect_aliases`에 분리 보존 | 사용자 결정(2026-08-24). 대상 10건에 스키마 확장·뷰어 표시 설계가 파생되어 비용 대비 효과가 낮다. W3-A로 원본이 자체 지표를 갖게 되면 체감 영향도 사라진다 |
| 성과순 정렬 키 | `like + comment + share` | `like + comment + share + view` | `view_count`는 X만 제공한다(실측: LinkedIn·Threads 0건). 합산하면 X가 항상 상위를 독점해 플랫폼 간 비교가 무너진다 |
| DOM 경로 지표 파싱 | 기각 (데이터 정리만) | 축약값 역변환 구현 | 대상 26건(2.1%), 축약형("1.2천") 역변환은 정밀도 손실. 같은 글이 network 경로로 재수집되면 정확한 원값이 들어온다 |
| LinkedIn 확장 방식 | 스크롤 깊이 실험 먼저 → 전량 | 4회 고정으로 전량 순회 | 4회 기준 매칭률이 10.3%다. 189명 전량을 돌려도 ~68건(10.3%)에 그친다. 깊이를 늘려 매칭률 자체를 올리는 편이 같은 시간에 더 많이 얻는다 |
| `BL-0504-02` 처리 | 인증 프로브 가드만 | 인증 실패 상태 기록 UI 전량 구현 | 본 계획의 목적은 커버리지 확대다. UI 구현은 `server.py`·`script.js`까지 번져 범위가 커진다. 30~50분 순회의 조용한 실패만 막으면 목적은 달성된다 |
