## 2. 문제

### P1 — 뷰어 콘솔 소음이 진짜 문제를 가린다

업데이트 클릭 순간 `ERR_NETWORK_CHANGED`로 로컬 요청 5건이 끊긴다. 실질 피해는 거의 없다.

- prefetch 실패 2건은 **무해하다**. hover 시점 최적화일 뿐이고(`script.js:3111`), 클릭하면 `ensurePostDetail`이 다시 가져온다
- 이미지 3건만 리렌더 전까지 깨진 채 남는다

다만 콘솔에 빨간 글씨로 남아 실제 결함을 가린다. 그리고 브라우저 4개 동시 기동이라는 트리거 자체는 회피 가능하다.

### P2 — `지표 보유만` 필터가 소임을 다했다

도입 시점(2026-08-24) 보유율은 5.2%였고, 이 버튼은 "재수집 없이 103건을 첫 화면에 모으는 유일한 수단"이었다. 지금은 93.6%이므로 **2,112건 중 135건(6.4%)만 걸러낸다.** 게다가

- `반응순` 정렬이 이미 같은 일을 한다 (1.1 #3)
- 정렬은 새로고침에도 유지되는데 이 토글만 휘발한다 (1.1 #4)

남은 실효는 X(21.1%)와 조합할 때뿐인데, 그건 `BL-0824-08` 미해결의 부작용이지 필터가 풀 문제가 아니다.

### P3 — 유튜브 수집 범위가 등록된 것의 1/3

`PLAYLISTS`에 3개가 등록돼 있으나 런처는 `drive7` 하나만 넘긴다. 이는 버그가 아니라 선행 계획 4.7절의 **파일럿 제한이 그대로 남은 것**이다("전량은 사용자가 파일럿 결과를 보고 명시적으로 지시할 때만").

문제는 그 사실이 **화면에 전혀 드러나지 않는다**는 점이다. 완료 팝업은 "YouTube 0건 추가"만 보여주므로, 정상 동작과 범위 누락을 구분할 수 없다. 실제로 이번에 사용자가 "조용한 실패 아닌가" 의심한 원인이 이것이다.

### P4 — 지표 갱신 구조가 3개 플랫폼에 없고, 있는 것도 검증되지 않았다

- Threads·X·YouTube는 최초 1회 스냅샷으로 영구 고정된다
- 그 값이 **언제 기준인지 기록조차 없다**(`metrics_updated_at` 0건)
- LinkedIn 정책은 존재하지만 **재갱신 분기가 한 번도 실행된 적 없다**(1.1 #17)

그리고 지금 구조로는 사후 분석조차 어렵다. 일자별 파일은 "그날의 값"이지 "그날 읽은 값"이 아니다 — 재수집하지 않은 글도 병합 과정에서 같은 값이 그대로 복사돼 실린다. 그래서 **"안 변한 것"과 "안 읽은 것"을 구분할 수 없다.** 이번 조사에서 실제로 이 함정에 빠져 잘못된 결론을 냈다(5절 참조).

### P5 — 새로 만든 태그가 추천 목록에 나오지 않는다

사용자가 태그 관리 화면에서 `✅SNS벤치마킹`을 만들었으나, 게시글 카드의 `+Tag` 추천 칩에 나오지 않는다. 새로고침해도 같다. 병행 세션이 증상을 제기했고, 이 세션에서 코드로 원인을 확인했다.

**데이터 유실이 아니다.** 카탈로그 파일에 정상 저장돼 있고(1.1 #22), 고아 태그도 0개다.

원인은 추천 목록 생성부다(`web_viewer/script.js:2965-2966`).

```js
const allExistingTags = new Set();
Object.values(postTags).forEach(tags => tags.forEach(tag => allExistingTags.add(tag)));
```

재료가 **`postTags`(실제 게시글에 붙어 있는 태그)뿐**이고 카탈로그(`tagCatalog`)는 전혀 참조하지 않는다. 따라서 **아직 아무 게시글에도 안 붙은 태그는 구조적으로 추천에 나올 수 없다.** 관리 화면의 "(0개)" 표시가 그대로 원인이다.

결과적으로 새 태그는 **최소 한 번 직접 타이핑해야만** 그다음부터 추천에 나오는 닭-달걀 상태다. 태그 관리 화면에서 태그를 만드는 기능 자체가 절반만 동작하는 셈이다.

### P6 — 정적 자산 캐시버스터가 멈춰 있다

`index.html:25`·`:643`의 `?v=` 값이 `20260824-metrics-w1`에 고정돼 있다(1.1 #27). 이 상태로 `script.js`를 고치면 **브라우저가 이전 파일을 계속 쓴다.** 선례가 있다 — 커밋 `d0ab5f6` "정적 자산 캐시버스터 갱신으로 지표 배지 반영".

W1·W1-T·W3가 모두 `script.js`를 건드리므로, 갱신을 빠뜨리면 **코드는 맞는데 화면은 그대로**인 상태가 되고 검증 자체가 무의미해진다.

**전체 선행 조건**: 이 계획은 **X 수집 개선 병행 세션(`dfdff5f4`)의 작업이 종료된 뒤** 실행한다. 이유는 두 가지다.

2. **`git status` 오염** — 현재 미커밋 산출물이 이미 8건 쌓여 있다. 두 세션이 동시에 수집을 돌리면 통합본·수집 파일이 뒤섞여 되돌리기가 어려워진다

W2는 W1과 파일이 겹치지 않아 병행 가능하나, 위 선행 조건은 동일하게 적용된다.

**W3는 반드시 W5보다 먼저**다 — 기록 없이 정책을 켜면 2절 P4의 함정을 그대로 반복한다.

| # | 항목 | 자동 증거 |
|---|---|---|
| V1 | 기존 e2e 회귀 없음 | `pytest tests/e2e/test_metric_layout_ui.py tests/e2e/test_core_ui.py` 종료코드 0 |

#### V4를 실행 가능하게 만드는 방법

`scrapRunInProgress`는 `DOMContentLoaded` 콜백 내부에 선언돼 있어(`web_viewer/script.js:435`) **Playwright에서 `window`를 통해 직접 세울 수 없다.** 그렇다고 업데이트 버튼을 누르면 `/api/run-scrap`이 실제로 호출돼(`:1135`) 진짜 수집이 돌아간다 — X 병행 세션·`output_*`와 충돌한다.

따라서 **네트워크 인터셉트로 가짜 스크랩 상태를 만든다.** 코드에 테스트 전용 노출(`window.__scrapRunInProgress` 같은 것)을 추가하지 않는다.

```
1. page.route('**/api/run-scrap', ...) 로 요청을 가로채
   즉시 응답하지 않고 붙잡아 둔다 (스크랩이 "진행 중"인 상태 재현)
   → 실제 서버로 전달되지 않으므로 수집이 돌지 않는다
2. page.route('**/api/status', ...) 는 정상 200을 반환하도록 fulfill
   (버튼 핸들러가 :1127 에서 먼저 이걸 확인한다)
3. page.on('dialog', d => d.accept()) 로 confirm(:1112) 승인
4. 업데이트 버튼 클릭 → scrapRunInProgress = true 가 됨 (:1115)
5. 카드에 hover → page.on('request') 로 '/api/post/' 요청 0건 assert
6. 붙잡아 둔 run-scrap 요청을 abort 하고 페이지를 닫는다
```

`/api/run-scrap`을 가로채므로 `total_scrap.py`는 실행되지 않는다. 서버 상태도 바뀌지 않는다.

**이 방식이 불가능하다고 판명되면 V4를 자동화하지 않고 W1에서 제외한다.** 대신 A 가드의 존재를 코드 리뷰로 확인하고, 그 사실을 완료 보고에 명시한다 — 검증 못 한 것을 검증한 것처럼 적지 않는다.

증거 파일(pytest 출력, 캡처)은 `_docs/evidence/20260826_02/`에 남긴다. 커밋 포함 여부는 W1 커밋 시 사용자 지시를 받는다.

### W1-T — 신규 태그가 추천 목록에 나오지 않는 버그 수정

P5 해결. 병행 세션은 증상만 제기했고, 원인 확인과 계획 수립은 이 세션에서 수행했다(1.1 #20~#26).

#### 수정 내용

`web_viewer/script.js:2965-2966` 한 곳. 추천 목록의 재료를 **카탈로그 키 + 게시글에 붙은 태그의 합집합**으로 바꾼다.

```js
// 변경 전
const allExistingTags = new Set();
Object.values(postTags).forEach(tags => tags.forEach(tag => allExistingTags.add(tag)));

// 변경 후
const allExistingTags = new Set(Object.keys(tagCatalog || {}));
Object.values(postTags).forEach(tags => tags.forEach(tag => allExistingTags.add(tag)));
```

이후 필터(`postExistingTags` 제외)와 정렬(`.sort()`)은 **그대로 둔다.**

#### 이 형태가 안전한 근거

| 우려 | 확인 결과 |
|---|---|
| `tagCatalog`이 이 스코프에서 보이는가 | 보인다. `renderTags`(`:2917`)는 `DOMContentLoaded` 콜백(`:113`) 내부 중첩 함수이고 `tagCatalog`은 `:169` 선언이다(1.1 #24). 인자 전달 불필요 |
| 최신 값을 읽는가 | 읽는다. `tagCatalog`은 `let`이며 서버 로드 시 재할당된다(`:1964`). 추천 목록은 `+Tag` **클릭 시점**에 생성되므로 항상 그 시점의 값을 본다 |
| alias가 추천에 섞이지 않는가 | 섞이지 않는다. `normalizeTagCatalog`(`:1304-1319`)이 만드는 객체의 **키는 정규 태그명뿐**이고 alias는 값 안의 배열이다(1.1 #23) |
| 다른 곳에 영향이 있는가 | 없다. `allExistingTags`는 이 세 줄에서만 쓰인다(1.1 #21). `updateGlobalTags()`(`:3118`)는 별개 함수로 범위 밖 |
| 저장 데이터가 바뀌는가 | 바뀌지 않는다. `sns_tags.json`·`sns_tag_catalog.json`·`sns_user_metadata.json` 모두 건드리지 않는 **순수 표시 로직**이다 |
| 추천 칩을 눌렀을 때 서버에 저장되는가 | 저장된다. 기존 경로가 `localStorage` → `syncTagsToServer()`를 이미 수행한다(1.1 #25) |

#### 정렬은 바꾸지 않는다

사용 0건 태그가 현재 **1개뿐**이라(1.1 #22) 추천 칩이 20개 → 21개로 하나 늘 뿐이다. 완화할 문제가 없다. 사전순 `.sort()`를 유지한다. 0건 태그가 수십 개로 쌓이면 그때 재검토한다(4절 #14).

#### 회귀 방지 테스트 (신규)

태그 추천 관련 자동 테스트가 현재 **0건**이다(1.1 #28). `tests/e2e/test_tag_suggestion_ui.py`를 신설한다. 기존 e2e와 같은 구조를 쓴다 — headless 고정, 실행 중인 5000번 서버 전제(1.1 #29).

| 케이스 | 판정 |
|---|---|
| T1 | `+Tag` 클릭 시 추천 칩에 **사용 0건 카탈로그 태그가 포함**된다 |
| T2 | 해당 게시글에 **이미 붙은 태그는 추천에서 제외**된다 (기존 동작 회귀 없음) |
| T3 | 추천 칩 클릭 후 `GET /api/tags` 응답에 해당 태그가 반영된다 (서버 저장 확인) |

T1의 기댓값은 하드코딩하지 않는다. `sns_tag_catalog.json`과 `sns_tags.json`을 읽어 "카탈로그에 있고 그 게시글에 안 붙은 태그"를 계산해 비교한다. 특정 태그명(`✅SNS벤치마킹`)에 의존하면 그 태그를 쓰기 시작하는 순간 테스트가 죽는다.

**T3의 데이터 오염 처리 — 자동 원복으로 확정한다.** 수동 검증으로 미루지 않는다.

현재 `web_viewer/sns_tags.json`·`sns_tag_catalog.json`은 이미 `M`(수정) 상태다(사용자가 `✅SNS벤치마킹`을 만든 결과). 테스트가 여기에 더 쓰면 커밋 대상이 섞인다. 그래서 pytest fixture로 다음을 강제한다.

실제 엔드포인트는 `GET /api/get-tags`([scrap_sns_server.py:813](scrap_sns_server.py:813))와 `POST /api/save-tags`([:826](scrap_sns_server.py:826))다. `/api/tags`는 존재하지 않는다.

`save_tags()`는 받은 dict로 `sns_tags.json`을 **통째로 덮어쓴다**(`:838`). 즉 전체 교체 복원이 가능하다.

```
1. setup:  GET /api/get-tags 로 원본 전체를 받아 메모리에 보관
2. 테스트: 지정 게시글에 추천 칩 클릭 → GET /api/get-tags 로 반영 확인
3. teardown: 보관한 원본을 POST /api/save-tags 로 그대로 되돌린 뒤,
   GET /api/get-tags 결과가 setup 시점과 동일한지 assert
```

동일성 비교는 `json.dumps(..., sort_keys=True)` 결과로 한다 — 서버가 저장 시 `sort_keys=True`, `indent=4`로 재직렬화하므로(`:838`) 원본 파일과 byte 단위로 같지 않을 수 있다. **파싱된 자료구조가 같은지**를 본다.

teardown의 assert까지 통과해야 T3가 성공이다. 되돌리기 실패를 조용히 넘기지 않는다.

원복 대상 게시글은 테스트가 직접 고른다 — `sns_tags.json`에 아직 태그가 하나도 없는 게시글 1건을 골라 쓰면 원본이 "키 없음" 상태라 복원이 단순해진다.

### W2 — 유튜브 수집 확대

순서가 중요하다. 병렬화를 먼저 해야 이후 단계의 시간이 1/3이 된다.

#### W2-a. 요약 병렬화 (동시 3)

`call_agy()`는 `subprocess.run()` 한 번으로 끝나는 무상태 호출이다(`utils/agy_client.py:259`). 대화 세션 재사용도, 공유 핸들도 없어 병렬화에 구조적 장애물이 없다.

병렬화 시 반드시 함께 손볼 것 3가지:

| # | 문제 | 조치 |
|---|---|---|
| 1 | `append_ledger()`가 append 모드 파일 쓰기 (`youtube_scrap.py:466`) — 동시 호출 시 줄 섞임 | `threading.Lock`으로 감싼다 |
| 2 | `--max-summaries` 상한을 `summarized += 1` 카운터로 판정 — 병렬이면 **상한 초과 호출** 가능 (비용 직결) | 루프에서 세지 말고 **제출 전에 대상 목록을 잘라서** 넘긴다 |
| 3 | `collected.append()`가 `ordered_ids` 순서 의존 | 인덱스로 재정렬 (결정성 확보) |
| 4 | `Future.result()` 예외·타임아웃 시 전체를 중단할지 계속할지 미정 | **계속 진행으로 확정.** 실패 건은 원장에 남기고 나머지는 처리한다. 순차 구조에서 1건 타임아웃이 32분을 막았던 문제(1.1 #12)를 병렬로 푸는 것이 목적인데, 예외에 전체를 중단시키면 그 목적이 무너진다 |

요약 캐시는 영상별 파일(`summaries/{video_id}.json`)이라 충돌하지 않는다. 자막 provider는 요약 시작 전 종료돼 무관하다.

**동시성 3으로 시작하는 근거**: `agy --sandbox`는 호출마다 프로세스를 새로 띄우고 고정 오버헤드 약 5,500토큰이 붙는다(`agy_client.py:110`). Gemini 쪽 rate limit은 agy CLI가 감싸고 있어 우리 코드에서 확인할 수 없다. 원장에 rate limit 관련 에러가 늘지 않으면 4로 올린다 — 원장이 이미 계측 도구 역할을 하므로 별도 준비가 필요 없다.

**예상 효과** (1.1 #11 실측 기준)

| 건수 | 순차 | 병렬 3 | 병렬 4 |
|---|---|---|---|
| 71건 | 23분 | 8분 | 6분 |
| **187건** | 61분 | **20분** | 15분 |
| 382건 | 125분 | 42분 | 31분 |

시간 단축보다 **장애 격리**가 더 중요할 수 있다. 1.1 #12처럼 한 건이 막히면 순차 구조에서는 나머지 전부가 대기한다.

#### W2-b. 3개월분 187건 선행 처리

아래 명령을 **그대로** 실행한다. 배치 크기는 `50`으로 확정한다.

```
python youtube_scrap.py --mode update --playlists all --max-summaries 50
```

같은 명령을 **4회 반복**한다(50 × 4 = 200 ≥ 187). 매 회차는 이전 회차가 만든 요약 캐시를 히트해 건너뛰므로 중복 과금이 없다(아래 재개 근거). 마지막 회차 로그의 `이번 실행 agy 호출 N건`이 0이면 소진 완료다.

배치를 50으로 자른 이유: 병렬 3 기준 1회 약 5~6분이라 중간에 상태를 확인하고 끊을 수 있다. 187건을 한 번에 걸면 실패 시 어디까지 갔는지 로그를 뒤져야 한다.

터미널에서 실행한다. 뷰어 버튼은 동기 블로킹(`BL-0825-02`)이라 대량 처리에 부적합하다.

#### 중단·실패 시 재개 — 이미 지원된다

`load_cached_summary()`(`youtube_scrap.py:494`)가 `transcript_sha1` + `prompt_sha1` + `model` 3중 비교로 캐시를 판정한다. 셋이 모두 같으면 agy를 호출하지 않고 저장된 요약을 반환한다.

따라서 **타임아웃·에러·강제 종료 뒤 같은 명령을 다시 실행하면, 이미 요약된 건은 과금 없이 건너뛴다.** 요약 캐시(`output_youtube/summaries/*.json`)는 git 추적 대상이라 캐시 자체도 보존된다.

| 실패 유형 | 조치 |
|---|---|
| 개별 영상 타임아웃 (`agy-timeout`) | 그 건만 실패로 남고 나머지는 진행. 원장 `logs/youtube_summary_ledger.jsonl`에 기록. 재실행하면 실패분만 다시 시도 |
| 프로세스 강제 종료 | 같은 명령 재실행. 완료분은 캐시 히트로 건너뜀 |
| 요약 결과가 이상함 | `--refresh-summaries`로 해당 건만 재생성 (**전량에 쓰면 187건 전부 재과금된다 — 쓰지 않는다**) |

**롤백**: 요약·수집 산출물이 모두 git 추적 대상이므로 `git checkout -- output_youtube/`로 직전 커밋 상태로 되돌릴 수 있다. 단 **이미 발생한 API 비용은 되돌아오지 않는다.** 그래서 배치를 50으로 잘라 1회 노출을 제한한다.

**착수 전 필수**: W2-b 실행 직전에 `output_youtube/`와 `output_total/`이 커밋된 상태여야 롤백 지점이 존재한다. 현재 `output_youtube/python/youtube_py_full_20260826.json` 등이 미커밋(`??`)이므로, **W2 착수 전에 사용자에게 커밋 여부를 확인받는다.**

#### W2-c. 런처 인자 전환

`total_scrap.py:374`를 `--playlists all --max-summaries 15`로 바꾼다. 병렬 3 기준 15건 = 약 1분 40초라 버튼 체감이 거의 없다.

> **🔴 정정 (2026-08-26 실행 후)**: 여기에 "잔여분이 매 업데이트마다 15건씩 자동 소진된다"고 적었으나 **사실이 아니다.** 요약 대상이 `pending`(=`existing` 에 없는 영상)으로만 계산되므로(`youtube_scrap.py:791`→`:799`→`:835`), 상한에 걸려 `deferred` 로 저장된 영상은 **다음 실행에서 대상에서 아예 빠진다.** 실측: 295건이 `deferred` 인 상태에서 `--mode update --playlists all` 실행 시 `신규 0건 (기존 458건 재사용)` — 요약 시도 자체가 없었다. 이 결함은 `BL-0826-04` 로 등재했고, 잔여분 소진은 `--mode all` 로 해야 한다(`BL-0826-03`).

### W3 — `metrics_updated_at` 전 플랫폼 기록

`utils/post_schema.py:26`에 필드는 이미 있고 LinkedIn만 채운다. Threads·YouTube 수집 경로에서도 지표를 쓸 때 함께 기록한다.

동시에 뷰어 지표 행에 **기준일**을 표시한다(예: `8/26 기준`). 갱신 주기를 아무리 짧게 잡아도 시점 차이는 남으므로, 이 표시가 갱신 자체보다 중요할 수 있다.

**이 웨이브의 진짜 목적**은 화면 표시가 아니라 **"읽은 값"과 "복사된 값"의 구분**이다. 이것이 있어야 일자별 파일 + git만으로 완전한 시계열이 복원된다(P4 참조).

### W5 — 갱신 정책 이식

#### 공통: 정책 모듈을 플랫폼 중립으로 승격

`classify_target` / `select_targets`(`utils/linkedin_metrics.py:177`, `:218`)에서 LinkedIn 의존 부분은 `activity_id` 추출뿐이다. 판정 로직(신선도 / 갱신주기 / 실패 한도 / 상한)은 그대로 재사용 가능하다. `utils/metric_refresh.py`로 승격하고 플랫폼별 파라미터만 주입한다. 세 번 복붙하면 정책이 세 벌로 갈라진다.

#### 플랫폼별 파라미터

| 플랫폼 | 신선도 | 갱신 주기 | 1회 상한 | 비고 |
|---|---|---|---|---|
| LinkedIn | 30일 | 7일 | 120건 | 현행 유지 |
| YouTube | 30일 | 7일 | — | `videos.list`가 50건 배치라 **82건 전량 갱신해도 API 2회**. 지표 전용 경로를 따로 만들어 **자막·요약 재생성은 절대 타지 않게 한다** |
| Threads | **14일** | **5일** | **50건** | 아래 근거 참조 |

Threads를 LinkedIn(30일/7일)보다 **짧게** 잡는 이유: 사용자 가설("Threads·X는 수렴이 빠르다")이 맞는지 확인하려면 관측이 필요한데, 지금은 관측 표본이 0건이다(1.1 #16). 짧게 잡아 관측을 빨리 쌓은 뒤, 실제로 안 변한다는 게 확인되면 늘린다. 재수집 비용이 20초 수준이라(1.1 #14) 이 방향이 안전하다.

Threads의 유일한 진짜 제약은 시간이 아니라 **로그인 세션 노출**이다(LinkedIn과 달리 로그인 경로로 읽는다). 1회 상한 50건으로 고정한다.

#### 운영 로그 — 사람이 기억하지 않아도 되게 만드는 장치

`total_scrap.py` 완료 로그와 뷰어 완료 팝업에 한 줄을 추가한다.

```
지표 갱신 12건 · 값이 바뀐 글 3건 (최대 +18)
```

이것이 이 계획에서 **가장 중요한 한 줄**이다. 업데이트를 누를 때마다 결과가 눈앞에 뜨므로, 파라미터 재검토 시점을 사람이 달력에 기억할 필요가 없다. "3주째 변화 0건"이면 그 자리에서 주기를 늘리는 판단이 서고, 계속 바뀌면 유지한다.

측정 코드가 아니라 **운영 로그**다. 실험이 끝나도 지울 필요가 없다.

**서버 필터 분기 추가가 함께 필요하다.** `_scrap_progress_message_from_line()`(`scrap_sns_server.py:115`)은 **화이트리스트**다 — 지정된 문자열·정규식에 맞지 않는 줄은 전부 `None`으로 버린다(`:118`). `total_scrap.py`에 로그를 출력하는 것만으로는 뷰어 팝업·`logs/scrap_progress.log`에 **절대 도달하지 못한다.**

따라서 W5는 두 파일을 함께 고친다.

| 파일 | 변경 |
|---|---|
| `total_scrap.py` | 갱신 결과 집계 후 `지표 갱신 N건 · 값이 바뀐 글 M건` 형식으로 stdout 출력 |
| `scrap_sns_server.py:115` | 위 패턴을 인식하는 분기를 `_scrap_progress_message_from_line()`에 추가 |

기존 분기들과 같은 방식(문자열 포함 검사 또는 `re.search`)을 쓴다. 새 규칙 체계를 만들지 않는다.

#### 사후 분석 스크립트

`scripts/analyze_metric_growth.py`를 `scripts/`에 둔다. 언제 실행하든 그 시점까지 축적된 전부로 답을 낸다. **운영 경로에서 호출하지 않는다** — 정규 파이프라인은 건드리지 않는다.

#### 재검토를 백로그 착수조건으로 등재

날짜 알람이 아니라 조건으로 건다. 이 레포의 기존 관행(`BL-0825-02`의 "실제로 버튼이 묶여 불편이 발생했을 때")과 같다.

> 지표 갱신 파라미터 재검토 · **착수 조건**: 갱신 관측이 200건 이상 쌓였을 때. 위 운영 로그로 확인 가능

#### 롤백과 부분 실패 처리

W5는 수집 데이터의 지표 필드를 **덮어쓴다**. 안전망을 명시한다.

| 상황 | 조치 |
|---|---|
| 갱신 결과가 잘못됨 | `output_*/python/*.json`이 git 추적 대상이므로 `git checkout -- output_threads/ output_youtube/ output_linkedin/`로 원복 (**LinkedIn 포함** — 공통 모듈 승격으로 LinkedIn 갱신 경로도 함께 바뀐다) |

**착수 전 필수**: W5 실행 직전에 `output_threads/`·`output_youtube/`·**`output_linkedin/`**·`output_total/`이 커밋된 상태여야 롤백 지점이 있다. 현재 미커밋 산출물이 다수이므로 **W5 착수 전 커밋 여부를 사용자에게 확인받는다.**
