### B1. 상단 건수 라벨이 `N / M 건` 형태를 잃어 기존 테스트가 깨진다 — 계획에 언급 없음

계획 3.2(2)는 MY 탭의 모집단을 **내 글 총건수(68건)** 로 바꾼다. 그런데 `updateTotalPostsLabel()`은 보이는 수와 모집단이 같으면 슬래시를 빼고 `"68 건"`만 출력한다.

```javascript
// web_viewer/script.js:257-261
el.textContent = (visibleCount === null || visibleCount === total)
    ? `${total} 건`
    : `${visibleCount} / ${total} 건`;
```

실측으로 **숨김 처리된 내 글은 0건**이다(숨김 3건은 모두 타인 Threads 글). 따라서 MY 탭에서 보이는 수(68) == 모집단(68) → 라벨은 `"68 건"`이 되고 슬래시가 사라진다.

- `tests/e2e/test_my_posts_filter_ui.py:373` `test_total_label_keeps_slash_form`이 `re.fullmatch(r"\d+\s*/\s*\d+\s*건")`을 단언하므로 **확정 실패**한다.
- 계획의 개편 대상 목록(3.2(3))에 이 테스트가 **없다.**

**요구 수정**: (a) 이 테스트를 삭제 또는 `N 건` 형태도 허용하도록 개편 대상에 명시하고, (b) MY 탭에서 슬래시 없는 `68 건`이 **의도된 표시**임을 계획에 적는다. (필터를 걸었는데 분모가 안 보이는 게 맞는지는 사용자 판단 사항 — 아래 D1)

## Required Fixes (비차단이나 반영 권장)

### R1. 3.1의 최신순 단언이 상위 두 글을 구분하지 못한다 — 잘못된 카드가 위에 있어도 통과한다

내 글 중 최신 두 건은 **같은 내용을 두 플랫폼에 교차 게시한 글**이다.

```
seq 2558  linkedin  2026-08-25 15:34:06  "<AI 바이브코딩 강의, 해보기 전엔 미처 …"
seq 2557  threads   2026-08-25 15:31:04  "AI 바이브코딩 강의, 해보기 전엔 미처 몰…"
```

기존 V12 방식대로 `본문 앞 20자 in first_card` 로 단언하면, Threads 글이 위로 올라와도 LinkedIn 본문이 그 문자열을 포함하므로 **통과해 버린다.** 정렬이 뒤집혀도 잡히지 않는다.

**수정안**: 카드에 이미 `article.dataset.platform`이 붙어 있다(`script.js:2708`). 본문과 **플랫폼을 함께** 단언한다.

```python
first = viewer.locator(CARD).first
assert first.get_attribute("data-platform") == newest["sns_platform"]
assert head in first.inner_text()
```

추가로 정렬을 명시적으로 `로컬수집순(saved)`으로 고정한다. 이 단언은 `saved` 정렬에서만 성립하는데, 사용자의 `localStorage.sns_sort_order`가 `engagement` 등이면 깨진다.

### R2. `getServerPlatformFilter()`에 `'my'` 처리가 없다 — 검색 중 MY 탭이 비어 보일 수 있다

`getServerPlatformFilter('my')`는 목록에 없으므로 `''`를 반환한다(`script.js:1771-1774`). 검색어가 있는 상태에서 MY 탭을 누르면 서버에 플랫폼 필터 없이 **최대 500건**을 요청하고(`/api/search`에 내 글 파라미터 없음 — `scrap_sns_server.py:1394-1411` 확인), 클라이언트가 그중에서 내 글을 걸러낸다. 내 글은 전체의 2.7%(68/2,558)라 **흔한 단어로 검색하면 500건 안에 내 글이 한 건도 안 들어와 MY 탭이 0건**이 된다.

이건 지금도 같은 구조라 신규 회귀는 아니다. 다만 계획이 옵션 2·3을 기각한 근거가 *"저자 필터나 검색으로 충분히 대체 가능"* 이므로, **그 근거의 절반(검색)이 신뢰할 수 없다**는 점은 계획에 적어야 한다. 저자 필터는 확인 결과 정상 동작하므로 기각 근거를 **저자 필터 단독**으로 좁히거나, `/api/search`에 `own=1` 파라미터를 추가하는 후속 백로그를 남긴다.

### R3. 제안 코드의 `currentFilter === 'my'` 중복

계획 3.2(2)의 `matchesFilter`와 `matchesOwn` 양쪽에 `currentFilter === 'my' ? isOwnPost(post)`가 들어 있다. 동작은 같지만 나중에 한쪽만 고치면 어긋난다. `matchesFilter`에서 `'my'`는 `true`로 두고 소유 판정은 `matchesOwn` 한 곳으로 모은다.

### R4. `index.html` 수정 방식 — 새 버튼 추가보다 기존 버튼 개조가 안전하다

`#myPostsBtn`은 **이미 `#filterContainer` 안에**, YouTube 칩 바로 뒤에 있다(`index.html:147-156`). 계획대로 "새 칩을 추가하고 기존 요소를 제거"하면 위치가 바뀔 수 있다. 같은 자리에서 `id`/`aria-pressed`를 떼고 `class="filter-chip …"` + `data-filter="my"` 를 붙이는 편이 diff도 작고 위치도 보존된다. 위임 핸들러(`script.js:303-318`)가 `.filter-chip`을 잡으므로 active 상태 관리는 자동으로 된다.

### R5. 검증 명령어와 완료 기준 보강

계획 4장의 명령어에 **`test_own_post_interleave_ui.py`가 빠져 있다.** 3.1에서 "그 파일도 함께 고쳐야 한다"고 써 놓고 검증에서 돌리지 않는다. 또 AGENTS.md는 `index.html`·`web_viewer/` 변경 후 **5000번 서버 재시작**을 요구한다.

```powershell
wscript sns_hub.vbs
pytest tests/e2e/test_my_posts_filter_ui.py tests/e2e/test_own_post_interleave_ui.py -v
pytest tests/e2e/test_core_ui.py -v
pytest tests/unit -v
```

`test_core_ui.py`는 필터 칩 전반을 만지므로 회귀 확인 대상에 넣는다.

### D1. MY 탭에서 분모가 사라지는 표시를 받아들일 것인가
B1의 결과로 MY 탭 라벨이 `68 건`이 된다. "필터를 걸었는데 전체 대비 몇 건인지 안 보인다"가 불편하면, MY 탭에서는 모집단을 **전체(2,558)** 로 둬서 `68 / 2558 건`으로 보이게 하는 선택지도 있다. 어느 쪽이든 계획에 못 박아야 테스트를 쓸 수 있다.

### D2. 새로고침 후 MY 탭이 풀리는 것을 받아들일 것인가
지금은 MY 상태가 `localStorage`에 저장돼 **새로고침해도 유지**된다(`test_my_filter_persists_across_reload`가 이를 단언). 계획은 상태 저장을 전부 없애는데, `currentFilter`는 애초에 저장되지 않으므로(`script.js:180` `let currentFilter = 'all'`) **새로고침하면 항상 All로 돌아간다.**

이건 계획이 명시하지 않은 동작 변경이다. 다만 이번 문제의 근본 원인이 "MY 상태가 영구 저장돼 탭 이동 후에도 고착된 것"이었으므로, **저장하지 않는 편이 문제 재발을 막는다**는 점에서 나는 저장 없음(계획대로)을 권한다. 사용자가 "MY를 자주 쓰니 새로고침해도 유지되면 좋겠다"면 `currentFilter` 전체를 저장하는 별도 결정이 된다.
