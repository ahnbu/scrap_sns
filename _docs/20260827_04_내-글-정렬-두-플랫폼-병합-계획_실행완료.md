### 1.2 직전 수정이 남긴 구조

`_docs/20260827_03` 이 「로컬수집순」의 내 글 역순 문제를 고치면서 이 구조를 만들었다(`total_scrap.py:615-621`).

```
for group in (own_posts, threads_own_posts):     ← 플랫폼별로 따로 처리
    batch_key = min(crawled_at)                   ← 묶음 대표 시각
    rank = 작성일 오름차순 순위
```

정렬 1차 키는 `_saved_at_key()` 가 돌려주는 **묶음 대표 시각**(= 수집 시각), 2차 키는 묶음 안의 순위다.

**역순 문제를 고친 것은 옳다.** 블록 내부가 작성일순으로 잘 서 있다(#6). 이 계획은 그 구조를 유지하고 **"묶음을 플랫폼별로 쪼갠 것" 하나만** 바꾼다.

### 1.3 이 접근의 트레이드오프

**얻는 것**: 같은 날 올린 링크드인·쓰레드가 화면에서 나란히 붙는다. 두 플랫폼 성과를 스크롤 없이 비교할 수 있다.

**잃는 것**: 「로컬수집순」이라는 이름과 내 글의 실제 정렬 근거가 더 멀어진다. 내 글에 한해 1차 키는 묶음 시각(수집), 2차 키는 작성일이 되는데, 이 계획 후에도 그 구조는 그대로다. 다만 **내 글은 애초에 "저장"한 적이 없어** 어떤 기준을 쓰든 이름과 완전히 맞을 수 없다(직전 계획 `_saved_at_key` 주석의 판단과 같다).

## 2. 문제

### P1 — 내 글이 플랫폼별 두 덩어리로 갈라진다

묶음을 플랫폼별로 잡으므로(1.2) 블록이 둘 생긴다. 화면에서 쓰레드 32건을 다 지나야 링크드인이 나온다(#2). 같은 날 올린 같은 원고가 **32칸 떨어져** 있다.

### P2 — 덩어리 위치가 수집 시점에 좌우돼 불안정하다

블록의 자리는 `min(crawled_at)` 이 정한다. 오늘 Threads를 처음 수집했다는 이유만으로 Threads가 위에 왔다(#3·#4). **내일 LinkedIn만 재수집하면 정반대로 뒤집힌다.** 같은 글이 어제와 오늘 다른 자리에 있다.

수집 시점은 글의 내용·성과와 무관한 우연이다. 그것이 화면 순서의 1차 기준인 한 순서는 계속 흔들린다.

### P3 — 같은 날 안에서 플랫폼 순서가 들쭉날쭉하다

P1·P2를 고쳐 날짜순으로 섞어도 남는 문제다. 작성 시각(분 단위)으로 세우면 그날 어느 쪽을 먼저 올렸느냐에 따라 순서가 바뀐다(#7).

| 날짜 | 링크드인 | 쓰레드 | 앞에 오는 쪽 |
|---|---|---|---|
| 2026-08-25 | 15:34 | 15:31 | 링크드인 |
| 2026-07-24 | 20:07 | 20:02 | 링크드인 |
| 2026-07-03 | 15:37 | 15:39 | **쓰레드** |
| 2026-05-15 | 13:08 | 13:11 | **쓰레드** |
| 2026-04-23 | 10:16 | 10:16 | 동률(불확정) |

사용자가 직접 제기한 문제다 — "어떤 날은 쓰레드가 앞에 오고 어떤 날은 링크드인이 앞에 오는데 이게 맞는지 모르겠다."

### P4 — 「성과순」에서 링크드인이 통째로 바닥에 깔린다

성과순은 좋아요+댓글+공유를 더해 세운다(`web_viewer/script.js:220`). 그런데 실측이 이렇다(#9·#10).

| | 좋아요 | 댓글 | 공유 |
|---|---|---|---|
| LinkedIn 내 글 36건 | **3** | 3 | **0** |
| Threads 내 글 32건 | **32** | 32 | 32 |

링크드인 33건이 지표 0으로 맨 아래 깔린다. **성과가 나빠서가 아니라 숫자가 없어서다.**

#### 원인 — 결함이 아니라 한 번도 실행되지 않았다

처음에는 "수집기가 막혔다"고 의심했으나 로그로 확인하니 아니었다.

```
비로그인 지표 수집기 마지막 실행 : 2026-08-26 10:10:04   (#13)
내 글 파일이 처음 생긴 시각      : 2026-08-26 12:56:09   (#14)
```

**수집기가 돌 때 내 글 파일이 아직 없었다.** `linkedin_metric_single.py:85` 가 `if not path: 건너뜁니다` 로 지나갔고, 그 뒤로 수집기가 다시 돈 적이 없다. `logs/linkedin.log` 에 "내 글" 문자열이 0회인 것이 그 증거다(#15).

막힌 것이 아니라는 근거도 있다. 지금 `select_own_targets(posts)` 를 돌리면 **정상적으로 20건을 고르고**(#16), 8/26 내 글 실패 기록은 0건이다(#17).

즉 **한 번 돌리면 채워진다.** 다만 한 번에 20건이 상한이라(`utils/metric_refresh.py:43`) 36건 전부를 채우려면 2회이거나 상한을 올려 1회다.

### P5 — 지금 채워도 다음 실행에 다시 비워질 수 있다

P4 를 한 번 돌려 채워도 끝이 아니다. **같은 파일을 두 프로세스가 병렬로 쓴다**(#19).

```
consumer 웨이브 (전부 동시 시작, #18)
├ LinkedIn  : linkedin_metric_single.py   ← linkedin_own_full 읽고 쓴다 (반응수)
├ MyPosts   : my_posts_scrap.py           ← linkedin_own_full 읽고 쓴다 (본문·노출수)
└ MyThreads : my_threads_scrap.py
```

`_docs/20260826_03` 3.4.1 이 "저장글과 다른 파일을 써서 경합을 막는다"고 했는데, 그건 **저장글 파일과의** 경합만 막았다. **내 글 파일 자체를 두 프로세스가 공유**하는 것은 그대로다.

`merge_own_post()` 가 기존 반응수를 보존하지만 **자기가 파일을 읽은 시점 이후에 상대가 쓴 값은 보존할 수 없다.** 늦게 저장하는 쪽이 이긴다.

날짜가 바뀌는 날은 더 꼬인다. `my_posts_scrap.py` 는 **오늘 날짜 파일**을 새로 만들고, `linkedin_metric_single.py` 는 `latest_own_full_file()` 로 그 시점의 최신 파일에 쓴다. 둘이 다른 파일을 볼 수 있다.

**이번 미충전은 이 경합이 아니라 실행 순서(#13·#14) 때문이었다.** 하지만 T4 로 채우고 나면 다음 정기 업데이트부터 이 경합이 실제로 발동한다. **고치지 않으면 오늘 채운 것이 다음 주에 사라진다.**

#### 이미 한 번 겹쳤다 — 가설이 아니다

반응수를 가진 3건의 타임스탬프가 그 증거다.

```
my_posts_scrap.py 저장       12:56:09.799854   (#24)
   ↓ 41초 뒤
지표 수집기가 3건을 덮어씀   12:56:50.478      (#23)
                             12:56:59.079
                             12:57:07.754
```

**두 프로세스가 같은 파일에 순차로 썼다.** 이번엔 `my_posts_scrap.py` 가 **먼저** 저장해서 지표 3건이 살아남았다. 순서가 반대였으면 3건 다 사라졌다.

3건이 다른 33건과 형식까지 다르다(#22·#23) — 33건은 타임존이 붙은 어댑터 값이고 3건은 타임존 없는 밀리초 값이다. **한 파일 안에 두 가지 형식이 섞여 있다.** 8~9초 간격은 `linkedin_metric_single.py` 의 건당 지연 4~6초와 맞는다(#25).

즉 **P5 는 앞으로 생길 위험이 아니라 이미 발생한 사건이고, 운으로 피했다.**

#### 쓰는 주체가 셋이다

`scripts/linkedin_metric_backfill.py` 도 같은 파일에 `like_count`·`comment_count`·`metrics_updated_at` 을 쓴다(#26). 지금 남아 있는 백업 2개는 저장글 대상이라 이번 3건의 출처는 아니지만(#27), **수동으로 아무 때나 실행할 수 있는 세 번째 쓰기 주체**다.

### P6 — `metrics_updated_at` 에 두 가지 형식이 섞여 있다

같은 파일 안에 이렇게 있다(#22·#23).

| 건수 | 값 | 형식 |
|---|---|---|
| 33 | `2026-08-26T12:56:09+09:00` | ISO + **타임존** |
| 3 | `2026-08-26T12:56:50.478` | ISO + **밀리초, 타임존 없음** |

**이 값은 갱신 정책이 신선도를 판단하는 근거다**(`utils/metric_refresh.py` `refresh_after_days`). 형식이 갈리면 비교가 어긋날 수 있다. 지금은 두 값의 날짜가 같아 증상이 안 보이지만, 타임존이 붙은 값과 안 붙은 값을 문자열로 비교하면 경계에서 틀린다.

쓰는 주체가 셋인데(P5) 각자 다른 형식을 넣고 있다는 뜻이기도 하다.

### P7 — 정렬 회귀를 잡을 테스트가 없다

내 글 정렬을 단언하는 단위 테스트가 **하나도 없다**(#11). 직전 수정도 e2e만 추가했고 그 e2e는 순서를 보지 않는다(#12). 오늘만 이 영역이 두 번(직전 수정, 이 계획) 바뀌는데 회귀를 잡을 그물이 없다.

### 🆕 P8 — 갱신 정책이 타임존 있는 시각을 읽으면 프로세스가 죽는다 (실행 차단)

**초안의 T6-a 를 그대로 넣으면 LinkedIn 지표 갱신 전체가 예외로 멈춘다.** 검수에서 실측으로 재현했다(#28·#30).

```
utils/metric_refresh.py
  now = now or datetime.now()          ← 타임존 없는 값
  parse_dt("2026-08-26T12:56:09+09:00") ← fromisoformat 이 타임존 있는 값을 돌려준다
  now - parsed                          ← TypeError
```

`select_targets()` 는 `linkedin_metric_single.py:90` 에서 **try 없이** 불린다. 예외가 나면 프로세스가 통째로 죽고, 저장글 지표 갱신까지 같이 멈춘다.

지금 안 터지는 이유는 우연이다(#29). 타임존 붙은 33건이 `like_count=None` 이라 1순위 `missing-metrics` 로 먼저 빠져나가 신선도 검사에 **도달하지 않는다.** **T4 가 그 33건을 채우는 순간 도달하기 시작한다.**

폭발 반경은 내 글에 그치지 않는다. T6-a 는 저장글 지표도 같은 함수로 쓰므로, `metrics_updated_at` 을 가진 저장글 **544건**(#30)이 전부 이 경로를 탄다.

즉 **T6-a 는 P6 을 고치는 게 아니라 P8 을 발동시키는 방아쇠다.** 순서를 뒤집어야 한다 — 읽는 쪽을 먼저 고치고 쓰는 쪽을 나중에 고친다.

### 🆕 P9 — 채운 지표가 다음 실행에서 「갱신 불필요」로 굳는다 (실행 차단)

`merge_own_post()` 는 `like_count`·`comment_count`·`share_count` 만 보존하고 **`metrics_updated_at` 은 보존하지 않는다**(#31). 어댑터가 `metrics_updated_at = collected_at` 을 넣으므로(`utils/my_posts_adapter.py:84`), `my_posts_scrap.py` 가 돌 때마다 **갱신 시각이 「지금」으로 리셋된다.**

초안의 T5-b 는 `my_posts_scrap.py` 를 **앞에** 두므로 이 리셋이 매번 먼저 일어난다.

```
my_posts_scrap.py            → metrics_updated_at = 지금        (반응수는 보존)
   && linkedin_metric_single.py --only own
                             → stale_days = 0 < 7 → up-to-date
                             → 🎯 대상 0건. 아무것도 안 읽는다
```

검수에서 실제 데이터로 재현했다. **반응수는 안 지워지지만 영원히 갱신되지 않는다.** 초안의 V19("반응수 보유 건수가 줄지 않는다")는 이 상태를 **통과시켜 버린다** — 건수가 줄지 않는 이유가 "경합이 해소돼서"가 아니라 "아무것도 안 돌아서"인데 구분하지 못한다.

## 3. 해결

### 3.1 범위

**한다**

- 내 글 두 묶음을 **하나**로 합친다 (P1·P2 해소)
- 같은 날이면 **링크드인을 위에** 고정한다 (P3 해소)
- **링크드인 내 글 반응수 36건을 채운다** (P4 해소)
- **내 글 파일에 쓰는 순서를 고정해 재발을 막는다** (P5 해소)
- **`metrics_updated_at` 형식을 하나로 통일한다** (P6 해소)
- 🆕 **갱신 정책이 타임존 있는 시각을 안전하게 읽게 한다** (P8 해소 — T6-a 의 **선행 조건**)
- 🆕 **`metrics_updated_at` 을 로그인 경로가 덮지 않게 한다** (P9 해소)
- 내 글 정렬 단위 테스트 신설 (P7 해소)
- 통합본 재생성 + 뷰어 확인

**하지 않는다**

- 「날짜순」·「별표순」 정렬의 같은 날 순서 (6절 #5)
- **「성과순」 정렬 로직 변경** (6절 #4) — 정렬은 옳다. 데이터를 채워서 푼다
- 기본 정렬 변경 (6절 #3)
- 뷰어 `script.js` 변경 — 이 계획은 **저장되는 순번과 지표 값만** 바꾼다

### 3.2 T1 — 두 묶음을 하나로 합친다 (P1·P2 해소)

`total_scrap.py:615-621` 의 반복을 하나로 바꾼다.

```
현재: for group in (own_posts, threads_own_posts):   ← 묶음 둘
변경: own_all = own_posts + threads_own_posts        ← 묶음 하나
```

`batch_key` 는 합친 전체의 `min(crawled_at)` 이다. 두 플랫폼 중 **먼저 수집한 쪽** 시각으로 블록이 자리 잡는다.

`max` 가 아니라 `min` 을 쓰는 이유: 블록이 "가장 최근 수집" 자리로 계속 올라오면 P2 의 불안정이 남는다. `min` 은 한 번 자리를 잡으면 그 뒤 수집으로 위로 튀지 않는다.

#### 🆕 기본 화면 최상단이 바뀐다 — 의도한 결과다

통합 `batch_key` 는 두 시각 중 이른 쪽인 `2026-08-26 12:56:09`(LinkedIn 수집 시각)이 된다. 그 결과 8/27 새벽에 담긴 **유튜브 2건이 내 글 블록 위로 올라간다**(#44).

「로컬수집순」 화면 최상단이 `내 글 32건` 에서 `유튜브 2건 → 내 글 68건` 으로 바뀐다. `min` 을 택한 이상 정상이며, 이 사실을 미리 알고 봐야 V7 결과를 오판하지 않는다. MY 필터를 켜면 유튜브는 빠지므로 V9 에는 영향이 없다.

### 3.3 T2 — 같은 날은 링크드인 먼저 (P3 해소)

정렬 키를 세 단계로 만든다.

| 순위 | 키 | 방향 |
|---|---|---|
| 1 | 작성 **날짜**(`created_at` 앞 10자) | 오름차순 |
| 2 | 플랫폼 고정 순서 | `threads` → `linkedin` |
| 3 | 작성 **시각** 전체 | 오름차순 |

#### 🔴 방향을 반대로 넣기 쉬운 지점

**배열은 오름차순으로 정렬하고 `sequence_id` 를 앞에서부터 매기는데, 뷰어는 `sequence_id` 내림차순으로 보여준다**(`web_viewer/script.js:2535` `b._seqId - a._seqId`). 즉 **배열에서 뒤에 있을수록 화면 위에 뜬다.**

따라서 같은 날 **링크드인을 화면 위에 두려면 배열에서는 링크드인이 뒤**여야 한다.

```
OWN_SAME_DAY_ORDER = {'threads': 0, 'linkedin': 1}
                       └ 배열 앞      └ 배열 뒤 = 화면 위
```

이 값을 뒤집으면 화면도 뒤집힌다. V1 이 이 방향을 직접 단언한다.

3차 키(작성 시각)는 같은 날 **같은 플랫폼**에 2건 이상일 때만 쓰인다. 현재 그런 날은 없지만(#43 실측) 앞으로 생길 수 있어 결정적 순서를 보장한다.

🆕 **3차 키는 `_normalize_ts()` 를 통과시킨다.** 지금 내 글 68건의 `created_at` 은 전부 `YYYY-MM-DD HH:MM:SS` 로 균일해(#42) 날것 문자열 비교로도 맞지만, 다른 어댑터가 `T` 구분자 값을 내면 `'T'(0x54) > ' '(0x20)` 때문에 같은 날 안에서 순서가 뒤집힌다. `_normalize_ts()` 는 이미 그 함정을 막으려고 만든 함수다(`total_scrap.py:678`). 1차 키의 앞 10자 슬라이스는 두 포맷 모두 안전하므로 그대로 둔다.

🆕 **`platform_sequence_id` 의 의미가 바뀐다.** 지금은 플랫폼 안의 순위(1~36 / 1~32)인데 T1 이후 내 글 한정으로 **두 플랫폼 통합 순위(1~68)** 가 된다. 이 필드를 읽는 곳은 `total_scrap.py:766` 과 `scripts/rebuild_total.py:57` 의 정렬 키 **둘뿐**이고 (검수 확인) 둘 다 대소 비교만 하므로 안전하다. 뷰어·API·스키마는 이 필드를 읽지 않는다.

### 3.4 T4 — 링크드인 내 글 반응수를 채운다 (P4 해소)

수집기를 고칠 것이 없다. **한 번도 안 돌았을 뿐이므로 돌린다.**

```
python linkedin_metric_single.py --only own --own-limit 40
```

`--own-limit` 은 기존 인자다(`linkedin_metric_single.py:66`). `--only own` 은 T5-a 로 새로 만든다.

#### 🆕 대상은 36건이 아니라 33건이다

검수에서 실제 파일로 돌려 확인했다(#32·#41).

| 구분 | 건수 | 사유 |
|---|---|---|
| 갱신 대상 | **33** | `like_count` 가 없다 (`missing-metrics`) |
| 제외 | **3** | 이미 `like_count` 를 갖고 있고 갱신 시각이 7일 안이다 (`up-to-date`) |
| 실패한도로 제외 | **0** | 6건의 `no-metrics-in-dom` 은 전부 저장글이다 |

**36건 전량 갱신은 이번 실행으로 되지 않는다.** 판정 기준을 33건 기준으로 다시 적는다 — **33건 중 28건 이상**(85%) 성공하면 통과. 그 미만이면 `scrap_failures_linkedin.json` 의 사유를 확인해 보고한다.

제외된 3건은 T6-b 대로 두면 7일 뒤 자동으로 대상이 된다. 값 자체는 이미 정상 경로가 넣은 것이라 급하지 않다. **손으로 고치지 않는다.**

#### 🆕 예상 소요는 약 6분이다

로그 실측으로 건당 6초(`0.1분`)이고 여기에 `polite_sleep` 4~6초가 붙어 **건당 약 11초**다(#37). 33건이면 **약 6분**. 초안이 적은 "약 2분"은 대기 시간만 세고 페이지 로드·대기 2.5초를 빠뜨린 값이다.

**headless 로 돈다**(`linkedin_metric_single.py:108` `launch(headless=True)`). 비로그인 익명 컨텍스트라 로그인 세션도 건드리지 않는다.

#### 전부 채워지지 않을 수 있다 — 그것도 정상이다

`no-metrics-in-dom` 실패가 8/25 저장글에서 6건 있었다(#17). 비로그인 공개 페이지가 지표를 렌더링하지 않는 글이 존재한다는 뜻이다. 내 글에서도 일부는 그럴 수 있다.

**판정 기준을 미리 정한다.** 36건 중 **30건 이상** 채워지면 성공으로 본다. 그 미만이면 실패 사유(`scrap_failures_linkedin.json` 의 `reason`)를 확인하고 남은 건수와 사유를 보고한다. 이 계획에서 그 원인까지 고치지는 않는다.

T4 는 **단독 실행**이라 P5 의 경합이 없다. 재발 방지는 T5 가 맡는다.

### 3.5 T5 — 내 글 파일에 쓰는 순서를 고정한다 (P5 해소)

내 글 파일을 만지는 프로세스를 **하나의 실행 슬롯에 직렬로 묶는다.** 동시에 쓰는 상황 자체를 없앤다.

#### T5-a — `linkedin_metric_single.py` 에 처리 범위 옵션을 추가한다

현재는 저장글과 내 글을 항상 둘 다 처리한다(#20). 갈라 실행할 수 있어야 직렬화가 된다.

```
--only {all,saved,own}    기본 all (기존 동작 유지)
```

`main()` 의 `sources` 구성 반복(`:82-95`)에서 해당 라벨만 남기면 된다. 기존 호출과 예약작업은 인자를 안 주므로 `all` 로 지금과 똑같이 동작한다.

#### T5-b — consumer 웨이브를 직렬로 묶는다

```
현재
├ LinkedIn : linkedin_metric_single.py                  ← 저장글 + 내 글
└ MyPosts  : my_posts_scrap.py                          ← 내 글        (동시 = 경합)

변경
├ LinkedIn : linkedin_metric_single.py --only saved     ← 저장글만
└ MyPosts  : my_posts_scrap.py && linkedin_metric_single.py --only own
                                    └ 앞이 끝난 뒤에 실행 = 경합 없음
```

`cmd /c` 를 거치므로 `&&` 체이닝이 그대로 동작한다(#21). **앞이 실패하면 뒤가 안 돈다** — 내 글 수집이 실패했는데 지표만 갱신하는 상황을 막아준다.

이 배치가 P4 의 근본 원인(#13·#14: 파일이 없을 때 수집기가 지나감)도 함께 없앤다. 이제 수집기가 **항상 파일이 생긴 뒤에** 돈다.

#### 🆕 T5-b 는 T5-d 없이는 오히려 해롭다

이 순서(`my_posts` 먼저)는 **P9 를 매 실행마다 발동시킨다.** 앞선 `my_posts_scrap.py` 가 `metrics_updated_at` 을 「지금」으로 리셋하므로 뒤이어 도는 지표 수집기가 **대상 0건**을 보고 그냥 끝난다. T5-d 를 반드시 함께 넣는다.

### 3.6 T6 — `metrics_updated_at` 형식을 통일한다 (P6 해소)

**정본 형식을 정한다: 타임존을 붙인 ISO 8601 (`2026-08-26T12:56:09+09:00`).**

#### 🔴🆕 T6-0 — 읽는 쪽을 먼저 고친다 (P8 해소, T6-a 의 선행 조건)

**T6-a 보다 반드시 먼저 한다. 순서를 뒤집으면 LinkedIn 지표 갱신 전체가 예외로 죽는다(P8).**

`utils/metric_refresh.py` 의 `days_since()` 가 naive `now` 에서 aware 값을 뺀다(#28). 지금도 타임존 붙은 값이 파일에 33건 있고, 안 터지는 건 그 33건이 신선도 검사에 도달하지 않기 때문일 뿐이다(#29).

고칠 자리는 `days_since()` 한 곳이다.

```python
def days_since(value, now):
    parsed = parse_dt(value)
    if parsed is None:
        return None
    # 🔴 타임존이 붙은 값과 안 붙은 값이 한 파일에 섞여 있다(#22·#23).
    #    naive - aware 는 TypeError 다. 비교 전에 한쪽으로 맞춘다.
    if parsed.tzinfo is not None:
        parsed = parsed.astimezone(KST).replace(tzinfo=None)
    return (now - parsed).total_seconds() / 86400.0
```

`now` 를 aware 로 바꾸는 대신 `parsed` 를 naive-KST 로 내리는 이유: `now` 는 이 모듈 밖에서도 호출자가 넘긴다(`select_targets(now=...)`, 테스트 다수). aware 로 올리면 그 호출자들이 전부 깨진다. **읽는 쪽에서 흡수하는 게 파급이 가장 작다.**

`KST` 는 `utils/auth_status.py:13` 의 것을 재사용한다(검수 확인: `timezone(timedelta(hours=9))` 로 존재).

#### 🔴🆕 T6-0b — `parse_dt()` 가 타임존을 잃지 않게 한다 (2차 검수 반영)

**초안은 이것을 「관찰 항목」으로 미뤘으나, 2차 검수 지적을 받아들여 T6-0 범위 안으로 끌어온다.**

`parse_dt()` 는 `strptime` 후보를 먼저 돌리는데 입력을 `text[: len(fmt) + 6]` 으로 자른다. **마이크로초 6자리와 타임존이 같이 있으면 그 절단이 정확히 타임존만 잘라내고 나머지가 성공적으로 파싱된다.** 실측:

| 입력 | 결과 | tzinfo |
|---|---|---|
| `2026-08-26T12:56:09+09:00` | `12:56:09` | **`+09:00` 유지** |
| `2026-08-26T12:56:09.123+09:00` | `12:56:09.123` | **`+09:00` 유지** |
| `2026-08-26T12:56:09.799854+09:00` | `12:56:09.799854` | 🔴 **None — 조용히 소실** |
| `2026-08-26T12:56:09.799854+00:00` | `12:56:09.799854` | 🔴 **None — 9시간 어긋난다** |

**T6-0 만으로는 못 막는다.** T6-0 의 `if parsed.tzinfo is not None:` 검사를 **우회**하기 때문이다 — 타임존이 이미 사라진 뒤라 검사에 걸리지 않는다.

**도달 가능성은 지금은 낮지만 0이 아니다.** 현재 `metrics_updated_at` 971건 중 타임존 있는 65건은 전부 마이크로초가 없고, T6-a 도 `timespec="milliseconds"` 라 마이크로초를 만들지 않는다. 그러나 외부 수집기(`sns_insight_update`)는 실제로 마이크로초를 낸다 — `linkedin_own_full_20260826.json` 의 `metadata.updated_at` 이 `2026-08-26T12:56:09.799854` 다. 그 값에 UTC 오프셋이 붙는 날 9시간이 어긋난다. **Threads Graph API 가 UTC 를 주는 레포라 이 조합은 언제든 들어올 수 있다.**

고칠 자리는 `parse_dt()` 의 순서 한 줄이다.

```python
def parse_dt(value):
    if not value:
        return None
    text = str(value).strip().replace("Z", "")
    # 🔴 fromisoformat 을 먼저 시도한다. strptime 절단 경로(text[:len(fmt)+6])는
    #    마이크로초 6자리 + 타임존 조합에서 타임존만 잘라내고 성공해버려,
    #    타임존이 조용히 사라진 naive 값을 돌려준다(검수 실측).
    try:
        return datetime.fromisoformat(text)
    except ValueError:
        pass
    for fmt in _DT_FORMATS:
        ...
```

`fromisoformat` 이 못 읽는 형식(`2026-08-26 12:56:09` 공백 구분자는 Python 3.11+ 에서 읽지만 그 이하에서는 못 읽는다)은 기존 `strptime` 루프가 그대로 받는다. **순서만 바꾸므로 기존에 파싱되던 값이 파싱 안 되는 경우는 없다.**

⚠️ **V23 에 이 케이스를 반드시 넣는다** — `parse_dt('...799854+00:00')` 이 타임존을 유지하는지, 그리고 `days_since` 가 그 값에서 예외 없이 올바른 일수를 돌려주는지.

#### 🆕 재생성 도구는 `scripts/rebuild_total.py` 다

수집 없이 저장된 full 파일만 다시 합치는 전용 스크립트가 이미 있다(#36). `merge_results`·`save_total` 을 그대로 import 하므로 T1·T2 가 자동으로 반영된다. **전체 재수집(수십 분 + 로그인)을 하지 않는다.**

```
python scripts/rebuild_total.py --dry-run   # 저장 없이 내 글 예상 순서만 출력
python scripts/rebuild_total.py             # 통합본 재생성
```

⚠️ **`--dry-run` 출력의 「연속 블록: 아니오」에 놀라지 않는다.** `_print_own_preview()` 가 플랫폼별로 순번이 연속인지 보고하는데(`scripts/rebuild_total.py:60-95`), T1 이후에는 두 플랫폼이 교차하므로 **양쪽 다 「아니오」가 정상**이다. 이 문구가 오판을 부르므로 **함께 손본다** — 내 글 전체를 한 블록으로 보고 연속성을 판정하고, 미리보기는 플랫폼별이 아니라 통합 순서로 출력한다.

## 7. 미확정 · 확인 범위

### Threads 내 글 파일에는 같은 구조가 없다 — 지금은

`output_threads_own/` 은 `my_threads_scrap.py` 하나만 읽고 쓴다. Threads 지표는 Graph API 가 5종을 한 번에 주므로 반응수를 채우는 별도 프로세스가 없기 때문이다.

앞으로 Threads 쪽에도 보조 수집기를 붙이면 **P5 와 똑같은 경합이 생긴다.** T5-b 의 직렬화 패턴을 그대로 쓰면 된다.

### 반응수 3건의 출처를 확정하지 못했다

`like_count` 를 가진 3건은 `source` 가 `my_insight_recent_activity`(내 글 수집 경로)인데, `utils/my_posts_adapter.py` 는 `like_count` 를 설정하지 않는다(`NON_LOGIN_PATH_METRIC_FIELDS` 로 보존만 한다). 백필 스크립트 로그(`logs/backfill_run_full.out`)는 Threads 대상이라 무관하다.

**어디서 들어왔는지 확인하지 못했다.** T4 를 돌리면 33건이 정상 경로로 덮이고 이 3건은 7일 뒤 대상이 되므로 실질 영향은 없다.

🆕 **검수에서 좁혀진 것**: `logs/linkedin.log` 는 `total_scrap.py` 가 리다이렉트해 만드는 파일이라 **오케스트레이션 실행만 담긴다**(`total_scrap.py:427-445`). 터미널에서 `python linkedin_metric_single.py` 를 손으로 돌리면 이 로그에 아무것도 안 남는다. 3건의 8~9초 간격이 `polite_sleep` 4~6초와 정확히 맞으므로(#23·#25) **수동 실행으로 보는 게 가장 자연스럽다.**

이 때문에 P4 의 근거 #13·#15("한 번도 실행되지 않았다")는 엄밀히는 **"오케스트레이션 경로로는 한 번도 실행되지 않았다"** 로 읽어야 한다. 결론(지표가 안 채워져 있다)은 파일 실측으로 독립 확인되므로(#32: 33건이 `missing-metrics`) 계획의 조치는 그대로 유효하다.

🆕 **함께 남기는 관찰**: `metric_refresh.parse_dt()` 는 마이크로초와 타임존이 같이 있는 값(`2026-08-26T12:56:09.799854+09:00`)에서 `strptime` 절단 경로에 먼저 걸려 **타임존을 조용히 버리고 naive 로 읽는다**(검수 실측). KST 로컬 환경에서는 결과가 같아 증상이 없다. T6-0 은 이 경로를 고치지 않으므로 형식 통일은 절반만 된 상태로 남는다. 이 계획에서는 손대지 않는다.

### 그 외

- 앞으로 한 플랫폼에만 올린 날은 짝 없이 한 줄만 뜬다. 정상 동작이며 V3 로 확인한다.
- 같은 날 같은 플랫폼에 2건 이상 올린 사례는 아직 없다. V5 가 그 경우의 결정적 순서를 보장하지만 실데이터 검증은 못 한다.
