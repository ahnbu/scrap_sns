### 1.2 왜 쓰레드 수집이 먼저인가

이전 판은 쓰레드 수집과 교차 연결을 한 덩어리로 묶고 "검증하려면 둘 다 필요하다"고 적었다. **그 논거는 틀렸다.** 교차 연결을 검증하려면 쓰레드 데이터가 필요한 것이지, 두 작업을 같이 해야 하는 것이 아니다.

쓰레드 수집만으로 완결된 가치가 있다 — 뷰어에서 내 쓰레드 글과 성과를 볼 수 있게 된다. 교차 연결은 그다음에 붙여도 재작업이 없다(6절 #7).

### 1.3 이 접근의 트레이드오프

**얻는 것**: 내 쓰레드 글 32건이 노출수와 함께 뷰어에 들어온다. 링크드인 내 글과 같은 화면에서 성과를 본다.

**잃는 것**: scrap_sns에 없던 의존이 하나 생긴다 — 쓰레드 수집은 중간에 별도 프로세스(MCP 서버)를 띄운다. 다만 그 부분이 `sns_insight_update` 안에 갇혀 있어 scrap_sns 코드에는 번지지 않는다(3.2).

## 2. 문제

### P1 — 내 쓰레드 글이 통합본에 아예 없다

통합본 2,523건 중 쓰레드는 1,273건이지만 **전부 남의 글(저장글)**이다. `is_own_post: true`는 링크드인 36건뿐(#19 대조군). 내 쓰레드 성과를 보려면 별도 레포를 따로 열어야 하고, 그 데이터도 2026-07-25가 마지막이다.

### P2 — 본문이 500자에서 잘린다 (가장 큰 문제)

쓰레드 본문 최대가 499자다(#8). 그냥 수집하면 **32건 중 21건(66%)의 본문이 중간에 끊긴 채 저장된다**(#11). 누락 6,905자(#13).

실제 사례 — 2026-08-25 글은 이렇게 끝난다.

```
… 반응이 가장 좋았던 '100p 실습 가이드북' PDF 나눠드립니다.
아래 댓글 확인해주세요 👇
```

이어지는 내용은 **자기 답글**에 있는데 `get_my_threads`가 답글을 주지 않는다(#10). 뷰어에서 읽으면 여기서 끝나고, 검색도 뒷부분이 안 걸린다.

### P3 — 리포스트가 섞여 온다

남의 글을 공유한 리포스트 2건이 함께 온다(#3). 본문이 비어 있고 내 글이 아니다. 그대로 두면 하루 2건이 되는 날이 생겨 2단계 짝짓기까지 오염된다 — 실제로 2026-02-13이 그 경우였다.

### P4 — 시각이 UTC라 그대로 저장하면 하루가 어긋난다

쓰레드는 UTC를 반환하고(#6) 이 레포는 전 플랫폼이 **한국시간 naive 문자열**로 저장한다(`utils/common.py:109`의 `datetime.fromtimestamp()`가 시간대 인자 없이 머신 로컬을 쓴다). 변환하지 않으면 날짜 정렬·필터·검색이 전부 9시간 어긋난다.

### P5 — `BL-0826-01`의 착수 조건이 근거와 연결되지 않는다

`BACKLOG.md`의 원문은 이렇다.

> 실패 모드가 LinkedIn과 다르다 — LinkedIn은 `storage_state` 만료… Threads는 `THREADS_ACCESS_TOKEN` 만료… 두 실패 모드를 한 웨이브에 섞으면 원인 분리가 어렵다. **착수 조건: LinkedIn 경로가 최소 2회 업데이트에서 노출수 정상 반영을 보인 뒤.**

앞의 진단과 뒤의 조건이 이어지지 않는다. 원인 분리가 문제라면 해법은 **실패 신호에 플랫폼을 표시하는 것**이고, 링크드인을 두 번 성공시키는 것과는 무관하다. 게다가 그 표시는 이미 되어 있다 — `utils/auth_status.py:20`의 `emit_auth_required()`가 `{"platform": "linkedin", "scope": "my_posts"}`를 찍는다(`my_posts_scrap.py:126`).

조건 자체에도 허점이 있다. "2회 **정상**"은 성공 2회를 요구할 뿐 만료 상황을 겪게 하지 않는다. 다음 업데이트가 무사히 지나가면 아무것도 검증되지 않는다.

## 3. 해결

### 3.1 범위

**한다**

- 내 쓰레드 글 수집 진입점 + 어댑터 (링크드인 선례와 같은 구조)
- 리포스트 제외
- 자기 답글을 본문에 이어붙이기 (`is_merged_thread` 표시)
- UTC → KST 변환
- 노출수(`views`)를 `view_count`에 매핑
- 통합본 병합, CLI·API·뷰어 노출
- `BL-0826-01` 착수 조건 정정

**하지 않는다**

- 교차 연결(`cross_post_id`) — **2단계.** 10절
- 남의 댓글 수집 — 요구 없음
- `sns_insight_update` 레포 수정 — 호출만 한다

### 3.2 수집 경로 — 링크드인 선례를 그대로 따른다

`my_posts_scrap.py`는 직접 수집하지 않는다. `sns_insight_update`의 수집기를 호출해 산출물만 받아 형식을 맞춘다. 쓰레드도 같다.

```
my_threads_scrap.py  →  sns_insight_update.collectors.threads
                            └ threads_mcp_runner  → MCP 서버 프로세스 (subprocess)
```

MCP 서버는 `threads_mcp_runner`가 자기 안에서 띄운다(`subprocess.Popen`). scrap_sns는 파이썬 함수 하나를 부를 뿐이라 MCP 의존이 scrap_sns 코드에 번지지 않는다.

설정과 토큰은 `~/.claude/settings.json`의 `mcpServers.threads`에서 읽는다(#1). scrap_sns가 새로 관리할 자격증명이 없다.

### 3.3 자기 답글 합치기 (P2 해소)

**이 레포에 이미 있는 개념이다.** 쓰레드 저장글 1,273건 중 1,187건이 이미 연쇄글을 이어붙여 저장돼 있고(#17), 표준 스키마에 `is_merged_thread` 칸이 있다. 새 필드를 만들지 않는다.

#### 판별 규칙

글마다 `get_thread_replies`를 한 번 호출하고, 아래 두 조건을 **모두** 만족하는 답글만 시간순으로 본문에 이어붙인다.

| 조건 | 근거 |
|---|---|
| 작성자가 내 계정(`byungwook.an`) | 남의 댓글 70개가 여기서 전부 빠진다(#15) |
| 원글 이후 **30분 이내** | #14 |

이어붙인 글은 `is_merged_thread: true`로 표시한다.

#### 왜 30분인가

실측 자기 답글 23개의 분포다(#14).

```
본문 이어쓰기 22개 : 0분 ~ 11.6분
대화형 답글    1개 : 551.7분 (9시간)

30분 선 기준 —  아래 여유 18.4분,  위 여유 521.7분
```

#### 기각한 두 가지 판별법

**`replied_to` 필드로 구분** — 실패. `fields`로 요청하면 값이 오지만 본문 이어쓰기·남의 댓글·9시간 뒤 대화형 답글이 **전부 원글을 가리킨다**(#16). 쓰레드는 답글을 계층으로 쌓지 않고 원글 밑에 평평하게 붙인다.

**"남이 댓글 달기 전에 올린 것"으로 구분** — 실측에서 23개 중 21개만 맞았다. 2026-05-15 글에서 남이 7분 만에 댓글을 달았고, 그 뒤 올린 내 본문 보충("참고로 이건 Claude Max + ChatGPT Pro를 같이 쓰는…")이 잘려나갔다. 30분 규칙은 이것을 정확히 포함한다.

#### 남는 약점과 보완

**대화형 답글 표본이 1건뿐이다.** 30분이 그 1건과 521분 떨어져 있어 여유는 크지만, 하나를 보고 정한 선인 것은 사실이다.

보완: **이어붙일 때마다 로그를 남긴다.** 날짜·붙인 개수·글자수·본문 앞 40자를 찍는다. 엉뚱한 것이 붙으면 수집 로그만 훑어도 눈에 띈다. 반례가 나오면 그때 기준을 조정한다.

### 3.4 리포스트 제외 (P3 해소)

`media_type == "REPOST_FACADE"`인 항목을 수집 대상에서 뺀다(#3). 판별 필드가 명확해 조건 한 줄이다. 제외 건수를 로그에 남긴다.

### 3.5 시간대 변환 (P4 해소)

어댑터가 UTC를 KST naive 문자열로 바꿔 `created_at`에 넣고, `date`도 KST 기준으로 채운다. 저장 시점에 끝낸다 — 하류(정렬·필터·검색·2단계 짝짓기)가 시간대를 몰라도 되게 한다.

검증값: 알려진 글 `2026-02-15T15:00:18+0000` → `2026-02-16 00:00:18`.

### 3.6 배치 — consumer 웨이브

`total_scrap.py`의 consumer 웨이브에 등록한다. `MyPosts`(링크드인) 옆이다.

producer가 아닌 이유는 링크드인과 다르다. 링크드인은 같은 계정 로그인 세션 중복을 피하려는 것이었고, 쓰레드는 API 토큰이라 그 제약이 없다. **그럼에도 consumer에 두는 이유**는 실패 격리다 — 저장글 수집(producer)이 내 글 수집 실패로 멈추면 안 된다.

## 4. 선행 조건 — `BL-0826-01`의 "2회" 조건을 정정한다

**결론: 이 조건은 폐기하고, 대신 실효성 있는 조건으로 바꾼다.**

P5에서 보인 대로 조건과 그 근거가 연결되지 않는다. 원래 걱정(두 플랫폼 실패 원인 구분)은 다른 방법으로 이미 해결돼 있다.

#### 바꾸는 내용

| 항목 | 기존 | 변경 |
|---|---|---|
| 착수 조건 | LinkedIn 내 글 수집이 2회 정상 | **폐기** |
| 대신 요구하는 것 | — | 쓰레드 수집기도 인증 실패 시 **`exit_auth_required("threads", reason="login_required")`를 반드시 호출한다** (T1 필수 요건, V7로 검증) |

새 요구가 원래 걱정을 직접 해소한다. 두 수집기가 각각 자기 플랫폼 이름을 찍으므로, 한 웨이브에서 둘 다 실패해도 로그만 보면 어느 쪽이 원인인지 바로 갈린다.

이 정정은 **사용자 결정으로 확정됐다**(2026-08-27 세션 `c31b5cef`). 계획 게이트 2라운드 리뷰어는 기존 조건 유지를 요구했으나, 조건의 근거가 실제 코드와 맞지 않는다는 사실을 확인한 뒤 사용자가 정정을 지시했다.

## 8. 미확정 · 확인 범위

- **자기 답글 30분 기준의 표본이 얇다.** 대화형 답글 실측이 1건(551.7분)뿐이다. 여유는 521분으로 크지만 반례가 나올 수 있다. 3.3의 로그로 보완하고, 반례가 나오면 기준을 조정한다.

- **X(Twitter)에도 같은 원고를 올리는지 확인하지 않았다.** 이번 범위 밖이다.

| # | 항목 | 실제 |
|---|---|---|
| 1 | **T7(갱신 정책 등록) 미수행** | 불필요해서 하지 않았다. `linkedin_own` 정책이 필요한 이유는 `linkedin_metric_single.py` 가 "어떤 내 글을 갱신할지" 고르기 때문이다. Threads 는 수집기 하나가 매 실행마다 전수(32건)를 가져오므로 대상 선정 단계가 없고, `metric_refresh` 를 참조하는 코드 경로도 없다. 등록하면 죽은 설정이 된다 |
| 2 | `code` 를 shortcode 로 매핑 | 계획에 없던 구현 세부. Graph API 는 숫자 id 를 주는데 `utils/post_meta.py:62` 가 `code` 로 원문 URL 을 조립하므로 그대로 쓰면 열리지 않는 URL 이 만들어진다. permalink 에서 shortcode 를 뽑아 저장글과 같은 체계(`DUn02Eukm2o` 형태)로 맞췄다 |
| 3 | 기존 e2e 단언 2건 수정 | T8 을 "확인만"으로 잡았으나 실제로는 수정이 필요했다. (a) `test_my_filter_combines_with_platform_chip` 이 "Threads + MY = 0건"을 단언하고 있었다 — 이번 변경으로 전제가 바뀌었다. (b) `test_my_filter_shows_only_own_posts` 가 카드 개수 감소로 판정했는데, 내 글이 36→68건이 되며 마소너리 지연 로딩 상한(60장)에 걸려 켜기 전후가 같아졌다. 상단 건수 라벨로 판정하도록 바꿨다 |
| 4 | 리포스트 필터가 실제로는 발동하지 않음 | 상류 `collect_threads_posts()` 가 노출수 없는 레코드를 이미 버려서 리포스트 2건이 도달 전에 빠진다. 필터는 안전망으로 남겼고 단위 테스트로 검증한다 |

### 11.4 남은 리스크

- **30분 기준의 표본이 얇다**(대화형 답글 1건). 이번 실행에서는 정확히 동작했으나 반례가 나올 수 있다. 이어붙인 내용은 수집 로그에 날짜·개수·글자수·앞 40자로 남는다.
