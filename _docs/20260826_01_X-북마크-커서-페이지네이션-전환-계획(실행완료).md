## 2. 문제

### 2.1 문제 재정의

`BL-0824-08`의 제목 "북마크 수집이 첫 페이지 20건에서 멈춤"은 증상의 오독이다. 정확한 문제는:

> **X 게시물 95건 중 74건이 지표를 채우지 못한 채 방치돼 있다. API는 그 74건의 지표를 정상적으로 내려주고 있는데, 수집기가 그 응답을 받기 직전에 스스로 종료한다.**

지표 보유 20건이 정확히 첫 페이지 20건과 일치하는 것이 그 증거다.

### 2.2 근본 원인 — 코드 결함 2개

**결함 A. 존재하지 않는 메서드 호출** — [twitter_scrap.py:362](twitter_scrap.py:362)

```python
response = page.wait_for_response(...)   # 동기 API에 없는 메서드
except Exception:
    page.wait_for_timeout(5000)          # 매 실행 여기로 떨어짐
```

Playwright 동기 API(설치본 1.58.0)의 `Page`에는 `wait_for_response`가 없다(`expect_response`가 정식). 따라서 이 호출은 **매 실행 예외를 던지고**, 북마크 응답 대기가 "눈 감고 5초"로 대체돼 왔다. 같은 결함이 [scripts/auth_runtime/verify_x_auth.py:108](scripts/auth_runtime/verify_x_auth.py:108)에도 있다 — 인증 판정이 5초 안에 우연히 도착한 것만 보고 내려진다.

**결함 B. 조기 종료 임계값** — [twitter_scrap.py:449](twitter_scrap.py:449)

```python
if consecutive_no_new >= 5:
    break
```

재수집 시 첫 페이지 20건은 전부 기존 데이터라 신규가 0이다. 리다이렉트된 History 화면에서 다음 `Bookmarks` 호출은 스크롤 5회차 부근에야 발생한다(실측). **2페이지가 도착하기 직전에 루프가 닫힌다.** 백로그의 "18~19초 조기 종료" 관측과 정확히 일치한다.

### 2.3 리다이렉트의 실제 지위

리다이렉트는 원인이 아니라 **증폭 요인**이다. 스크롤 대상이 북마크 목록이 아니게 되면서 다음 장 요청이 느리고 불규칙해졌고, 그 위에 결함 B의 짧은 임계값이 겹쳐 정지가 확정됐다. 리다이렉트 자체를 되돌릴 방법은 없고, **되돌릴 필요도 없다** — API는 정상 동작하기 때문이다.

## 3. 해결

### 3.1 방향 결정

| 안 | 내용 | 판정 | 근거 |
|---|---|---|---|
| ① | 북마크 목록 컨테이너를 특정해 그 안에서 스크롤 | **기각** | 이번 사고의 원인이 화면 구조 변경인데 해법이 또 화면 구조에 의존한다. `data-testid`는 X가 자주 바꾼다 |
| ② | **Bookmarks GraphQL을 커서로 직접 페이지네이션** | **채택** | 실측으로 전량 수집·정상 종료 확인. 화면 구조와 무관. 파서 무변경 |
| ③ | 스크롤 임계값만 5→20으로 상향 | 기각 | 증상은 가려지나 대기 시간이 3초×20으로 늘고, 다음 레이아웃 변경 때 같은 자리에 선다 |
| ④ | 미해결 유지 | 기각 | 74건 지표가 API로 즉시 확보 가능한데 방치할 이유가 없다 |

②의 방식은 새 인증을 뚫는 것이 아니다. **페이지가 이미 보낸 요청 하나를 잡아 `variables.cursor`만 갈아끼워 재발행**하며, 쿠키는 브라우저 컨텍스트가 그대로 싣는다. 필요한 헤더는 캡처된 요청에서 나오는 6종(`authorization`, `x-csrf-token`, `content-type`, `x-twitter-active-user`, `x-twitter-auth-type`, `x-twitter-client-language`)뿐이다.

### 3.2 실행 단계

**S1. 결함 A 수정 (선행)**

`wait_for_response` → `expect_response` 로 교체. 대상 2곳: `twitter_scrap.py:362`, `scripts/auth_runtime/verify_x_auth.py:108`. 단독으로도 값어치가 있는 수정이며, S2의 첫 응답 캡처가 이 위에서 동작한다.

**단순 이름 치환으로는 고쳐지지 않는다.** `expect_response`는 컨텍스트매니저이므로 응답을 유발하는 동작을 **감싸야** 한다. 현재 두 파일 모두 `page.goto()`가 이미 끝난 뒤 별도 함수에서 대기하는 구조라([twitter_scrap.py:373](twitter_scrap.py:373), [verify_x_auth.py:106](scripts/auth_runtime/verify_x_auth.py:106)), 이름만 바꾸면 응답이 이미 도착한 뒤 리스닝을 시작해 동일하게 5초 blind wait로 떨어진다. 아래 형태로 `goto` 호출 자체를 감싸도록 재구조화한다.

```python
with page.expect_response(lambda r: "Bookmarks?variables=" in r.url, timeout=10000) as info:
    page.goto("https://x.com/i/bookmarks", wait_until="domcontentloaded")
response = info.value
```

**S2. 커서 페이지네이션 도입**

`main()`의 스크롤 루프를 대체한다. 구현 요건:

1. 첫 `Bookmarks` **요청**을 리스너로 캡처(URL·헤더 보관)
2. 첫 **응답**에서 Bottom 커서 추출
3. `page.evaluate`의 `fetch`로 커서만 바꿔 재발행, 응답을 기존 `handle_response`/`extract_from_json`에 그대로 투입
4. 호출 간 1.5초 지연

**종료 가드 4종** (하나라도 걸리면 중단):

| 가드 | 조건 | 실측 근거 |
|---|---|---|
| 커서 소멸 | Bottom 커서 없음 | — |
| 커서 반복 | 직전과 동일한 커서 | **실제 종료가 이 가드로 발생** |
| 빈 응답 | `entries` 0건 | 마지막 장에서 동반 발생 |
| 페이지 상한 | 120회(=2,400건) | 무한 루프 최종 방어 |

**중단·재개 가드**: 매 응답의 `x-rate-limit-remaining`을 읽어 20 미만이면 진행분을 보존하고 중단. HTTP 200이 아니면 즉시 중단. 실측상 전량 수집에 6회를 쓰므로 500 예산 대비 여유는 충분하지만, 계기판을 보고 달리는 편이 안전하다.

**DOM 경로(`extract_from_html`)**: API가 전량을 주므로 보조로 격하한다. 제거는 이번 범위에 넣지 않는다 — API 경로가 한 사이클 안정적으로 도는 것을 본 뒤 별도로 판단한다.

**S3. 안전 반영 순서**

되돌릴 수 없는 상태를 만들기 전에 검증이 끝나도록 순서를 고정한다.

1. 수집 결과를 **임시 경로**에 먼저 기록
2. 아래 검증 통과 여부 판정
3. 통과 시에만 `twitter_py_simple_*.json`과 `twitter_py_full_*.json`을 **둘 다 백업**한 뒤 simple 갱신
   - 백업 규칙은 기존 패턴을 따른다: 같은 디렉터리에 `<파일명>.<YYYYMMDD_HHMMSS>.bak` ([migrate_threads_domain.py:156](migrate_threads_domain.py:156) `create_backup()`)
4. **`python twitter_scrap_single.py` 실행** — simple 의 지표를 full 로 전파
5. `merge_results()` → `download_images()` → `validate_local_image_links()`
6. 뷰어 확인

실패하면 임시 파일만 버리거나 백업본을 되돌린다. 기존 95건은 어느 단계에서 실패하든 그대로 남는다.

> **4단계가 필수인 이유**: `merge_results()`는 simple 이 아니라 **full 파일**을 읽는다([total_scrap.py:499](total_scrap.py:499)). 이 단계를 빠뜨리면 새로 확보한 74건 지표가 simple 에만 남아 통합본에 반영되지 않고, V1·V5를 통과할 수 없다. AGENTS.md의 "upstream full 파일을 함께 맞춘 뒤 통합본을 재생성한다"는 규칙이 X에도 그대로 적용된다.
>
> 현재 `twitter_py_full_20260826.json`은 95건 전부 `is_detail_collected=True`이므로 신규 상세 수집 대상은 0건이고, consumer 는 "메타데이터 동기화만 진행" 경로로 진입해([twitter_scrap_single.py:85](twitter_scrap_single.py:85)) `full_map[pid].update(post)`로 지표만 전파한다([twitter_scrap_single.py:163](twitter_scrap_single.py:163)). 즉 추가 네트워크 수집 없이 파일 동기화만 일어난다.

### 3.4 롤백

`twitter_py_simple_*.json`과 `twitter_py_full_*.json` **백업본을 함께 복원** → `merge_results()` 재실행. 두 파일은 S3-3에서 같은 시점에 백업하므로 짝이 맞는다.

S3의 순서를 지키면 3단계 이전에 실패한 경우 롤백할 대상 자체가 생기지 않는다. 4단계(consumer)에서 실패하면 full 백업본만 되돌리면 되고, 5단계(병합)에서 실패하면 두 백업본을 되돌린 뒤 재병합한다.

## 4. 리스크와 이미 확인된 것

| 리스크 | 상태 | 대응 |
|---|---|---|
| Rate limit 도달 | **낮음** — 15분당 500회 중 6회 사용 | 잔여 횟수 감시 가드 |
| 본문 오염 재발(`BL-0412-05`) | **징후 없음** — 94건 본문 변경 0건 | V3·V4로 반영 전 차단 |
| 무한 루프 | 종료 가드 4종 | 실측상 커서 반복으로 정상 종료 |
| **작성자 핸들 변경 4건** | 실제 계정 개명 (예: `NotebookLM` → `Gemini_Notebook`) | 아래 참조 |
| `view_count` 타입 불일치 | 기존부터 문자열(다른 지표는 정수) | 이번 범위 밖. 뷰어는 `Number()`로 처리해 동작에 지장 없음 |
| 저장분 1건이 목록에 없음 | 북마크 해제/원글 삭제 추정 | 삭제하지 않고 보존 |

**핸들 변경 4건에 대하여**: 사용자 상태(별표·숨김·메모)의 키는 `{platform}:{platform_id}`이고 사용자명을 쓰지 않는다([utils/post_meta.py:71](utils/post_meta.py:71)에서 확인). 따라서 **상태 유실은 발생하지 않는다.** 뷰어의 작성자 필터 표시명과 원문 URL이 새 핸들로 바뀌며, X는 옛 핸들 URL도 리다이렉트하므로 원문 열기에도 지장이 없다. 오래된 핸들이 최신값으로 정정되는 것이므로 데이터 품질상 개선이다.
