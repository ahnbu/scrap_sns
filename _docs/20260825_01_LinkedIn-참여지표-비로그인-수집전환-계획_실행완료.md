## 1. 상황 (Situation)

### 1.1 지금까지의 경위

2026-08-24 세션에서 참여지표(좋아요·댓글 수) 커버리지를 5.2% → 67.3%로 끌어올렸다. 그러나 플랫폼별 편차가 크다.

| 플랫폼 | 지표 보유 | 비율 |
|---|---|---|
| threads | 1,189 / 1,240 | 95.9% |
| **linkedin** | **134 / 660** | **20.3%** |
| x | 20 / 95 | 21.1% |
| 전체 | 1,343 / 1,995 | 67.3% |

LinkedIn은 작성자 프로필을 순회하며 게시물을 만나면 지표를 채우는 방식이었다. 125명을 처리해 26 → 134건을 얻었고(작성자당 약 0.86건), 잔여 56명은 인증 만료로 중단된 상태로 `BL-0824-09`에 남아 있다.

### 1.2 오늘 발생한 사건

`BL-0824-09` 해소를 위해 LinkedIn 재로그인을 진행했다. 로그인 자체는 성공했으나(`storage_state.json` 갱신, `li_at` 만료 2027-08-25), 그 과정에서 LinkedIn이 다음 경고를 띄웠다.

> "회원님의 계정에서 **과도한 LinkedIn 프로필 데이터 접근이 감지**되었습니다"

이는 일반적인 재로그인 확인 절차가 아니라 스크래핑 탐지 경고다. 시점과 증상으로 볼 때 어제의 프로필 125명 연속 순회가 원인일 가능성이 높고, 어제 기록된 "인증 만료로 중단"도 실제로는 만료가 아니라 이 차단이었을 개연성이 크다.

### 1.3 수집 아키텍처 — 2-wave 구조 (개정 1판 추가)

`total_scrap.py`의 `run()`은 다음 순서로 동작한다. 뷰어의 「업데이트」 버튼이 `POST /api/run-scrap` → `subprocess: total_scrap.py --mode update`로 이어지는 유일한 실행 경로다.

```
① collect_existing_post_state()      기존 상태 보존용 스냅샷
② run_scrapers_in_parallel()
     WAVE 1 · producer   Threads / X / LinkedIn / YouTube      (목록 수집)
     WAVE 2 · consumer   thread_scrap_single / twitter_scrap_single  (상세 수집)
③ merge_results()                    플랫폼별 full 파일 통합
④ download_images()
⑤ save_total() + validate_local_image_links()
⑥ cleanup_old_output_json_after_success()
→ SNS_SCRAP_SUMMARY (auth_required 포함) → 서버가 증감 계산 → 뷰어 모달
```

**핵심: WAVE 2에 LinkedIn 항목이 없다.** Threads와 X는 목록을 받은 뒤 상세 수집 단계를 한 번 더 거치며 그 단계에서 지표를 얻는다. LinkedIn만 이 단계가 존재하지 않는다.

| 플랫폼 | producer | consumer | 지표 보유 |
|---|---|---|---|
| Threads | `thread_scrap.py` | `thread_scrap_single.py` | 95.9% |
| X | `twitter_scrap.py` | `twitter_scrap_single.py` | 21.1% |
| **LinkedIn** | `linkedin_scrap.py` | **없음** | **20.3%** |
| YouTube | `youtube_scrap.py` | 없음 | 해당 없음 |

이 사실이 본 계획의 설계 위치를 결정한다(3.3절).

### 1.4 로그인이 필요한 정보와 아닌 정보

LinkedIn 수집 데이터를 출처 기준으로 나누면 다음과 같다. 분류 기준은 "그 정보가 내 계정에만 존재하는가"이다.

| 구분 | 정보 | 근거 |
|---|---|---|
| **로그인 필수** | 저장글 목록 자체 (`/my-items/saved-posts`) | 내 계정에만 있는 개인 데이터. 대체 경로 없음 |
| 로그인 경로로 취득 | `full_text`, `username`, `display_name`, `user_link`, `profile_slogan`, `url`, `media`, `created_at`, `time_text` | 원리상 공개 정보지만 위 목록 API 응답에 함께 실려 온다. 추가 로그인 비용 없음 |
| **비로그인만 가능** | `like_count`, `comment_count` | 로그인 경로로는 얻을 수 없다(2.2절). 비로그인 공개 페이지 DOM 속성에 정확한 값 노출 |
| 취득 불가 | `view_count` | 게시글 작성자 본인만 조회 가능 |
| 취득 불가 | `share_count` | **2026-08-25 실측 확정** — 비로그인 공개 페이지의 `data-num-*` 속성은 `reactions`·`comments` 2개뿐이고 퍼감 수 텍스트도 없다 |

**요약하면, 로그인은 「어떤 글을 저장했는지」를 알기 위한 것이지 「그 글이 몇 개의 반응을 받았는지」를 알기 위한 것이 아니다.** 두 목적이 한 세션에 섞여 있었던 것이 1.2절 사건의 근원이다.

## 2. 문제 (Complication)

### 2.1 기존 경로를 그대로 재개하면 안 되는 이유

잔여 56명을 같은 방식으로 돌리면 얻는 것은 약 48건(전체 커버리지 67.3% → 69.7%, **+2.4%p**)이다. 반면 경고 직후 동일 패턴을 반복하는 것은 탐지 시스템 입장에서 가장 뚜렷한 신호이며, 다음 단계는 계정 임시 제한 또는 정지다. 해당 계정은 사용자의 업무 자산이고 제한은 되돌리기 어렵다.

**+2.4%p를 위해 업무용 계정을 거는 교환**이므로 성립하지 않는다.

### 2.2 정규 수집 경로는 지표를 가져올 수 없다

`linkedin_scrap.py`는 DOM을 긁는 방식이 아니라 LinkedIn 내부 API(Voyager GraphQL) 응답을 가로채 파싱하는 구조다(`handle_response` → `process_network_data` → `extract_post_from_view_model` → `utils/linkedin_parser.py:parse_linkedin_post`).

저장된 디버그 스냅샷 11건을 전수 스캔한 결과:

| 확인 항목 | 결과 |
|---|---|
| `socialActivityCounts` 등 지표 필드 **스키마 선언** | 존재 |
| 실제 **값이 채워진** 인스턴스 (`numLikes`, `numComments` 등) | **0건** |

즉 저장된 게시물 목록 API는 본문·저자·URL은 주지만 **지표 값은 응답에 담아주지 않는다.** 어제 세션이 프로필 순회라는 우회로를 택한 이유가 이것으로 설명된다.

따라서 지표는 어떤 방식이든 **정규 수집과 분리된 추가 단계**로 얻어야 한다.

### 2.3 지표는 한 번 읽고 끝나지 않는다 (개정 1판 추가)

초판은 일회성 백필 526건만 다뤘다. 그러나 백필이 끝난 뒤에도 문제가 남는다.

- **신규 수집분만 읽으면** 기존 글의 지표가 수집 시점 값으로 영원히 굳는다. 게시 직후 수집한 글은 좋아요 3건으로 박제된다.
- **전량을 매번 읽으면** 660건 × 약 5초 ≈ **55분**이라 「업데이트」 한 번에 감당할 수 없다.

즉 **갱신 대상을 고르는 정책**이 필요하다. 초판에는 이 정책이 없었다.

### 2.4 갱신 시각을 기록할 자리가 없다 (개정 1판 추가)

2.3절의 정책을 구현하려면 "이 글의 지표를 마지막으로 읽은 때"를 알아야 한다. 그런데 `utils/post_schema.py`의 `STANDARD_FIELD_ORDER`에 해당 필드가 없다. `crawled_at`은 **본문** 수집 시각이라 대체할 수 없다 — 본문은 한 번 받으면 다시 안 받지만 지표는 반복해서 읽기 때문이다.

필드가 없으면 대상 선정 자체가 불가능하므로, 스키마 확장이 선행 조건이 된다.

### 2.5 병합이 지표를 덮어쓸 수 있다 (개정 1판 추가)

`linkedin_scrap.py:merge_linkedin_full_posts()`는 기존 레코드와 새 수집분을 다음과 같이 합친다.

```python
merged = {**existing, **post}   # 새 수집분이 기존값을 덮어쓴다
```

현재는 **우연히 안전하다.** `parse_linkedin_post()`가 반환하는 dict에 지표 키가 아예 없고(`reorder_post()`도 없는 필드를 추가하지 않는다), `linkedin_scrap.py`는 `normalize_post()`를 사용하지 않기 때문이다. 그래서 `post`에 지표 키가 없어 `existing`의 값이 살아남는다.

**문제는 이 안전이 설계가 아니라 우연이라는 점이다.** LinkedIn 경로에 `normalize_post()`를 적용하는 순간 — 스키마 정리, 다른 플랫폼과의 일관성 확보 등 지극히 자연스러운 작업 — 지표 필드가 `None`으로 채워지고, 그 `None`이 `{**existing, **post}`에서 기존값을 **전부 지운다.**

초판 4.1절의 보존 가드는 백필 러너에만 걸려 있어 이 경로를 막지 못한다. 지금 증상이 없기 때문에 오히려 발견이 늦어질 위험이 크다.

**발동 조건 (개정 2판 추가):** 이 병합 함수는 `CRAWL_MODE == "all"`일 때만 호출된다. `--mode update`는 신규 건만 덧붙이므로 기존 레코드를 건드리지 않는다. 따라서 함정은 **전체 재수집 시점에 터진다** — 그때 526건의 지표가 한 번에 사라진다. 자세한 내용은 3.6절.

### 2.6 실패 이력을 남길 곳이 없다 (개정 1판 추가)

Threads·X는 `scrap_failures_threads.json`, `scrap_failures_twitter.json`을 운영한다. LinkedIn 것은 존재하지 않는다. 초판 4.1절은 "실패 이력에 기록"이라고만 적었을 뿐 대상 파일을 정의하지 않았다. 이대로면 삭제·비공개 전환된 게시글을 매 실행마다 재시도하게 된다.

### 2.7 방치했을 때의 비용

지금 정규 경로를 손대지 않으면, 앞으로 수집되는 LinkedIn 게시물은 계속 지표 없이 쌓인다. 그러면 오늘과 같은 대규모 백필을 주기적으로 반복해야 한다.

## 3. 해결 (Resolution)

### 3.1 채택안 — 비로그인 URL 직행 수집

게시글 URL로 **로그인하지 않은 상태**에서 직접 접근해 DOM 속성에서 지표를 읽는다.

**실측 근거 (2026-08-25):**

| 검증 항목 | 대상 | 결과 |
|---|---|---|
| 비로그인 접근 | 게시글 permalink | HTTP **200**, 본문 전체 노출 |
| 반응(좋아요) 수 정확도 | 8건 (좋아요 3 / 5 / 41 / 77 / 168 / 383 / 2,408 / 3,828) | **8/8 정확히 일치** |
| 반응 + 댓글 동시 정확도 | 4건 (5·1 / 77·2 / 168·8 / 383·19) | **4/4 정확히 일치** |

- 추출 위치: `data-num-reactions`, `data-num-comments` 속성
- 대조 기준: 어제 로그인 방식으로 수집한 기존 134건의 값
- 부수 확인: 기존 134건도 12건 대조에서 전부 일치 → **재수집 불필요**

**기존 방식과의 비교:**

| 항목 | 기존 (로그인 + 프로필 순회) | 채택안 (비로그인 URL 직행) |
|---|---|---|
| 로그인 | 필요 | **불필요** |
| 계정 리스크 | 경고 실제 발생 | 로그인을 안 하므로 **무관** |
| 접근 대상 | 작성자 프로필 순회 | 이미 보유한 게시글 URL 직행 |
| 매칭 실패율 | 약 90% | **해당 없음** |
| 커버 가능 범위 | 잔여 56명 → 약 48건 | **지표 미보유 526건 전부** |
| 예상 LinkedIn 커버리지 | 20.3% → 약 27% | 20.3% → **90%대** |
| 예상 전체 커버리지 | 67.3% → 69.7% | 67.3% → **약 90%** |

### 3.2 기각한 옵션과 근거

| 옵션 | 기각 근거 |
|---|---|
| **A. 기존 프로필 순회 재개** | 얻는 것 +2.4%p 대비 계정 제한 리스크가 과도. 경고 직후 동일 패턴 반복은 최악의 타이밍 |
| **B. 쿨다운 후 저속 재개** | 리스크가 낮아질 뿐 사라지지 않는다. 채택안이 리스크를 0으로 만들면서 결과도 더 좋으므로 선택할 이유가 없다 |
| **C. JSON-LD `interactionStatistic` 파싱** | **부정확해서 기각.** 같은 페이지에서 좋아요 252인 글을 `LikeAction: 0`으로 반환했다. 댓글 수만 맞고 좋아요는 신뢰 불가. **이 함정은 반드시 문서에 남긴다** |
| **D. 정규 수집기 API 응답에서 지표 추출** | 2.2절 참조 — 응답에 값 자체가 없어 불가능 |
| **E. 백필만 하고 정규 경로는 손대지 않음** | 2.7절 참조 — 백필을 주기적으로 반복하게 된다 |
| **F. `linkedin_scrap.py` 내부에서 후처리 (초판 설계)** | **개정 1판에서 기각.** 1.3절의 2-wave 구조와 어긋난다. 한 프로세스에서 로그인 세션과 비로그인 세션을 섞게 되고, producer 실행 시간이 늘어 다른 플랫폼과의 병렬성이 깨지며, 지표 수집 실패가 본문 수집에까지 영향을 준다 |

### 3.3 설계 — consumer wave에 LinkedIn 추가 (개정 1판 변경)

2.2절 결론에 따라 지표는 본문 수집과 분리된 단계가 된다. 그런데 1.3절에서 확인했듯 **그 자리는 이미 존재한다** — WAVE 2 consumer다. 새 구조를 만드는 것이 아니라 비어 있던 칸을 채운다.

```
WAVE 1 · producer     linkedin_scrap.py          [로그인 세션]
                        ↓ 본문 · 저자 · URL · 이미지
                      갱신 대상 선정 (3.4절)
                        ↓
WAVE 2 · consumer     linkedin_metric_single.py  [로그인 없음]
                        ↓ like_count · comment_count · metrics_updated_at
                      보존 가드 (3.6절)
                        ↓
                      merge_linkedin_full_posts()
                        ↓
                      output_total/total_full_*.json → 뷰어
```

**공용 추출 모듈:** 실제 추출 로직은 `utils/linkedin_metrics.py`에 둔다. `linkedin_metric_single.py`(상시)와 `scripts/linkedin_metric_backfill.py`(일회성)가 **같은 함수를 호출한다.**

백필용으로 따로 짜고 나중에 정규 경로에 옮기면 추출 로직이 두 벌이 된다. LinkedIn이 마크업을 바꾸면 한쪽만 고치고 다른 쪽은 조용히 썩는다.

**실행 방식 — Playwright headless 고정 (개정 1판 추가):** 지표는 `data-num-reactions` / `data-num-comments` **DOM 속성**에서 읽으므로, 단순 HTTP 요청(`requests`)이 아니라 브라우저 렌더링이 필요하다. 따라서 Playwright를 쓰되 **`headless=True`로 고정한다.**

- 백필(`scripts/linkedin_metric_backfill.py`), 상시(`linkedin_metric_single.py`), 뷰어 검증 스크립트 **전부 headless**다.
- 이 계획에는 창을 띄워야 하는 예외가 **없다.** 로그인을 하지 않으므로 수동 로그인 같은 사유가 발생하지 않는다.
- 창이 뜨면 사용자 포커스를 뺏어 병행 작업이 끊기고, done-check가 사람 눈에 의존하게 된다.
- 컨텍스트는 `storage_state`를 **주입하지 않은** 새 컨텍스트로 연다. 로그인 세션이 섞이면 이 계획의 전제가 무너진다.

**consumer wave 방식의 부수 이득:** 기존 로그 파일 체계, 실패 격리, `SNS_SCRAP_SUMMARY` 시그널을 그대로 쓸 수 있다. 단, 이 consumer는 로그인하지 않으므로 `auth_required` 시그널을 낼 일이 없다 — 실패는 일반 실패(`returncode`)로만 보고한다.

### 3.4 상시 갱신 정책 (개정 1판 신설 · C2)

2.3절 문제에 대한 해답이다. 매 「업데이트」 실행에서 지표를 읽을 대상을 다음 우선순위로 고른다.

| 순위 | 대상 | 이유 |
|---|---|---|
| 1 | 지표가 없는 글 (`like_count is None`) | 커버리지를 먼저 채운다 |
| 2 | 이번 실행에서 새로 수집된 글 | 신규분은 항상 지표를 갖고 시작한다 |
| 3 | 작성 30일 이내이면서 마지막 지표 갱신이 7일을 넘은 글 | 반응이 아직 늘어나는 구간만 다시 읽는다 |

**작성 30일을 넘긴 글은 갱신하지 않는다.** LinkedIn 게시물의 반응은 대체로 1~2주 안에 수렴하므로, 오래된 글을 반복해 읽는 것은 시간만 쓰고 값은 거의 바뀌지 않는다.

**1회 상한:** 기본 **120건**(건당 약 5초 → 약 10분). 설정값으로 두어 조정 가능하게 한다. 상한에 걸려 처리하지 못한 대상은 다음 실행으로 넘긴다.

**상한을 두는 이유:** 상한이 없으면 첫 실행에서 660건을 시도해 55분간 「업데이트」가 끝나지 않는다. 또한 짧은 시간에 대량 요청이 몰려 2.x절의 IP 제한을 유발한다.

### 3.5 스키마 확장 (개정 1판 신설 · C3)

`utils/post_schema.py`의 `STANDARD_FIELD_ORDER`에 지표 갱신 시각 필드를 추가한다.

| 항목 | 내용 |
|---|---|
| 필드명 | `metrics_updated_at` |
| 위치 | `view_count` 다음, `source` 앞 |
| 기본값 | `None` (`normalize_post()`의 defaults에 등록) |
| 값 형식 | ISO 8601 문자열. `crawled_at`과 동일 형식 |
| 기록 주체 | 지표를 실제로 읽은 주체 — `linkedin_metric_single.py`, 백필 러너 |

**주의:** 이 필드는 전 플랫폼 공용 스키마에 들어간다. Threads·X 데이터에는 당분간 `None`으로 남는다. 그것으로 문제없다 — 두 플랫폼은 현재 갱신 정책 대상이 아니다. 다만 나중에 같은 정책을 확장할 때 그대로 쓸 수 있다.

**순서상 주의:** 스키마 확장은 백필보다 **앞서야 한다.** 백필이 526건에 `metrics_updated_at`을 채워야 3.4절 정책이 처음부터 정상 작동한다. 백필 후에 필드를 추가하면 526건 전부가 "갱신 시각 미상"이 되어 정책 판정이 불가능해진다.

### 3.6 병합 보존 가드 (개정 1판 신설 · C4)

2.5절 함정을 막는다. `merge_linkedin_full_posts()`의 병합 직후에 보존 로직을 넣는다.

```
merged = {**existing, **post}
→ 보존 대상 필드에 한해: merged 값이 None이면 existing 값을 이월
   단, existing 값이 None 또는 -1이면 이월하지 않는다
```

**보존 대상 필드 (개정 2판 확정 · 계획 게이트 B1):** 아래 7개다. 구현 시 이 목록을 상수로 명시하고, "지표 필드"라는 서술에 의존하지 않는다.

| 필드 | 비고 |
|---|---|
| `like_count`, `comment_count`, `share_count`, `quote_count`, `bookmark_count`, `view_count` | `thread_scrap_single.py:171`의 `METRIC_FIELDS`와 동일한 6개 |
| **`metrics_updated_at`** | **반드시 포함한다.** 아래 사유 참조 |

**`metrics_updated_at`을 보존 대상에 넣어야 하는 이유:** 이 필드는 지표가 아니라 메타데이터지만, **지표와 항상 같이 움직여야 한다.** 지표를 이월하면서 갱신 시각을 이월하지 않으면 "지표는 있는데 언제 읽었는지 모름" 상태가 되고, 3.4절의 상시 갱신 정책이 대상을 고를 수 없게 된다. Threads의 `METRIC_FIELDS`에는 이 필드가 없으므로(신설 필드이므로 당연히 없다) **그 목록을 그대로 복사하면 안 된다.**

**원칙은 Threads의 `thread_scrap_single.py:preserve_existing_metrics()`와 같다.** 특히 **`0`은 유효한 지표값이므로 truthy 검사로 구현하면 안 된다** — 좋아요 0건이 기존값으로 되살아난다. 반드시 `is None`으로 판정한다. 어제 세션에서 이미 검증된 규칙이다.

**함정의 발동 조건 (개정 2판 추가):** `merge_linkedin_full_posts()`는 [`linkedin_scrap.py:470`] 기준으로 **`CRAWL_MODE == "all"`일 때만 호출된다.** `--mode update`는 `new_items + old_posts`로 신규 건만 덧붙이므로 기존 레코드를 건드리지 않는다. 즉 2.5절 함정은 **전체 재수집(`--mode all`)에서 발동한다.**

그렇다고 우선순위가 낮아지지는 않는다 — 전체 재수집은 실제로 수행되는 작업이고, 그때 526건의 지표가 한 번에 사라진다. 또한 이 가드는 앞으로 consumer나 다른 로직이 이 병합 함수를 재사용할 때의 방어선이 된다.

**공용화 검토:** 같은 로직이 Threads와 LinkedIn 두 곳에 생기므로 `preserve_existing_metrics()`를 공용 모듈로 승격하는 것이 이상적이다. 다만 Threads 경로를 건드리면 검증 범위가 넓어지므로, 본 계획에서는 **LinkedIn에 동일 원칙을 구현하는 데까지만** 하고 공용화는 별도 항목으로 백로그에 남긴다.

### 3.7 백업과 롤백 (개정 1판 신설 · 계획 게이트 B2)

백필은 `output_linkedin/python/linkedin_py_full_*.json`을 **제자리에서(in-place) 갱신**한다. 526건을 건드리므로 실패·오염 시 복구 경로가 반드시 있어야 한다.

| 항목 | 내용 |
|---|---|
| 백업 시점 | **2회.** ① 파일럿(7단계) 시작 직전 ② 전량 배치(8단계) 시작 직전 |
| 2차 백업이 필요한 이유 | 파일럿도 실제 데이터를 갱신하므로, 8단계 시점의 원본은 1차 백업본과 다르다. 1차 백업본으로 롤백하면 파일럿 성과까지 함께 날아간다 |
| 백업 대상 | 최신 `output_linkedin/python/linkedin_py_full_*.json` 전체 파일 |
| 백업 경로 | `_backup_linkedin_metrics_YYYYMMDD_HHMMSS/` (레포 루트). `.gitignore:127`의 `_backup_*/` 규칙에 이미 걸리므로 커밋되지 않는다 |
| 무결성 확인 | 백업 직후 원본과 바이트 크기·게시글 수를 대조한다. 불일치면 백필을 시작하지 않는다 |
| 롤백 조건 | 파일럿·전량 게이트 미달, 기존 지표 소실 1건 이상, 본문·저자 변동 감지 |
| 롤백 방법 | 백업 파일을 원본 경로로 되돌린 뒤 `merge_results()` 재실행 → 통합본 재생성 |
| 부분 실패 정리 | 배치 중단 시 이미 갱신된 건은 유지한다. 지표 필드만 추가되었고 본문은 불변이므로 부분 적용 상태도 유효하다. 남은 대상은 3.4절 정책이 다음 실행에서 다시 집어낸다 |

**부분 실패를 롤백하지 않는 이유:** 이 작업은 지표 필드를 채우기만 하고 기존 데이터를 변형하지 않는다. 500건 중 300건까지 갱신된 상태는 그 자체로 정상이며, 되돌리면 오히려 성과를 버린다. 롤백은 **오염이 확인된 경우에만** 발동한다.

### 4.1 순서의 근거

### 4.3 남은 리스크 (해소되지 않음)

- **IP 단위 제한**은 로그인 여부와 무관하게 남는다. 계정 리스크와 달리 완전히 없앨 수 없고, 지연·배치·상한으로 낮출 뿐이다.
- **비공개 전환 게시글**은 구조적으로 수집 불가. 526건 전량이 아니라 공개분만 채워진다.
- **`share_count`·`view_count`는 취득 불가로 확정됐다**(1.4절). `share_count`는 파일럿 단계에서 실측했고(비로그인 페이지의 `data-num-*` 속성은 `reactions`·`comments` 2개뿐), `view_count`는 작성자 본인만 조회 가능하다. LinkedIn에서 얻을 수 있는 지표는 좋아요와 댓글 둘뿐이다.
- 백필 예상 소요 약 90분. 배치 단위로 끊어 진행 가능.

## 5. 완료 기준

`AGENTS.md`의 SNS 수집·병합 변경 완료 기준을 따른다.

**모든 기준은 종료코드와 로그로 판정한다.** 화면 검증도 headless Playwright가 DOM을 직접 조작·판독해 종료코드로 결과를 내며, 사람이 눈으로 보고 판단하는 항목은 없다. 캡처는 보조 증거이고 판정 근거가 아니다.

| # | 기준 | 판정 방법 (증거) |
|---|---|---|
| 1 | 단위·계약 테스트 통과 | `pytest tests/unit tests/contract` **종료코드 0** |
| 2 | upstream과 통합본의 지표 일치 | 두 JSON을 로드해 `platform_id` 기준 지표 대조하는 스크립트 **종료코드 0**. 불일치 건수를 로그에 출력 |
| 3 | 뷰어 총건수와 JSON 게시글 수 일치 | headless 스크립트가 `/api/latest-data` 응답 건수와 화면 상단 총건수 DOM 텍스트를 읽어 대조, **종료코드 0** |
| 4 | 뷰어에 LinkedIn 지표 배지 표시 | **headless Playwright**가 `http://localhost:5000/`에서 플랫폼 필터를 클릭해 LinkedIn만 남긴 뒤, 카드 중 지표 배지를 가진 개수를 세어 기대값과 대조, **종료코드 0**. 캡처는 스크래치패드에 부수 저장 |
| 5 | 백필 전후 데이터 불변 | 백업본과 갱신본을 대조하는 스크립트 — 건수·저자·본문 **차이 0건**, 기존 지표 소실 **0건**, **종료코드 0** |
| 6 | consumer 실제 동작 | 「업데이트」 1회 실행 후 `logs/`에서 LinkedIn consumer 단계 로그 존재 확인 + 갱신된 JSON에 `metrics_updated_at`이 채워진 건수 > 0, **종료코드 0** |
| 7 | 보존 가드 실증 | 「업데이트」 **연속 2회** 실행. 1회차 직후와 2회차 직후의 지표 보유 건수를 비교해 **감소 0건**, **종료코드 0** |

**4번의 headless 강제 이유:** 창이 뜨면 사용자 포커스를 빼앗고, 결과가 사람 눈에 의존해 done-check가 증거 기반으로 판정할 수 없게 된다. 어제 세션도 같은 방식(headless Playwright가 DOM을 클릭해 판독, 검증 6종 전부 종료코드 0)으로 이 규칙을 충족했다.

**7번이 필요한 이유:** 2.5절 함정은 1회 실행으로는 드러나지 않는다. 2회차에서 지표가 줄어드는지가 보존 가드의 유일한 실증이다.
