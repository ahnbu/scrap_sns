## 0. 한 줄 결론

**벤치마킹 계정 수집기 3개가 만들어져 있는데 어디서도 실행되지 않는다.** 「업데이트」 버튼은 저장글만 긁고, 벤치마킹 글은 2026-09-06에 손으로 한 번 돌려 만든 파일이 매번 다시 병합되고 있을 뿐이다. 화면에는 글이 보여서 멈춘 줄 모른다.

수정은 **3개를 이 순서로** 해야 한다. 순서를 바꾸면 9/6에 모은 글이 사라진다.

| 순서 | 작업 | 안 하면 |
|---|---|---|
| W1 | Threads·LinkedIn 벤치마킹 산출물을 **누적**하도록 수정 | W2를 켜는 순간 기존 벤치마킹 글이 통합본에서 사라진다 |
| W2 | `total_scrap.py`에 **벤치마킹 wave 추가** | 「업데이트」를 눌러도 벤치마킹 글은 영원히 9/6에 멈춘다 |
| W3 | 병합 후 **계정 카드 수치 자동 갱신** | 화면의 「저장 36건 · 최신 9/5」가 계속 거짓말을 한다 |

### 1.1 「업데이트」 버튼의 실제 경로

```
뷰어 버튼 → POST /api/run-scrap → python total_scrap.py --mode update
```

근거: [scrap_sns_server.py:1374](../scrap_sns_server.py#L1374)

`total_scrap.py`가 실행하는 명령 전체([total_scrap.py:382](../total_scrap.py#L382)):

### 1.2 만들어져 있지만 호출되지 않는 것

| 파일 | 무엇을 하나 | 호출처 |
|---|---|---|

## 2. 문제 (P)

### P1 — 「업데이트」가 벤치마킹을 수집하지 않는다 〔치명〕

`total_scrap.py`의 `phase_commands`에 벤치마킹 수집기가 없다. 사용자가 화면에서 계정을 켜고 「수집 가능」 배지를 확인해도, 그 계정의 글은 자동으로 들어오지 않는다.

**영향**: 계정을 켜는 행위가 아무 일도 하지 않는다. 벤치마킹 기능 전체가 사실상 죽어 있다.

### P2 — Threads·LinkedIn 벤치마킹은 누적되지 않는다 〔치명·잠재〕

| 수집기 | 기존 파일을 읽나 | 저장 방식 |
|---|---|---|
| `youtube_scrap.py --channel` | ✅ `load_existing_posts(channel_mode=True)` ([youtube_scrap.py:721](../youtube_scrap.py#L721)) | 기존 + 신규 병합 |
| `threads_scrap_benchmark.py` | ❌ | **이번 실행분(계정당 최대 5편)만** 새 파일로 저장 ([threads_scrap_benchmark.py:186](../threads_scrap_benchmark.py#L186)) |
| `linkedin_scrap_benchmark.py` | ❌ | **이번 실행분(계정당 최대 5편)만** 새 파일로 저장 ([linkedin_scrap_benchmark.py:158](../linkedin_scrap_benchmark.py#L158)) |

`merge_results()`는 각 폴더의 **최신 파일 하나**만 읽는다. 따라서 P1을 먼저 고치면, 다음 실행에서 9/6에 모은 Threads·LinkedIn 글이 통합본에서 빠진다(내 저장글에도 있는 글만 살아남는다).

**영향**: 벤치마킹이 「쌓이는 자료」가 아니라 「최근 5편 스냅샷」이 된다. 발행 시각 분석·성과 추이 같은 원래 목적이 성립하지 않는다.

### P3 — 계정 카드의 수치가 갱신되지 않는다 〔중〕

계정 카드에 뜨는 `saved_count`·`last_saved_at`은 `scripts/sync_benchmark_accounts.py`가 통합본을 훑어 채우는 값인데, 이 스크립트도 자동 호출처가 없다. 현재 화면은 9/5~9/6 시점 수치를 그대로 보여준다.

**영향**: 수집이 멈춰도 화면 수치가 그대로라 **사용자가 알아챌 방법이 없다.** P1이 오래 숨어 있던 직접 원인이다.

### P4 — 후보 계정 자동 발굴이 없다 〔참고, 이번 범위 밖〕

`sync_benchmark_accounts.py` 상단 주석은 "세 소스를 합쳐 코드가 채운다"라고 적혀 있으나, 실제 구현은 `benchmark_seed.json`의 26계정만 순회한다([sync_benchmark_accounts.py:437](../scripts/sync_benchmark_accounts.py#L437)). 수집 데이터·제작자 프로필은 **시드에 이미 있는 계정의 빈 칸을 메우는 데만** 쓰인다.

**영향**: 내가 글을 많이 저장한 사람이라도 시드 JSON을 손으로 고치기 전에는 후보에 뜨지 않는다. **주석과 구현이 어긋나 있다.** 이번 계획에서는 고치지 않고 §7에 남긴다.

## 3. 해결 (R)

### W1 — 벤치마킹 산출물 누적 보존 〔선행, 필수〕

**대상**: `threads_scrap_benchmark.py`, `linkedin_scrap_benchmark.py`

**변경**: 저장 직전에 자기 폴더(`output_threads_user/python/`, `output_linkedin_user/python/`)의 최신 `*_user_full_*.json`을 읽어 이번 수집분과 합친 뒤 저장한다. YouTube가 이미 쓰는 방식(`load_existing_posts`)과 같은 모양으로 맞춘다.

**병합 규칙**

| 항목 | 규칙 |
|---|---|
| 중복 키 | `code`(= `platform_id`). 같으면 **이번 수집분이 이긴다** — 좋아요·댓글 수가 최신이다 |
| 계정당 보관 상한 | **30편**. 초과분은 게시일 내림차순으로 잘라낸다 |
| 상한 초과로 잘라낼 때 | **잘라낸 계정 id와 건수를 로그로 출력한다.** 형식은 f-string으로 값을 채운다 — `print(f"   ✂️ {account_id} 보관 상한 {KEEP_LIMIT}편 초과 — {removed}편 제거")`. 문자 그대로의 `<id>`·`N`을 출력하지 않는다. 조용히 사라지면 §4 기준 2와 구분되지 않는다 |
| 켜져 있지 않은 계정의 과거분 | 보존한다. 계정을 껐다고 이미 모은 글을 지우지 않는다 |
| 같은 날 재실행 | 같은 날짜 파일을 읽어 합친 뒤 덮어쓴다(현재는 통째 교체라 유실) |
| 기존 파일이 없을 때 | 빈 목록에서 시작한다. 최초 수집·갓 클론한 환경에서 예외로 죽지 않는다 |
| **저장은 원자적으로** | 아래 별도 항목 참조 |

**원자적 쓰기 (필수)**

누적으로 바뀌면 한 파일에 계정당 최대 30편이 들어간다. 지금은 통째 교체라 쓰기가 깨져도 잃는 것이 이번 수집분뿐이지만, 누적 후에는 **그동안 쌓은 것 전부**다. 그런데 현재 쓰는 [utils/common.py:19](../utils/common.py#L19)의 `save_json()`은 `open(path,'w')` 직후 `json.dump` 라 임시 파일도 rename도 없다 — 직렬화 실패·디스크 부족이면 원본이 잘린 채 남는다.

- 두 수집기의 저장을 `save_json()` 대신 **임시 파일에 쓴 뒤 `os.replace()`** 하는 방식으로 바꾼다.
- 새로 만들지 않는다. 같은 레포에 구현이 셋 있다 — [scrap_sns_server.py:939](../scrap_sns_server.py#L939) `_atomic_write_json`, [scripts/sync_benchmark_accounts.py:101](../scripts/sync_benchmark_accounts.py#L101), [scripts/backfill_youtube_channel_id.py:83](../scripts/backfill_youtube_channel_id.py#L83). 그중 하나의 형태를 그대로 쓴다.
- `utils/common.py`의 `save_json()` 자체는 건드리지 않는다. 레포 전역이 쓰는 함수라 이번 범위를 넘고, 그 변경은 별도 항목이다(§7).
- YouTube 벤치마킹(`youtube_scrap.py`)도 같은 `save_json()`을 쓰지만 이번엔 손대지 않는다 — 누적 방식이 이미 있고 이번 변경 대상이 아니다. §7에 남긴다.

보관 상한 30편의 근거: `BACKLOG.md#BL-0906-01`이 계정당 상한을 「초기 30 제안」으로 적었다. 1회 수집량(`limit`, 기본 5편)과는 다른 값이다 — **`limit`은 한 번에 가져올 편수, 30은 쌓아둘 상한**이다.

**검증**: 새 unit test `tests/unit/test_benchmark_accumulate.py`
- 기존 5편 + 신규 5편(겹침 2) → 8편이 남고 겹친 2편은 신규 값을 쓴다
- 계정 하나가 35편이 되면 30편으로 잘리고, 잘린 것은 가장 오래된 5편이다
- 켜지지 않은 계정의 기존 글이 살아남는다
- 기존 파일이 없으면 빈 목록에서 시작해 신규분만 저장한다(예외로 죽지 않는다)
- 저장 중 예외가 나도 기존 파일이 잘리지 않는다(임시 파일에 쓰고 교체하므로, 실패 시 원본이 그대로 남는다)

### W2 — `total_scrap.py`에 벤치마킹 wave 추가

**대상**: `total_scrap.py`

**변경**: `phase_commands`에 세 번째 wave `benchmark`를 추가한다. producer·consumer가 모두 끝난 뒤 실행하고, 세 수집기를 병렬로 돌린다.

```
("benchmark", {
    "BenchThreads":  "python -u threads_scrap_benchmark.py",
    "BenchLinkedIn": "python -u linkedin_scrap_benchmark.py",
    "BenchYouTube":  "python -u youtube_scrap.py --mode update --channel",
})
```

`PLATFORM_KEYS`에 `BenchThreads → bench_threads` 식으로 매핑을 추가한다(로그 파일명·결과 키가 한글이 되지 않게).

**왜 별도 wave인가 — 검토한 세 안**

| 안 | 내용 | 판정 |
|---|---|---|
| A | producer/consumer의 기존 슬롯 뒤에 `&&`로 직렬 연결 | **기각.** `&&`는 앞이 실패하면 뒤가 안 돈다. LinkedIn 로그인이 만료되면 관계없는 Threads 벤치마킹(비로그인)까지 멈춘다. 벤치마킹 실패도 저장글 실패로 보고돼 원인을 오인한다 |
| B | consumer wave에 슬롯만 추가 | **기각.** `linkedin_scrap_by_user.py`가 로그인 세션(`auth/auth_linkedin.json`, storage_state)을 쓴다([linkedin_scrap_by_user.py:487](../linkedin_scrap_by_user.py#L487)). consumer에는 이미 `my_posts_scrap.py`가 같은 세션을 쓰고 있어, 동시에 붙으면 세션이 깨진다 — 기존 코드 주석이 경계하는 바로 그 상황이다 |
| C | **별도 benchmark wave** | **채택.** 이 wave 안에는 LinkedIn 로그인을 쓰는 프로세스가 하나뿐이라 충돌이 없다. 세 수집기가 서로 다른 자원(비로그인 HTTP / 로그인 세션 / YouTube API)을 써서 병렬이 안전하다. 실패해도 저장글 수집에 영향이 없다 |

**순서 제약**: 반드시 W1 완료 후에 적용한다. 순서를 뒤집으면 P2가 현실화된다.

### W3 — 병합 후 계정 카드 수치 자동 갱신

**대상**: `total_scrap.py`의 `run()`

**변경**: `save_total()` 성공 직후, `cleanup_old_output_json_after_success()` 옆에 `scripts/sync_benchmark_accounts.py`를 **`--verify` 없이** 한 번 호출한다. `--verify`는 외부 네트워크(YouTube API·페이지 열기)를 타므로 「업데이트」 버튼 경로에 넣지 않는다.

이 스크립트는 `status`·`limit`·`memo`·`purpose`를 보존하고 `excluded`를 되살리지 않으므로([sync_benchmark_accounts.py:372](../scripts/sync_benchmark_accounts.py#L372)) 내가 켠 설정은 그대로 남는다. 갱신되는 것은 `saved_count`·`last_saved_at`·`match_keys`뿐이다.

실패해도 수집 결과를 되돌리지 않는다(감싸서 경고만 출력).

**검증**: 실행 후 `web_viewer/benchmark_accounts.json`의 `last_saved_at`이 실제 최신 게시일과 일치하는지 대조.

**기준 4의 검증 스크립트** — 신규 `scripts/verify_benchmark_refresh_headless.mjs`

기존 `scripts/verify_benchmark_mainview.mjs`의 관례를 그대로 따른다 — `PASS/FAIL` 한 줄 출력([verify_benchmark_mainview.mjs:66](../scripts/verify_benchmark_mainview.mjs#L66))과 `process.exit(failed.length ? 1 : 0)`([:301](../scripts/verify_benchmark_mainview.mjs#L301)). 사람 눈이 아니라 종료코드가 판정한다.
