## 1. 상황 (Situation)

`git status`에 `web_viewer/sns_tags.json`이 계속 변경 파일로 잡힌다. 사용자가 "진짜 수정된 것이 맞는가, 시간 정보 같은 무의미한 변경이 찍히는 것 아닌가"를 제기했다.

### 1.1 실측 — 내용은 100% 동일

`git show HEAD:web_viewer/sns_tags.json`과 작업트리 파일을 대조했다.

| 검증 항목 | 결과 |
|---|---|
| 태그 키 개수 | HEAD 1,683 = 작업트리 1,683 |
| 사라진 키 / 새 키 / 값 변경 | 0 / 0 / 0건 |
| 파일 문자 길이(LF 정규화 후) | 271,246자로 완전 동일 |
| 줄 다중집합 비교 | 동일 (순서만 다름) |
| 키 정렬 + LF 정규화 후 비교 | **완전 일치** |

`git diff --stat` 기준 `+4,469 / -4,469`. 즉 **같은 줄들이 자리만 바꾼 것**이다.

### 1.2 CRLF는 원인이 아니다

작업트리는 CRLF, HEAD는 LF지만 `core.autocrlf=true`(system 레벨)가 흡수한다. 근거: 동일하게 CRLF인 `sns_tag_catalog.json`·`sns_user_metadata.json`은 변경으로 잡히지 않는다. **CRLF는 이번 범위에서 제외한다.**

### 1.3 과거에도 반복됐다

```
2026-07-09  8118aa2  +3683/-3683   완전 대칭 = 순수 노이즈
2026-07-09  1c8b6ff  +3594/-3594   완전 대칭 = 순수 노이즈
2026-07-09  fdbb6ce  +3676/-3654   실제 변경 22줄이 노이즈에 묻힘
2026-07-26  22d768a  +3970/-3552   실제 변경 418줄이 노이즈에 묻힘
2026-07-07  02cd5fe  +3595/-3560   실제 변경 35줄이 노이즈에 묻힘
```

## 2. 문제 (Problem)

### 2.1 무엇이 문제인가

데이터 손실은 **없다**. 문제는 다음 세 가지다.

| 영향 | 내용 |
|---|---|
| 실제 변경 은폐 | 태그 1개를 바꿔도 4,469줄 diff에 묻혀 커밋 리뷰가 불가능하다 |
| 커밋 노이즈 | 매 커밋마다 약 295KB 전체가 새 blob으로 저장된다 |
| 병합 충돌 위험 | 전 구간이 변경으로 보여 두 세션이 같은 파일을 만지면 충돌 폭이 커진다 |

특히 첫 번째가 실질 피해다. `2026-07-26 22d768a`에서 실제 태그 추가 418줄이 노이즈 3,552줄에 섞여 들어갔고, 그 커밋만 봐서는 무엇이 추가됐는지 알 수 없다.

### 2.2 원인

`scrap_sns_server.py`의 저장 경로 3곳 모두 `json.dump(...)`에 **`sort_keys`가 없다.** 브라우저가 보낸 JS 객체의 삽입 순서를 그대로 파일에 쓴다.

| 위치 | 대상 파일 | 현재 발현 |
|---|---|---|
| `scrap_sns_server.py:833` (`save_tags`) | `sns_tags.json` | **발현 중** |
| `scrap_sns_server.py:866` (`save_tag_catalog`) | `sns_tag_catalog.json` | 잠재 |
| `scrap_sns_server.py:878` (`_atomic_write_json` → `save_user_metadata`) | `sns_user_metadata.json` | 잠재 |
| `migrate_threads_domain.py:102` (`write_json`) | `sns_tags.json` | 잠재 |

### 2.3 순서가 뒤섞이는 메커니즘

`web_viewer/script.js:1915-1921`:

```js
Object.assign(postTags, serverTags);
Object.keys(postTags).forEach((url) => {
    postTags[url] = (postTags[url] || []).filter(...);
    if (postTags[url].length === 0) delete postTags[url];
});
```

1. `postTags`는 먼저 `localStorage` 순서로 채워진다
2. `Object.assign`으로 서버 태그를 덮어쓴다 — 기존 키는 위치 유지, **새 키는 객체 끝에 추가**
3. 빈 배열 키는 `delete`로 제거된다
4. 이 뒤섞인 순서 그대로 `/api/save-tags`로 전송되고, 서버가 정렬 없이 저장한다

즉 `localStorage` 순서와 서버 파일 순서가 어긋나는 한 매번 다른 순서가 나온다. 자동태그 적용(`script.js:1463` `postTags[url] = [...merged]`)도 같은 방식으로 키를 뒤에 붙인다.

### 2.4 순서 의존성 검토 — 없음

정렬해도 안전한지 확인했다.

| 소비처 | 순회 방식 | 순서 의존 |
|---|---|---|
| `web_viewer/script.js:1570` | `Object.keys(postTags).forEach` — 레거시 키 마이그레이션 | 없음 |
| `web_viewer/script.js:1916` | `Object.keys(postTags).forEach` — 빈 배열 정리 | 없음 |
| `utils/query-sns.mjs:10` | URL을 키로 조회 | 없음 |

`sort_keys=True`는 **키만** 정렬한다. 태그 배열 **내부** 순서(사용자가 붙인 순서)는 건드리지 않는다.

### 2.5 수용하는 트레이드오프

정렬 저장으로 얻는 것은 diff 노이즈 제거이고, 잃는 것은 **JSON 파일 내 키 배열이 시간순(생성·적용 순서)에서 알파벳순으로 영구 변경**된다는 점이다.

즉 "이 태그를 언제 붙였는지"를 파일 내 키 위치로 추정하던 방식은 이후 불가능해진다. 다만 그 추정은 애초에 신뢰할 수 없다 — 2.3에서 확인했듯 현재도 `localStorage` 병합 때문에 순서가 매번 뒤섞이므로 시간순이 보존되고 있지 않다. 소비처 3곳(2.4)이 모두 순서 비의존임을 전수 확인했으므로 **이 트레이드오프를 수용한다.**

## 3. 해결 (Solution)

### 3.1 검토한 옵션과 기각 근거

| 옵션 | 내용 | 판정 |
|---|---|---|
| **A. 서버 저장 시 `sort_keys=True`** | 뷰어 상태 저장 경로 3곳에 인자 추가 + `migrate_threads_domain.py`는 호출부 분기(S2-B) | **채택** |
| B. 클라이언트에서 정렬 후 전송 | `script.js`에서 키 정렬해 POST | 기각 — 저장 경로가 여러 곳이고, 클라이언트를 우회하는 쓰기(`migrate_threads_domain.py`)를 못 막는다 |
| C. `.gitattributes`로 diff 억제 | `sns_tags.json -diff` 등록 | 기각 — 노이즈를 숨길 뿐 실제 변경도 함께 안 보이게 된다. 문제를 악화시킨다 |
| D. git에서 추적 제외 | `.gitignore` 등재 후 `git rm --cached` | 기각 — `AGENTS.md`가 이 파일들을 "영구 데이터 surface"로 규정한다. 사용자 태그는 백업 가치가 있다 |
| E. 아무것도 안 함 | 현행 유지 | 기각 — 2.1의 실제 변경 은폐가 이미 5회 이상 발생했다 |

##### S2-B. `migrate_threads_domain.py` — 파라미터화 (호출부 분기)

`write_json`은 **호출부 2곳의 성격이 다르다.** 무조건 정렬하면 수집 산출물의 필드 순서가 깨진다.

|---|---|---|
| `apply_file_rewrites` (212행) | `output_total/total_full_*.json`, `output_threads/python/**/*.json` — 수집 산출물 | **금지** (`utils/post_schema.py`의 `STANDARD_FIELD_ORDER`가 정본) |
| `apply_tag_rewrite` (226행) | `web_viewer/sns_tags.json` — 뷰어 상태 | **적용** |

따라서 함수를 기본값 `False`로 파라미터화하고 태그 호출부에서만 `True`를 넘긴다. 아래 코드를 그대로 적용한다.

**변경 1 — 함수 정의 (101-102행)**

```python
def write_json(path: Path, payload: Any, *, sort_keys: bool = False) -> None:
    path.write_text(
        json.dumps(payload, ensure_ascii=False, indent=4, sort_keys=sort_keys),
        encoding="utf-8",
    )
```

**변경 2 — 태그 호출부 (`apply_tag_rewrite`, 226행)**

```python

```

**변경 없음 — 산출물 호출부 (`apply_file_rewrites`, 212행)**

`write_json(path, rewritten)` 그대로 둔다. 기본값 `False`로 현재 동작이 유지된다.

태그 저장은 `scrap_sns_server.py:821` `/api/save-tags` POST로 브라우저 없이 완전히 재현된다. 이번 변경은 **저장 포맷만 바뀌고 뷰어 UX는 동일**하므로 `AGENTS.md:83`의 화면 캡처 요구 대상이 아니다(재시작 규약 `AGENTS.md:82`는 S4-A에서 준수). 따라서 수동 조작 대신 아래 스크립트로 검증하고 로그를 증거로 남긴다.

검증 기준은 **HEAD 대비 diff가 아니라 "정렬 저장 1회 후 상태" 대비 diff**로 잡는다. HEAD는 아직 정렬 이전 상태라 첫 저장에서 필연적으로 대규모 diff가 나오기 때문이다(6장 3번 위험 참조).

##### S4-C. 검증 스크립트

`$SCRATCH/s4_verify.mjs`로 저장한다(레포에 만들지 않는다).

```js
import { execSync } from 'node:child_process';
import { readFileSync, writeFileSync } from 'node:fs';

const REPO = 'D:/vibe-coding/scrap_sns';
const FILE = `${REPO}/web_viewer/sns_tags.json`;
const API = 'http://localhost:5000/api';
const PROBE_KEY = 'https://www.threads.com/@__sortkeys_probe__/post/PROBE';
const log = [];
const say = (m) => { log.push(m); console.log(m); };

const post = async (path, body) => {
  const r = await fetch(`${API}/${path}`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(body),
  });
  if (!r.ok) throw new Error(`${path} -> HTTP ${r.status}`);
  return r.json();
};
const readRaw = () => readFileSync(FILE, 'utf8');
const lineDiff = (a, b) => {
  const A = a.split(/\r?\n/), B = b.split(/\r?\n/);
  const inB = new Set(B), inA = new Set(A);
  return A.filter((l) => !inB.has(l)).length + B.filter((l) => !inA.has(l)).length;
};

// P0: 현재 태그를 그대로 재저장해 "정렬된 기준선"을 만든다
const original = await (await fetch(`${API}/get-tags`)).json();
if (PROBE_KEY in original) throw new Error('probe key already present — 중단');
await post('save-tags', original);
const baseline = readRaw();
say(`[P0] baseline 확정 — 키 ${Object.keys(original).length}개, ${baseline.length}자`);

// P0-1: 정렬 여부 직접 확인
const keysOnDisk = Object.keys(JSON.parse(baseline));
const sorted = [...keysOnDisk].sort();
const isSorted = keysOnDisk.every((k, i) => k === sorted[i]);
say(`[P0-1] 디스크 키 정렬 여부: ${isSorted}`);

// P1: 프로브 태그 1개 추가 → 변경 줄 수 측정
await post('save-tags', { ...original, [PROBE_KEY]: ['__probe__'] });
const added = lineDiff(baseline, readRaw());
say(`[P1] 태그 1개 추가 시 변경 줄 수: ${added}`);

// P2: 원복 → 기준선과 바이트 단위 일치해야 한다
await post('save-tags', original);
const restored = readRaw();
const identical = restored === baseline;
say(`[P2] 원복 후 기준선과 동일: ${identical}`);

// 참고: HEAD 대비 numstat (판정에는 쓰지 않음)
say(`[참고] HEAD 대비: ${execSync(`git -C ${REPO} diff --numstat -- web_viewer/sns_tags.json`).toString().trim() || '(변경 없음)'}`);

const pass = isSorted && added > 0 && added <= 10 && identical;
say(`[판정] ${pass ? 'PASS' : 'FAIL'}`);
writeFileSync(process.env.S4_LOG, log.join('\n') + '\n', 'utf8');
process.exit(pass ? 0 : 1);
```

#### S5. 나머지 두 파일 정렬 전환

S4에서 `sns_tags.json`은 이미 정렬 상태로 확정됐다. 나머지 두 파일(`sns_tag_catalog.json`, `sns_user_metadata.json`)은 서버 코드가 고쳐졌어도 **다음 저장이 일어나기 전까지는 옛 순서 그대로** 남는다.

이를 위해 뷰어 UI를 조작(카탈로그 편집·별표 토글 후 원복)하면 실제 데이터를 건드렸다가 되돌리는 것이라 실패 시 상태가 오염된다. 대신 **읽어서 정렬해 다시 쓰는 1회성 스크립트**를 쓴다. 데이터는 전혀 바뀌지 않고 키 순서만 바뀐다.

`$SCRATCH/s5_sort_once.mjs`:

```js
import { readFileSync, writeFileSync } from 'node:fs';

const REPO = 'D:/vibe-coding/scrap_sns';
const TARGETS = [
  'web_viewer/sns_tag_catalog.json',
  'web_viewer/sns_user_metadata.json',
];

// Python의 sort_keys=True는 재귀 정렬이다. 최상위만 정렬하면 다음 서버 저장 때
// 중첩 객체(sns_user_metadata.json의 post_key 하위 필드)에서 diff가 한 번 더 난다.
// 배열 내부 순서(태그 순서 등)는 map으로 그대로 보존된다.
const sortDeep = (v) =>
  Array.isArray(v) ? v.map(sortDeep)
  : (v && typeof v === 'object')
    ? Object.fromEntries(Object.keys(v).sort().map((k) => [k, sortDeep(v[k])]))
    : v;

for (const rel of TARGETS) {
  const path = `${REPO}/${rel}`;
  const data = JSON.parse(readFileSync(path, 'utf8'));
  // 서버의 json.dump(indent=4, ensure_ascii=False, sort_keys=True)와 동일한 출력
  const after = JSON.stringify(sortDeep(data), null, 4);
  // 데이터 동일성 확인 — 다르면 쓰지 않는다
  if (JSON.stringify(sortDeep(data)) !== JSON.stringify(sortDeep(JSON.parse(after)))) {
    throw new Error(`${rel}: 정렬 전후 데이터 불일치 — 중단`);
  }
  writeFileSync(path, after, 'utf8');
  console.log(`${rel}: 최상위 키 ${Object.keys(data).length}개 정렬 완료`);
}
```

```bash
cd D:/vibe-coding/scrap_sns && node "$SCRATCH/s5_sort_once.mjs" && git diff --numstat -- web_viewer/
```

**정렬 순서 일치 확인**: JS `Array.prototype.sort()`는 UTF-16 코드유닛, Python `sort_keys=True`는 유니코드 코드포인트 기준이다. BMP 밖 문자(이모지 등)가 키에 있으면 두 정렬이 갈린다. 두 파일의 키는 `post_key`·태그명이므로 실제 위험은 낮지만, S5 실행 후 서버를 통해 한 번 더 저장시켜(`/api/save-tag-catalog`, `/api/save-user-metadata`에 현재 값 그대로 POST) `git diff`가 비는지 확인하면 이 차이까지 배제된다. **비지 않으면 서버 저장본을 정본으로 채택한다.**
