# scrap_sns × 90_자료수집 통합 — 웹·파일 카드와 제작자 프로필

## 목적

scrap_sns 뷰어의 정체성을 넓힌다. **「내 SNS 저장글 모음」 → 「+ 벤치마킹」 → 「+ 저장 범위가 SNS 밖 웹·파일까지」**.

지금 뷰어는 SNS 4종(Threads·LinkedIn·X·YouTube) 2,922건만 보여준다. 그런데 실제로 참고하는 자료 상당수는 웹사이트·블로그·노션·PDF·전자책으로 배포되고, 그것들은 `C:/Users/ahnbu/cowork/90_자료수집` 옵시디언 볼트에 283건 쌓여 있으면서 뷰어에서는 전혀 보이지 않는다. 검색할 때 두 곳을 따로 뒤져야 한다.

두 번째 문제는 연결이다. 파일·요약본 중 일부는 원래 SNS·유튜브로 배포된 것이라 뷰어에 원문 카드가 이미 있는데(실측 53건), 그 카드에서 내가 정리해둔 요약본으로 갈 길이 없다.

세 번째는 사람이다. 같은 사람이 Threads·LinkedIn·YouTube·블로그에 걸쳐 활동하는데 뷰어는 플랫폼별로 다른 인물로 취급한다. 볼트에는 제작자 프로필 121명이 이미 정리돼 있다.

## 요구사항

- **R1.** 볼트의 자료 노트가 뷰어 목록에 카드로 보인다. 별도 화면이 아니라 SNS 글과 같은 목록·같은 검색 대상이어야 한다.
- **R2.** 상단 필터에 자료 유형 칩이 생겨, 웹으로 배포된 자료와 파일로 배포된 자료를 갈라 볼 수 있다.
- **R3.** 자료 카드를 열면 뷰어 화면 안에서 정리해둔 본문을 읽을 수 있다. 다른 앱으로 튕기지 않는다.
- **R4.** 뷰어에 원문 카드가 이미 있는 자료는 카드를 새로 만들지 않고, 그 원문 카드에서 내 요약본으로 갈 수 있다.
- **R5.** 카드의 작성자 이름 옆에서 그 사람의 프로필과, 그 사람 글을 플랫폼 구분 없이 한 목록으로 볼 수 있다.
- **R6.** 자료 카드에도 SNS 글과 똑같이 별표·숨김·메모·태그·검색이 동작한다.
- **R7.** 스킬 산출물 폴더에 고여 있는 자료(`sns-scrap-save/`, `yt-summary-save/`)가 볼트 표준으로 편입되어 R1~R6의 혜택을 받는다.

## 성공 기준

1. `pytest tests/unit`, `pytest tests/contract`, `pytest tests/e2e/test_api_security.py` 전부 통과.
2. 뷰어 상단 총건수 = 최신 `output_total/total_full_YYYYMMDD.json` 게시글 수 + 자료 인덱스 건수. 두 값이 화면에서 구분돼 보인다.
3. **창을 띄우지 않는 검증 스크립트**(`_shared/hidden-browser-verify-runner.mjs` 계열)로 실제 `http://localhost:5000/` 화면을 조작해 캡처를 남긴다.
   - 〈웹〉 칩 클릭 → 웹 자료만 표시
   - 〈파일〉 칩 클릭 → 파일 자료만 표시
   - 자료 카드 열기 → 정리 본문이 화면에 렌더됨
   - 원문 겹침 카드에서 「요약」 배지 클릭 → 해당 요약본이 열림
   - 이름 옆 프로필 아이콘 클릭 → 프로필과 그 사람의 SNS+웹+파일 글이 한 목록에 뜸
4. 볼트에서 노트 하나를 수정한 뒤 인덱스를 재생성하면 뷰어 표시가 바뀐다.
5. `node utils/query-sns.mjs`에서도 자료 카드가 조회된다.
6. 자료 카드에 별표·메모를 남기고 서버를 재시작해도 유지된다.
7. 겹치는 자료가 카드와 배지로 **이중 노출되지 않는다** (같은 글이 검색 결과에 두 줄로 뜨지 않음).
8. **병행 세션 기능이 회귀하지 않는다** — 벤치마킹 표식 건수·사용자 메타(별표·숨김·메모) 건수가 작업 전 기준선과 같고, `scripts/verify_creator_card_headless.mjs`가 기준선과 같은 결과를 낸다.
9. 자료 노트 본문에 섞인 스크립트·이벤트 속성·`javascript:` 링크가 뷰어에서 **실행되지 않는다**(악성 표본 렌더 테스트).
10. 〈웹〉·〈파일〉 칩을 켜고 흔한 단어로 검색해도 자료가 검색 상한에 잘려 빠지지 않는다(F25).

## 결정안

### D1. 볼트 → 파생 인덱스 → 뷰어

```
90_자료수집 (정본)  ──capture로 계속 수집·편집
      │
      ▼  인덱스 생성 스크립트 (신규, 재생성 가능)
web_viewer/sns_library_index.json   +   web_viewer/sns_creators.json
      │
      ▼
scrap_sns 뷰어 = SNS 2,922건 + 자료 약 240건
```

되돌릴 때 인덱스 파일을 지우면 원상복구된다. 볼트는 손대지 않는다.

이 구조를 택한 결정적 근거는 **같은 패턴이 이미 두 번 돌고 있다**는 것이다.
- YouTube는 SNS가 아닌데 이미 5번째 유형으로 589건 들어와 있다 (`index.html:130`).
- 카드 우하단 배지 → 외부 요약 링크가 이미 작동 중이다 (`web_viewer/script.js:3149` `buildExternalSummaryLinks`, Lilys·LiveWiki 911건 매핑).

### D2. 유형은 〈웹〉·〈파일〉 2종, `sns_platform` 필드를 재사용

- 원본 URL이 있으면 〈웹〉, 없으면 〈파일〉. 둘 다인 자료는 〈웹〉에 넣고 카드에 파일 아이콘을 붙여 구분한다.
- 3종(웹/파일/파일웹)을 기각한 이유: "파일이면서 웹"에 해당하는 건이 10건 미만이라 상단 칩 한 자리를 상시 점유할 값이 없다.
- 출처별 세분(노션·네이버·블로그…)을 기각한 이유: 대부분 한 자릿수라 빈 칩이 생긴다.

**트레이드오프 (기록해 둔다):** `sns_platform`에 SNS가 아닌 `web`·`file`을 넣으면 필드 이름이 사실과 어긋난다. 그럼에도 재사용하는 이유는 뷰어의 필터·정렬·검색·카운트가 이 필드 하나를 20여 곳에서 참조하고 있어, 새 필드를 만들면 그 전부를 고쳐야 하기 때문이다. YouTube가 이미 같은 처지다. `utils/post_schema.py`에 이유를 주석으로 남긴다.

### D3. 자료 카드는 뷰어 안에서 읽는다

- 목록 응답에는 미리보기만 싣고, 카드를 열 때 본문을 따로 요청한다 (기존 `full_text_preview` 방식과 동일).
- 우하단에 원문 사이트 / 원본 파일 / 옵시디언에서 열기 아이콘.
- 근거: 옵시디언으로 튕기면 뷰어 검색으로 자료 본문을 찾을 수 없게 된다.

### D4. 겹치는 자료는 카드 대신 배지

- 뷰어에 원문이 이미 있는 자료(실측 53건 + 승격분)는 자료 카드를 만들지 않는다.
- 대신 원문 카드 우하단, 바로가기 아이콘 왼쪽에 「요약」 배지를 붙이고, 누르면 그 자리에서 내 요약본이 열린다.
- 구현 위치는 `buildExternalSummaryLinks`(`script.js:3149`)와 같은 층. 그 함수의 기존 원칙 — *매핑이 없으면 아이콘을 아예 그리지 않는다* — 을 그대로 따른다.
- 근거: 원문과 요약본이 검색 결과에 두 줄로 뜨는 것을 막는다(성공 기준 7).

### D5. 제작자 프로필 — 두 층으로 나눈다 (2026-09-10 개정)

당초 "매핑 파일이 본체"라고 봤으나 이는 틀린 판단이었다. 기능을 두 층으로 갈라야 한다.

**층 1 — 모든 카드에서 즉시 동작 (매핑 불필요)**

이름 옆 아이콘 → 그 사람 페이지. 아래 재료가 이미 수집돼 있어 매핑이 하나도 없어도 전 카드에서 뜬다.

| 플랫폼 | 사람 식별 키 | 이미 가진 프로필 재료 |
|---|---|---|
| LinkedIn | `user_link` (731/769, 불투명 ID지만 사람 단위로 안정) | `display_name` + **`profile_slogan` 731건** (한 줄 소개) |
| Threads | `username` / `canonical_username` (유저명 변경 추적 필드 보유) | `display_name` |
| YouTube | `channel_id` (588/589) | 채널 표시명 |
| X | `username` | `display_name` |

5건 이상 대상(2026-09-10 추정 29명)에서 **소수 파일럿으로 적중률을 먼저 잰다**. 기준을 넘으면 대상 전원으로 넓히고, 미달이면 병행 세션 결론(채널 자동보강 기각, F23)을 따른다. 3건 이상(85명)으로의 확대는 이번 범위 밖이다. 파일럿 인원·기준 수치는 계획서 W5가 정한다.

**정정 (2026-09-11) — 벤치마킹 계정과의 대조는 계정 `id`가 아니라 `channels.threads` 핸들로 한다.** 앞서 "표기 불일치로 20개 중 19개 오판"이라 적은 것은 계정 내부 `id`와 스레드 핸들을 비교한 측정 오류였다(F21 철회). 조회 대상에서 뺄 사람은 벤치마킹 계정의 `channels`에 다른 플랫폼이 이미 등록된 사람이다.

**0단계의 정밀도 한계.** 본문에 유튜브 링크가 있다고 그 사람 채널이라는 보장이 없다 — 남의 콘텐츠 소개가 더 많다. 176명은 후보일 뿐이며, 핸들·이름 일치 검사를 통과한 것만 초안에 올린다. 자동 확정하면 엉뚱한 사람이 합쳐진다.

**4단계를 핵심으로 두는 이유:** 매핑은 한 번에 다 채우는 자산이 아니라 **쓰면서 쌓이는 자산**이다. 기계가 못 맞히는 대부분은 사용자만 아는 정보이고, 배치로는 수십 명치를 한 번에 확인해야 하지만 뷰어에서는 마주칠 때마다 한 명씩이다.

**위험:** 프로필 조회는 비로그인 공개 페이지 경로를 쓴다. 로그인 상태의 대량 조회는 계정 제한 위험이 있다. 이 레포는 이미 참여지표를 비로그인 경로로 읽고 있다(`utils/linkedin_metrics.py`).

동명이인·표기차이 위험이 있으므로 매핑은 자동 확정하지 않는다.

**구현 원칙 (세부는 계획서)**

- 자료 노트는 **폴더가 아니라 frontmatter로 고른다** — `topic`·`creator`가 있고 제작자 프로필(`type: creator`)이 아닌 것, `_`·`.`로 시작하는 폴더는 제외. `topics.json`은 주제 목록이 아니어서 폴더 목록의 근거가 못 된다(F32). 이 기준이면 `sns-scrap-save/`가 자연히 걸러져 [NO] "산출물 폴더 직접 읽기 금지"와 맞는다.
- 자료 전용 필드는 `META_FIELDS`에 올린다. 빠지면 목록 응답이 조용히 버린다(F26) — 이 레포가 세 번 겪은 함정이다.
- 서버 캐시 키·ETag에 볼트 상태를 넣는다. 안 넣으면 볼트를 고쳐도 화면이 안 바뀐다(성공 기준 4).
- 서버 검색과 뷰어의 플랫폼 허용 목록에 `web`·`file`을 넣는다. 안 넣으면 검색 상한 절단 뒤에 걸러져 자료가 조용히 빠진다(F25).
- 노트 본문은 **escape 먼저, 허용 태그만 직접 생성**하는 렌더러로 그린다. 노트에는 남의 글이 스크랩돼 있어 HTML로 그대로 넣으면 스크립트 주입이 된다. 라이브러리를 들이지 않는 기존 원칙(`script.js:2781-2783`)과 같다. 트레이드오프: 드문 마크다운 문법은 어색하게 보일 수 있다 — 표본 렌더 검증에서 깨지면 로컬 파일로 라이브러리를 들인다.
- 새 UI 스타일은 `style.css`에 둔다. `tailwind-built.css`는 미리 빌드된 파일이고 재빌드 명령이 없어(F33) 새 유틸리티 클래스가 적용되지 않는다.
- 자료 인덱스 JSON은 git에서 뺀다. 볼트에서 언제든 재생성되고 본문을 담아 수 MB가 된다(F32).
- 계정 연결의 확정 기준: **본인이 게시한 링크**(자기 프로필·애그리게이터)와 **사용자가 뷰어에서 연결한 것**만 확정한다. 이름·본문 링크로 찾은 것은 후보로만 둔다(F23 — 동명이인 실측).
