## 목적

내가 벤치마킹할 계정을 지정하면 그 계정의 콘텐츠와 성과를 **한 화면에서 조회**할 수 있게 한다.

지금은 `scrap_sns`에 **내가 저장(북마크)한 글만** 들어온다. 저장 여부가 「그 글이 좋았나」에 좌우되므로 잘 된 글만 모인 집합이고, **망한 글이 데이터에 아예 없다.** 계정 단위로 긁으면 성공작과 실패작이 같이 들어와 이 선택 편향이 사라진다.

용도는 넷이다(사용자 확인, 2026-09-06).

| 용도 | 무엇을 하나 |
|---|---|
| 새 소재 픽업 | 해외 원천에 뜬 것 중 국내에 안 풀린 걸 골라 SNS 글감으로 |
| 형식·훅 학습 | 잘 된 글의 제목·구조를 보고 내 글에 반영 |
| **소재 검증** | 내가 쓰려는 소재가 **이미 풀렸는지**, 그 소재영역을 어떻게 풀어간 글이 잘됐는지 확인 |
| 선점 역판정 | 국내 번역채널이 이미 다룬 주제인지 대조 |

세 번째가 이 SPEC의 설계를 가장 크게 좌우한다 — **내 저장글과 벤치마킹 글을 한 번에 검색**해야 성립하기 때문이다.

## 요구사항

- **R1.** 벤치마킹 계정 목록을 **화면에서** 추가·수정·비활성·삭제할 수 있다. 사용자가 JSON을 손으로 편집하지 않는다.
- **R2.** 한 계정이 여러 플랫폼에 있으면 **한 항목**으로 관리한다. 수집 단위는 플랫폼이 아니라 계정이다.
- **R3.** 계정별로 수집 편수 상한을 정할 수 있다.
- **R4.** 수집된 글은 기존 뷰어에서 **내 저장글과 함께 검색**되면서도, 둘을 **구분**해 볼 수 있다.
- **R5.** 이미 저장돼 있던 글이 벤치마킹 대상 계정의 것이면, **기존 맥락(태그·별표·수집경로)을 잃지 않고** 벤치마킹 계정 소속으로도 조회된다.
- **R6.** 재수집해도 같은 글이 두 번 쌓이지 않는다. 편수 상한을 나중에 올려도 마찬가지다.
- **R7.** 계정 등록 시 핸들 오타를 **입력 시점에** 잡는다.
- **R8.** 계정을 비활성하면 **그 계정으로만 들어온 글은 안 보이고, 원래 내 저장글이었던 것은 계속 보인다.** 다시 활성하면 안 보이던 글이 되살아난다.
- **R9.** 이미 논의·수집된 제작자는 **코드가 후보 풀에 미리 채워둔다.** 사용자는 그중에서 골라 켜기만 한다. 후보 풀을 다시 채워도 **이미 켜둔 설정이 초기화되지 않는다.**
- **R10.** 후보에서 **뺄 수 있다.** 뺀 계정은 후보 목록에서 사라지고 **동기화를 다시 돌려도 되살아나지 않는다.** 데이터는 지우지 않으며 되돌릴 수 있다.

## 성공 기준

**1차(파이프라인 검증)와 2차(쓸모 검증)의 합격 기준을 분리한다.** 섞으면 1차 결과로 잘못된 결론을 낸다.

| 단계 | 규모 | 판정 대상 | 합격 기준 |
|---|---|---|---|
| **1차** | 12계정 × 신규 5편 ≈ 60편 | **파이프라인이 도는가** | ① 화면에서 계정 추가·비활성이 되고 저장된다 ② 수집분이 뷰어에 뜬다 ③ 좋아요·조회수가 붙는다 ④ 중복 0건 ⑤ 내 저장글과 구분된다 ⑥ **수집 직전 스냅샷 대비 태그·별표·메모 건수가 같다**(고정 숫자 대조 아님 — D4 주의) |
| **2차** | 12계정 × 30편 ≈ 360편 | **벤치마킹이 되는가** | 계정 안에서 성과가 갈리고, 실제로 소재·형식을 건진다 |

> ⚠️ **1차는 쓸모 판정이 아니다.** 계정당 5편이면 그 계정 안에서 잘된 글과 망한 글이 갈리지 않아 「성과순 정렬」이 의미를 갖지 못한다. 1차 결과를 보고 *"별로 쓸모없네"* 하고 접으면 오판이다.

## 결정안

### D1. 계정 관리는 Settings 모달의 5번째 탭

`index.html`에 Settings 모달과 탭 4개(Tags·Hidden·Display·Maintenance)가 이미 있다. **Tags 탭이 필요한 것과 구조가 같다** — 검색창 + 추가 버튼 + 목록 + 빈 상태. 이를 복제한다.

서버도 `get-tag-catalog` / `save-tag-catalog` 쌍과 원자적 쓰기 헬퍼(`_atomic_write_json`)가 있어 같은 쌍을 하나 더 만드는 일이다.

**계정 한 줄의 구성**

| 요소 | 비고 |
|---|---|
| 이름 | |
| **켜기/끄기 토글** | 껐다고 수집분이 사라지지 않는다. **끌 때 「이 계정으로만 들어온 N건이 안 보이게 됩니다」를 숫자와 함께 알린다** |
| 계정 주소 칸 4개 | YouTube·Threads·LinkedIn·X, 빈칸 허용. **각 칸에 「수집 가능」 배지** — 지금 긁을 수 있는 것은 YouTube·LinkedIn뿐이다(D11) |
| 후보/대상 구분 | 꺼진 계정은 접어둔다. 후보 풀 전체가 늘 펼쳐져 있으면 못 쓴다 |
| 목적 | 드롭다운 — 선점소재/선점판정/형식학습/알림 (`20260721_03` §2) |
| 편수 | 기본 5 |
| 메모 | |

**계정 상태는 3개다 (R10)**

| 상태 | 수집 | 그 계정 글 | 후보 목록 | 동기화가 다시 올리나 |
|---|---|---|---|---|
| **켜짐** `active` | ○ | 보임 | 보임 | — |
| **꺼짐** `off` | ✕ | 안 보임 | 보임 | — |
| **뺌** `excluded` | ✕ | 안 보임 | **안 보임** | **안 올림** |

- **세 상태 모두 데이터를 지우지 않는다.** 저장글이었던 글은 어느 상태에서든 계속 보인다(R8)
- **뺀 계정은 「제외한 계정 보기」에서 확인·복구**한다
- **「뺌」이 없으면 동기화가 망가진다.** 뺀 계정이 소스에 남아 있으면 다시 돌릴 때마다 후보로 되살아난다. themodellers가 정확히 이 경우다 — 명단에서 뺐지만 수집 데이터에 9건이 남아 있다
- **완전 삭제는 화면에 두지 않는다.** 「뺌」이 사용자가 원하는 「제외」를 이미 충족하므로 되돌릴 수 없는 조작을 얹을 이유가 없다
>
> **용어**: 이 문서의 「계정 주소」는 유튜브 `@builderjoshkim`, Threads `@joshproductletter`, 링크드인 `linkedin.com/in/uxjosh`의 `uxjosh`처럼 **프로그램이 그 계정을 찾아가는 식별자**를 말한다. 사람 이름만으로는 수집할 수 없다.

> ⚠️ **등록 가능과 수집 가능은 다르다.** Threads 핸들을 등록해도 계정 단위 수집기가 없어 지금은 안 긁힌다. 화면에서 이를 구분해 표시하지 않으면 "등록했는데 왜 0건이냐"가 된다.

### D2. 저장 스키마

```json
{
  "accounts": [
    {
      "id": "builderjosh",
      "name": "빌더 조쉬",
      "status": "active",
      "purpose": "형식학습",
      "limit": 5,
      "channels": {
        "youtube": "@builderjoshkim",
        "threads": "@joshproductletter",
        "linkedin": "uxjosh"
      },
      "match_keys": {
        "youtube": ["UCxxxxxxxxxxxxxxxxxxxxxx"],
        "threads": ["joshproductletter"],
        "linkedin": ["ACoAAAfst4QBZ_TBpSZb5m5EitKHc3H5PhUbe5E"]
      },
      "memo": "1인 SaaS 빌드. 기획자 관점 PRD",
      "saved_count": 31,
      "last_saved_at": "2026-09-02",
      "sources": ["scrap_sns", "creator_profile"]
    }
  ]
}
```

뒤 3개는 **동기화 스크립트가 채우는 참고값**이다(D10). 사람이 켤지 말지 판단할 때 쓰고, 수집 동작에는 관여하지 않는다.

**게시물 쪽에 추가되는 필드 2개**

| 필드 | 용도 |
|---|---|
| `benchmark_accounts` (배열) | 이 글이 어느 벤치마킹 계정에서 왔나. 배열인 이유는 D9-다 |
| `is_saved` (불린) | 내 북마크에 있나. **`source`로 판정하지 않는 이유는 D9-나** |

표시 여부는 저장하지 않고 이 둘로 계산한다 — `보임 = is_saved OR (benchmark_accounts 중 status == "active")`

> 세 번째 필드 `channel_id`가 YouTube 레코드에 추가된다(D12). 세 필드 모두 `utils/post_schema.py`·`utils/post_meta.py`에 등록해야 한다(D16).

### D3. 핸들 검증

YouTube 핸들 입력 시 `yt-search channel`(1유닛)로 채널명·구독자수를 채운다. **오타를 그 자리에서 잡는 것이 목적이다** — 사후에는 수집 0건의 원인을 알 수 없다.

**핵심 사실 — 중복 제거는 「먼저 나온 쪽을 남긴다」.** `total_scrap.py:632-637`의 배열 순서가 곧 정책이며, 코드에 이미 경고 주석이 있다.

> *"내 게시물을 앞에 둔다. 같은 activity가 저장글에도 있으면 중복 제거가 먼저 나온 쪽을 남기는데, 내 글 레코드가 노출수와 is_own_post를 갖고 있어 더 풍부하다. **뒤에 두면 그 정보가 조용히 버려진다.**"*

즉 벤치마킹 수집분을 배열 어디에 넣느냐가 정책 결정이다.

| 안 | 방식 | 결과 | 판정 |
|---|---|---|---|
| **A** | 벤치마킹을 배열 **뒤**에 | 기존 73건 그대로 유지, 벤치마킹 중복분 drop. **그 73건에 「벤치마킹 계정 소속」 표시가 안 붙어 계정 필터에서 빠진다** | R5 위반 |
| **B** | 벤치마킹을 배열 **앞**에 | 벤치마킹 레코드가 남고 기존 drop. **내가 왜 저장했는지(`source`: ai.new2/drive7 등)가 날아간다.** 위 주석이 경고한 상황 그대로 | R5 위반 |
| **C** | **drop 대신 필드 병합** — 중복 제거 루프에서 버리기 전에 `benchmark_account` 표식만 기존 레코드에 얹는다 | 내 저장 맥락 유지 + 계정 소속 표시. R5 충족 | **권장** |

**C를 권한다.** A·B는 둘 다 정보를 버리고, 버려지는 게 조용해서 나중에 알아채기 어렵다. C는 `merge_results()`의 `continue` 앞에 표식 이전 한 줄을 넣는 수준이다.

> **전제 확인 필요(plan 단계)**: 태그·별표·메모는 `post_key` 기준으로 `sns_user_metadata.json`에 **레코드 밖에** 산다. 따라서 B에서도 태그는 살아남을 수 있다. 다만 `source`는 레코드 안에 있어 확실히 날아간다. C를 택하면 이 확인이 불필요해진다.

### D9. 비활성 시 게시물 처리 (R8)

사용자 확정 정책(2026-09-06): **저장글이었으면 유지 · 벤치마킹으로만 들어온 것은 숨김 · 재활성 시 복원.**

**구현은 「숨김 상태를 저장하지 않는다」.** 렌더 시점에 파생시킨다.

```
보임 = is_saved OR (benchmark_accounts 중 하나라도 status == "active")
```

이유는 기존 숨김 기능(Settings `tabHidden`, `invisiblePostsList`, `sns_user_metadata.json`)에 태우면 안 되기 때문이다.

| 태울 경우 새는 곳 |
|---|
| Hidden 탭에 자동 숨김 수십 건이 쏟아져 **사용자가 손으로 숨긴 글이 묻힌다** |
| 거기서 "숨김 해제"하면 **계정은 꺼져 있는데 글은 보이는** 모순 상태 |
| 재활성 시 **원래 사용자가 숨겼던 것까지 되살아난다** |

파생 방식이면 *"다시 추가하면 다시 보인다"*가 구현 대상이 아니라 자동 결과가 되고, 사용자 수동 숨김과도 독립적으로 동작한다.

**정책이 덮지 않는 케이스 3개**

| # | 상황 | 제안 | 상태 |
|---|---|---|---|
| **가** | ~~계정 **완전 삭제**~~ | **해소 — 화면에 삭제 버튼을 두지 않기로 확정(D1).** 끄는 것이 곧 안 보이게 하는 것이므로 별도 삭제가 불필요하다. 끌 때 *"이 계정으로만 들어온 N건이 안 보이게 됩니다"*를 숫자와 함께 알린다 | **확정** |
| **나** | 벤치마킹으로 들어온 글을 **나중에 내가 북마크** | 벤치마킹 뷰에서 좋은 글을 보고 저장하는 건 자연스러운 흐름이다. `source` 단일 필드로 판정하면 다음 수집 때 중복 제거로 `source`가 `benchmark`인 채 남아 **"저장글 아님"으로 오판**한다. → **`is_saved` 불린을 따로 두고 양방향 병합**(저장글 수집이 나중에 와도 기존 레코드에 `is_saved:true`를 얹는다) | **확정** |
| **다** | 한 글이 **두 계정에 걸침** (리포스트·공동출연) | 표식을 **배열**(`benchmark_accounts: [...]`)로 둔다. 비용이 없다 | 권장 확정 |

> ⚠️ **나를 놓치면 C안이 한쪽 방향으로만 만들어진다.** 「벤치마킹 → 기존 저장글에 표식 얹기」만 구현하고 「저장글 → 기존 벤치마킹 레코드에 `is_saved` 얹기」를 빠뜨리는 형태다. 증상이 조용해서(글이 슬쩍 사라짐) 발견이 늦는다.

### D10. 후보 풀 — 코드로 채우고, 내 설정은 보존한다

계정 관리는 두 층이다. 사용자 표현: *"그 리스트에서 골라서 추가하고, 해당 리스트 자체에 넣을 때는 코드를 통해서 업데이트하는 방식이다."*

```
후보 풀   = 세 소스를 합쳐 코드가 채운다
수집 대상 = 그중 화면에서 켠 것 (active: true)
```

**소스 3개 — 주 소스는 수집 데이터다**

| 소스 | 규모 | 주는 것 | 한계 |
|---|---|---|---|
| **`scrap_sns` 저자 집계** (주) | 저자 **1,172명** | 실제 계정 주소 · **내가 몇 건 저장했나** · 최신 저장일 · 플랫폼 | 저장한 적 없는 계정은 안 나옴(해외 5개가 그렇다) |
| `90_자료수집/_제작자별_상세` | 121명 중 주소 있는 **91명** | 멀티채널 주소가 프론트매터에 정리돼 있음(`youtube:` `threads:` `linkedin:` `x:`) | 30명은 주소 미기재. 우석지니·구씨·Jay Choi·피프가 없음 |
| 7월 명단 문서 `20260722_02` | 59채널 | 재생목록 기반 유튜브 채널 | 저장글에 안 들어온 것 보완용 |

주 소스를 수집 데이터로 두는 이유는 **「내가 몇 건 저장했나 · 마지막으로 언제 봤나」가 자동으로 붙기 때문**이다. 이것이 D8의 themodellers 제외 판단을 가능하게 한 값이며, 후보 판정의 1차 신호가 된다.

**동기화 규칙 — 덮어쓰지 않는다**

| 규칙 | 이유 |
|---|---|
| 다시 돌려도 `status` · 편수 · 메모는 **보존** | 초기화되면 도구를 못 쓴다 |
| **`status: excluded`인 계정은 다시 올리지 않음** | 없으면 뺀 계정이 소스에 남아 있는 한 매번 되살아난다(R10) |
| 새 제작자는 **추가**, 소스에서 사라진 제작자는 **표시만** 하고 목록에서 지우지 않음 | 이미 수집한 글이 가리킬 계정을 잃는다 |
| 같은 사람이 여러 소스에서 오면 **한 항목으로 합침** | 이승필이 제작자 파일과 수집 데이터 양쪽에 있다. 이름 기준으로 매칭한다 |

> **계정 주소는 「형태를 구분하지 않되, 유효성은 확인하고 넣는다」.** 두 가지를 섞지 않는다.
>
> - **형태 구분은 하지 않는다** — 링크드인이 읽는 주소(`seungpil`)로도 내부 ID(`ACoAAEYsARgB…`)로도 잡히지만, 어느 쪽인지 판정하는 규칙을 만들지 않는다. 과설계다.
> - **유효성은 넣기 전에 확인한다** — 등재 스크립트가 주소를 채울 때 실제로 열리는지 확인하고, **통과한 것만 칸에 넣는다.** 실패하면 주소를 비우고 「주소 미확인」으로 두어 켤 수 없게 한다.
>
> 이로써 목록에 들어간 주소는 전부 유효하며, 「돌려봐야 안다」가 없다. D3(입력 시 채널 확인)과 같은 규칙을 자동 등재에도 적용하는 것이다 — 사람이 넣은 주소만 검증하고 코드가 넣은 주소는 검증하지 않으면 앞뒤가 맞지 않는다.

### D12. 계정↔게시물 매칭 키 — **[검수 보완 2026-09-06]**

**실측한 문제**

### D13. 벤치마킹 수집분의 저장 위치와 병합 진입점 — **[검수 보완 2026-09-06]**

D4-C를 *"`merge_results()`의 `continue` 앞에 한 줄"*이라 적었으나, **그 한 줄이 붙을 자리에 벤치마킹 레코드가 아직 도착하지 않는다.**

| 안 | 방식 | 판정 |
|---|---|---|
| ㄱ | 기존 `output_youtube/python/youtube_py_full_*.json`에 섞어 쓴다 | **기각.** `is_saved`를 파일 출처로 도출할 수 없고, `youtube_scrap.py:756 select_update_targets()`가 벤치마킹 영상을 「이미 저장한 재생목록 영상」으로 오인해 내 재생목록 수집이 망가진다 |

### D14. `is_saved`의 기본값 — **[검수 보완 2026-09-06]**

> ⚠️ **그대로 구현하면 기존 2,685건이 화면에서 전부 사라진다.**

`utils/post_schema.py`의 `normalize_post()`는 `STANDARD_FIELD_ORDER`에 있으나 `defaults`에 없는 필드를 **빈 문자열**로 채운다. `보임 = is_saved OR (…)`를 그대로 쓰면 기존 레코드는 전부 `is_saved == ""`(거짓)이 되어 조건을 통과하지 못한다.

**결정**

- `defaults`에 **`is_saved: True`**를 넣는다 — 레거시·미표기 레코드는 전부 「내 저장글」로 본다. 안전한 쪽이 기본값이다
- 값은 병합 시점에 **도출**한다: D13-ㄴ의 벤치마킹 소스 파일에서만 온 레코드에만 `False`. 별도 백필 작업이 필요 없어진다
- 저장글 수집이 나중에 와도 기존 레코드에 `True`를 얹는 **양방향 병합**은 D9-나 그대로

### D15. 수집기 — `youtube_scrap.py --channel`, 요약은 돌리지 않는다 — **[검수 보완 2026-09-06]**

**두 가지가 서로 어긋나 있었다.** 의사결정 로그는 *"추가 개발 0(yt-search 활용)"*이라 적었고 D7 5번은 *"`youtube_scrap.py` 계정 모드"*라 적었다.

| 확인 | 결과 |
|---|---|
| `youtube_scrap.py`가 이미 YouTube Data API를 직접 쓰는가 | **그렇다.** `API_BASE`·`api_get()`·`fetch_video_details()`, 키는 `~/.env`의 `YOUTUBE_API_KEY` |
| `yt-search` 스킬을 끌어와야 하는가 | **아니다.** 레포가 `~/.claude/skills/` 외부 자산에 의존하게 된다 |

**결정**

- `youtube_scrap.py`에 **`--channel` 모드**를 추가한다(채널 → uploads 재생목록 → `playlistItems`). Data API는 이미 붙어 있어 신규 인증이 없다

**재수집 skip은 이미 3층으로 되어 있다** (2026-09-06 확인) — 수집 대상 선정(`select_update_targets():756`) · 자막 캐시(`download_transcript():441`) · 요약 캐시(`load_cached_summary():575`). 이미 받은 것을 다시 받거나 다시 요약하지 않는다.

| # | 무엇 | 처리 |
|---|---|---|
| L1 | `deferred`가 다음 실행에 자동 되살아나 **2차 확장 때 남은 300건이 조용히 요약된다** | 벤치마킹 레코드를 요약 재시도군에서 제외 |
