# X(Twitter) 게시일시가 UTC로 저장되는 결함 수정과 기존 95건 백필

## 1. 상황 — 왜 지금 이걸 보게 됐나

`01_사업/_SNS`에서 **SNS 발행 최적 시각**을 정하려고 이 레포의 수집 데이터를 분석하던 중이었다. 세션 `c3978eee`가 Threads 428건·LinkedIn 445건으로 시간대별 반응을 순열검정했고, 후속 세션 `08f70a6a`가 그 분석을 재검토하면서 **"시간대 분석의 전제인 `created_at`이 정말 KST인가"**를 4개 플랫폼 전수로 확인했다.

세 플랫폼은 통과했고, **X 하나만 UTC로 저장되고 있었다.**

이 레포 입장에서 이 결함은 "발행 시각 분석"보다 넓은 문제다. `created_at`은 뷰어 정렬·CLI 조회·향후 벤치마킹 분석이 전부 딛고 서는 값이고, **플랫폼마다 기준이 다르면 어떤 크로스 분석도 조용히 틀린다.**

## 2. 문제

### 2.1 결함 지점은 두 곳이다

| # | 위치 | 코드 | 왜 UTC가 되나 |
|---|---|---|---|
| ① | `twitter_scrap.py:72-75` `parse_twitter_date()` | `datetime.strptime(date_str, '%a %b %d %H:%M:%S +0000 %Y')` | 포맷 문자열에 `+0000`을 **리터럴로** 박아 파싱한다. `%z`가 아니므로 결과는 tz 정보 없는 naive datetime이고, 값은 UTC 벽시계 그대로다. 변환 없이 `strftime()` |
| ② | `twitter_scrap.py:281-283` (HTML 폴백) | `datetime.fromisoformat(dt_str.replace('Z','+00:00'))` → `dt.strftime(...)` | 이쪽은 tz-aware UTC로 잘 만들어놓고, `astimezone(KST)` 없이 바로 `strftime()`한다. 결국 UTC 벽시계 |

두 경로 모두 `created_at`(전체 시각)과 `date`(날짜)를 함께 만든다.

### 2.2 다른 플랫폼은 왜 맞나 — 대조

| 플랫폼 | 변환 지점 | 방식 | 결과 |
|---|---|---|---|
| Threads | `utils/common.py:109` | `datetime.fromtimestamp(int(ts))` | 로컬(KST) ✅ |
| LinkedIn | `utils/linkedin_parser.py:33` | Snowflake 디코딩 후 `datetime.fromtimestamp(ms/1000)` | 로컬(KST) ✅ |
| YouTube | `youtube_scrap.py:171` | `dt.astimezone(timezone(timedelta(hours=9)))` | KST 명시 ✅ |
| **X** | `twitter_scrap.py:72, 281` | 변환 없음 | **UTC** ❌ |

X만 유일하게 변환 단계가 빠졌다. 나머지 셋은 각기 다른 방식이지만 결과는 같다.

### 2.4 결정적 근거 — Snowflake ID 대조로 확증했다

X의 `platform_id`는 트윗 Snowflake ID다. 여기서 발행 시각을 독립적으로 복원할 수 있다(`(id >> 22) + 1288834974657` = epoch ms, UTC).

95건 전부를 디코딩해 저장값과 대조했다.

```
platform_id가 숫자인 건: 95 / 95
저장값 == Snowflake UTC (±2초): 95 | 불일치: 0
```

| platform_id | 저장된 created_at | Snowflake 디코딩(UTC) | 실제 KST |
|---|---|---|---|
| `2021555296…` | 2026-02-11 12:01:56 | 2026-02-11 12:01:56 | **2026-02-11 21:01:56** |
| `2021244380…` | 2026-02-10 15:26:27 | 2026-02-10 15:26:27 | **2026-02-11 00:26:27** ← 날짜도 밀린다 |
| `2021563581…` | 2026-02-11 12:34:51 | 2026-02-11 12:34:51 | 2026-02-11 21:34:51 |
| `2021214042…` | 2026-02-10 13:25:54 | 2026-02-10 13:25:54 | 2026-02-10 22:25:54 |

**코드 읽기와 데이터 대조가 같은 결론에 도달했다.** 추정이 아니다.

그리고 이 발견은 그냥 확증에 그치지 않는다 — **백필과 검증의 수단 자체를 바꾼다.** §4.1에서 다룬다.

### 2.5 코드만 고치면 안 되는 이유 — 재수집으로 자동 복구되지 않는다

두 가지 장치가 기존 레코드를 그대로 보존한다.

| 위치 | 동작 | 결과 |
|---|---|---|
| `twitter_scrap.py:383-395` | 기존 레코드는 **①신규 ②본문이 더 길어짐 ③지표가 새로 생김** 셋 중 하나일 때만 교체 | 시각만 틀린 레코드는 **교체 조건에 걸리지 않는다** |
| `twitter_scrap.py:343` | `max_sequence_id` + `stop_ids` 중단점으로 이미 아는 트윗에 닿으면 수집을 멈춤 | 옛 트윗은 **다시 긁지도 않는다** |

즉 코드만 고치고 수집을 돌리면 **신규만 KST, 기존 95건은 UTC로 남아 혼재한다.** 지금(전량 UTC로 일관)보다 오히려 나쁜 상태다 — 일관되게 틀린 데이터는 사후 보정이 되지만, 섞이면 어느 레코드가 어느 기준인지 판별할 방법이 없다.

**→ 코드 수정과 백필은 한 묶음이다. 따로 하면 안 된다.**

## 3. 검토한 옵션과 기각 근거

| 옵션 | 판단 | 사유 |
|---|---|---|
| **A. 코드만 고치고 데이터는 둔다** | ❌ 기각 | §2.5 — 혼재가 생겨 지금보다 나빠진다 |
| **B. 저장값에 일괄 +9시간을 더한다** | ❌ 기각 | 멱등하지 않다. 두 번 돌면 18시간이 밀리고, **밀렸는지 여부를 값만 보고는 판별할 수 없다.** 실행 마커·`crawled_at` 커트라인 같은 장치를 덧붙여야 하는데, `twitter_scrap.py:390`이 갱신 시 `crawled_at`을 보존하므로 커트라인도 안전하지 않다 |

| **D. X를 다시 전량 수집한다** | ❌ 기각 | 중단점(§2.5) 때문에 옛 트윗은 재수집되지 않는다. 우회하려면 북마크 전체를 다시 훑어야 하는데 인증·rate limit 비용이 크고, 삭제된 트윗은 영구 손실된다 |
| **E. 수집 코드를 Snowflake 디코딩으로 전환** | ⏸ 이번 범위 밖 | LinkedIn이 쓰는 방식이라 일관성은 좋다. 다만 network 경로는 API가 `created_at`을 직접 주므로 굳이 바꿀 이유가 약하다. 대신 **회귀 가드**로만 도입한다(§4.1 ③) |

## 4. 해결 — 4단계

> ⚠️ **네 단계 사이에 X 수집을 돌리지 않는다.** 중간에 수집이 끼면 KST/UTC 혼재가 생긴다.

### 4.1 [1단계] 코드 수정 — `twitter_scrap.py`

**① `parse_twitter_date()` (72-75줄)**

`+0000` 리터럴 파싱을 `%z`로 바꿔 tz-aware로 만든 뒤 KST로 변환한다. 다른 플랫폼과 같은 결과가 되도록 한다.

```python
KST = timezone(timedelta(hours=9))

def parse_twitter_date(date_str):
    try:
        dt = datetime.strptime(date_str, '%a %b %d %H:%M:%S %z %Y').astimezone(KST)
        return dt.strftime('%Y-%m-%d %H:%M:%S'), dt.strftime('%Y-%m-%d')
    except Exception:
        return None, None
```

**② HTML 폴백 경로 (281-283줄)**

이미 tz-aware이므로 `.astimezone(KST)` 한 단계만 추가한다.

```python
dt = datetime.fromisoformat(dt_str.replace('Z', '+00:00')).astimezone(KST)
```

**③ 회귀 가드 (신규)** — `utils/` 에 Snowflake 디코딩 헬퍼를 두고, 파싱 결과와 `platform_id` 디코딩값이 **60초 이상 어긋나면 경고**를 남긴다. 이번 결함이 5개월 넘게 조용히 살아 있었던 이유가 "틀렸는지 알 방법이 없어서"이므로, 그 구멍을 막는다.

```python
X_SNOWFLAKE_EPOCH_MS = 1288834974657  # 2010-11-04T01:42:54.657Z

def x_created_at_from_id(platform_id):
    """트윗 Snowflake ID에서 발행 시각(KST)을 복원한다.

    상위 41비트가 epoch 이후 밀리초다(하위 22비트는 워커·시퀀스).
    복원 불가하면 None을 돌려주고, 호출부는 원래 값을 유지한다.
    """
    text = str(platform_id or "").strip()
    if not text.isdigit():
        return None
    ms = (int(text) >> 22) + X_SNOWFLAKE_EPOCH_MS
    if ms < X_SNOWFLAKE_EPOCH_MS:
        return None
    return datetime.fromtimestamp(ms / 1000, tz=timezone.utc).astimezone(KST)
```

### 4.2 [2단계] 백필 스크립트 — `scripts/backfill_twitter_created_at_kst.py`

기존 선례(`scripts/backfill_threads_display_name.py`, `scripts/linkedin_metric_backfill.py`)의 인터페이스를 그대로 따른다.

**동작**

1. 최신 `output_twitter/python/twitter_py_full_*.json`을 읽는다
2. 각 레코드의 `platform_id`에서 KST 시각을 재계산한다

4. `platform_id`가 숫자가 아니거나 디코딩 실패 시 **건드리지 않고 목록에 남긴다** (현재 해당 0건이나 방어)

**멱등성**: 저장값이 아니라 `platform_id`에서 재계산하므로, 몇 번 실행해도 결과가 같다. 별도 실행 마커가 필요 없다.

## 8. 실행 결과 (2026-09-05)

계획 게이트(agy · Gemini 3.1 Pro High) 판정은 `실행 가능`이었고, Required Fixes 3건을 착수 전에 계획에 반영한 뒤 구현했다. **다만 실행 중에 계획의 파급 범위 누락 하나가 드러나 보정 대상을 넓혔다(§8.1).**

### 8.1 🔴 실행 중 발견한 계획 누락 — `twitter_py_simple_*.json`

**증상.** 백필·통합본 재생성·뷰어 검증이 전부 통과한 뒤, 회귀 테스트를 돌리고 다시 `--verify`했더니 upstream 95건이 **전부 UTC로 되돌아가 있었다.**

**추적.**

| 시각 | 파일 | 상태 |
|---|---|---|
| 11:09:24 | `output_total/total_full_20260905.json` | 정상(KST) |
| 11:18:37 | `twitter_py_full_20260905.json` · `twitter_py_simple_20260905.json` | **둘 다 같은 시각에 재작성, UTC로 복귀** |

두 파일 mtime이 초 단위로 같다는 것이 단서였다. 파일 크기도 보정 전과 동일했다 — 타임스탬프 문자열은 길이가 같아서 시각만 되돌아가면 크기가 변하지 않는다.

**원인.** `twitter_scrap_single.py`(consumer)는 `twitter_py_simple_*.json`을 읽어(58-68줄) `twitter_py_full_{date}.json`을 **생성한다**(141줄). 계획 §2.6은 `full`만 보정 대상으로 잡았고 **그 상류인 `simple`을 빠뜨렸다.** `pytest tests/smoke`가 consumer를 돌리자 UTC로 남아 있던 simple 기준으로 full이 재생성됐다.

**계획의 경고는 맞았고, 내가 그 경고를 어겼다.** §4는 "네 단계 사이에 X 수집을 돌리지 않는다"고 적었는데, 회귀 테스트가 수집을 돌린다는 것을 인식하지 못했다.

**수정.**

1. 백필 스크립트의 기본 대상을 `("twitter_py_simple_*.json", "twitter_py_full_*.json")` 둘로 넓혔다. **simple을 먼저 처리한다** — 상류부터 고쳐야 한다.
2. 여러 파일을 순회하며 하나라도 실패하면 exit 1을 유지하도록 `main()`을 고쳤다.
3. 누락하면 무슨 일이 벌어지는지를 스크립트 docstring에 실측과 함께 박아뒀다.

**재현 시도로 확인.** 되돌림을 일으켰던 `pytest tests/smoke/test_single_scrap_smoke.py`를 다시 돌렸다. consumer가 두 파일을 새로 썼지만(11:28:27) **KST가 유지됐고 `--verify` exit 0**이었다. 되돌림이 재현되지 않는다.

**교훈.** 파생 관계가 있는 산출물은 최종 파일만 고치면 안 된다. 상류를 안 고치면 다음 파이프라인 실행이 조용히 원복시키고, **그 원복은 파일 크기도 안 바꾸므로 눈에 띄지 않는다.**
