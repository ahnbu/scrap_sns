## 1. 상황 (Situation)

### 1.1 조사 착수 경위

사용자가 "최근 수집된 게시글 중 이미지만 있고 본문이 수집되지 않는 경우가 있다(쓰레드 몇 건). 다른 플랫폼도 그런지 확인하고, 중복 게시글도 진단하라"고 지시했다. 제시된 사례는 다음과 같다.

### 2.2 문제군 B — Threads 중복 (신규 발생은 멈춤, 과거 데이터 잔존)

### 2.3 문제군 C — X 저자·본문 오염 36건 (코드 경로는 교체됨, 데이터 오염 + 재발 여지)

#### 증상

```
X 총 95 건 / 고유 본문 62
```

`full_tweet_scan`은 현재 레포에 없는 문자열이다. 커밋 `ee9fb37`(2026-04-18, "fix(twitter-single): browserless detail collection으로 전환") **이전**의 `twitter_scrap_single.py`가 생성했고 그 커밋에서 통째로 교체됐다.

교차 검증: 오염된 16건의 display_name이 정상 레코드의 작성자와 정확히 매칭된다.

본문을 뽑는 `utils/twitter_parser.py:46-52`:

```python

        text_el = article.find('div', {"data-testid": "tweetText"})
```

정확한 촉발 조건(페이지 로딩 미완료인지, 대상이 답글이라 부모 트윗이 상단에 왔는지)은 **삭제된 코드라 재현 불가 — 미확정으로 남긴다.**

브라우저 DOM 의존은 사라졌으나 **"첫 항목이 대상"이라는 가정은 그대로다.**

## 3. 해결 (Resolution)

### 3.1 검토한 옵션과 기각 근거

#### Threads 본문 결측 — 두 방식 비교

| | **옵션 A: 목록에서 `reposted_post` 읽기** | **옵션 B: 리다이렉트 경로 승격** |
|---|---|---|
| 새로 짜야 할 코드 | 파서 신규 작성 + 목록 수집기 스냅샷 코드 | 조건 1줄 + 분기 1개 |
| 미확인 의존성 | `reposted_post` 값의 모양 (스냅샷 10건 전부 null이라 미확인) | 없음 |
| 하류 연동 | 신규 설계 필요 | 기존 설계 그대로 재사용 |
| 원글 본문 확보 | 목록 응답에 원문 전체가 담길지 불확실 | 원글 페이지 직접 수집 → 확실 |
| 추가 HTTP 요청 | 없음 | 리포스트당 1회 (9/1268 = 0.7%) |

**옵션 A 기각.** 옵션 B로 해결되면 A는 HTTP 1회 절약 이상의 값어치가 없는데, 미확인 필드 의존과 새 파서 유지비용이 붙는다.

**옵션 B 채택.** 결정적 근거는 하류 코드가 이미 이 시나리오를 처리하도록 설계돼 있다는 점이다.

| 위치 | 하는 일 | 상태 |
|---|---|---|
| `thread_scrap_single.py:113-127` | 리다이렉트/작성자 불일치 감지 → `detail_status="redirected"` | 작동 |
| `thread_scrap_single.py:129` `_mark_simple_alias_duplicate()` | simple DB에 `duplicate_of_canonical` 표시 | 작동 |
| `thread_scrap_single.py:295` `import_from_simple_database()` | `duplicate_of_canonical`은 재유입 skip | **빈 껍데기 재삽입 자동 차단** |
| `total_scrap.py:514-518` `merge_results()` | `duplicate_of_canonical`은 통합본에서 제외 | **뷰어 중복 자동 차단** |

#### 스냅샷 — 상시 확대 기각

상시 스냅샷 10개 롤링은 이번 진단에 무력했다. 이유는 두 가지다.

1. `thread_scrap.py`(목록 수집기)에 `save_debug_snapshot` 호출이 **0건**인데, 리포스트 껍데기는 `/saved` 목록 응답에만 존재한다.
2. 10개 롤링이라 8월 실패 4건의 HTML이 오늘 성공 건 10개에 전부 덮였다.

### 5.4 B-1 미실행 — 사용자 판단 필요

B-0 진단 결과가 계획 수립 시점의 전제를 뒤집었다.

**확인한 사실**: 요청 `@dddesign.io/post/DbkBrexCRqX` 에 대해 서버는 정상적으로 원글을 반환했다.


리다이렉트는 작동한다. 막힌 곳은 파서 입구다.

```python
# utils/threads_parser.py:36
def extract_json_from_html(html_content):
    if "thread_items" not in html_content: return None
```

Threads가 응답 구조를 바꿨다. 실패 스냅샷 4건과 **성공 경로로 저장된 스냅샷 10건 모두** `thread_items=0`, 게시글은 `result.data.media` 단일 객체로 들어온다. 파서가 지원하는 대체 경로(최상위 `containing_thread`)도 이 응답에는 없다 — 같은 이름의 키가 있으나 `text_post_app_info.containing_thread` 아래 빈 페이지네이션 토큰이다.

**영향 범위**: 8월 4건만의 문제가 아니라 **Threads 상세 수집 전체가 무력화된 상태**다. 오늘 `total_scrap.py --mode update` 가 실행되며 42건이 일괄 실패해 fail_count 2→3 이 된 것이 그 증거다(백업에서 복원 완료).

**B-1 을 실행하지 않은 이유**: 계획서 B-1 은 `is_existing_canonical` 조건 완화였다. 그러나 상세 수집 자체가 0건을 반환하는 지금 그 분기는 도달하지 않는다. 전제가 성립하지 않는다.

**필요한 작업과 범위 판단**: 파서에 `result.data.media` 경로를 추가해야 한다. 다만 한 페이지에 게시글을 담은 `"result":{"data"` 블록이 여러 개 있어(실측 5개 중 2개가 caption 보유) "어느 블록이 요청한 글인가"를 정확히 판정하는 설계가 필요하다. 잘못하면 이번에 X 에서 고친 것과 같은 유형의 오염을 Threads 에 만든다.
