**문제는 이 결과가 "기존 방식 대비 우월함"을 보여주지 않는다는 점이다.** 같은 날 오전 기존 방식도 604건을 정상 수집했다. 비교 대조군 없이 OpenCLI 단독 성공만으로 전환을 결정했다.

전환 판단의 실질적 근거는 5/5 문서의 "모두 실패" 한 줄이었으나, 이는 **특정 하루의 장애 상태를 기존 방식의 구조적 한계로 확대 해석**한 것이다.

특히 OpenCLI는 전량 훑기로 인한 속도 저하 때문에 3일 뒤 조기 종료 기능을 다시 추가했다(`6b47e42`, [[20260709_02_LinkedIn-update-20건-연속중단-복귀-구현계획]]). **이 기능은 기존 방식에 이미 있었다** — `CONSECUTIVE_EXISTING_LIMIT = 20`.

### C-3. 새로운 실패 유형이 생겼고, 미해결이다

OpenCLI `browser bind`는 특정 창을 지정하는 인자를 받지 못한다. [[20260710_01_LinkedIn-OpenCLI-bind-재시도-안정화-구현계획]]이 이를 명시한다.

> "문제는 OpenCLI `browser bind`가 특정 HWND를 직접 지정하지 않고, **bind 순간의 활성 Chrome 탭/창에 붙는다**는 점이다."

코드가 할 수 있는 것은 bind 직전 `SetForegroundWindow`로 전용 창을 앞으로 끌어오는 것뿐이다(`linkedin_scrap.py:290-293`, `:319-331`). 그 찰나에 사용자가 다른 크롬 창을 클릭하면 실패한다.

**실제 실패 이력:**

| 날짜 | 잘못 bind된 대상 |
|---|---|
| 2026-07-10 | `github.com`, `127.0.0.1:51981` |
| 2026-07-18 | `localhost:5000` (SNS 뷰어 자기 자신) |
| 2026-07-26 | `linkedin.com/mynetwork/grow/` |

`8f7eb7a`(재시도 안정화)로 완화를 시도했으나 7/18·7/26 실패는 그 이후 발생했다. **재시도 횟수를 늘리는 완화책일 뿐 구조적 해결이 아니다.**

특히 뷰어에서 수집을 실행하는 운영 구조상 뷰어 탭(`localhost:5000`)이 항상 경쟁 상대가 되므로, **재발은 구조적으로 예정돼 있다.**

### C-4. 되돌리기 장치가 의도적으로 제거됐다

[[20260707_06_LinkedIn-OpenCLI-기본수집기-도입계획]] 결정 사항:

> "`--backend opencli|legacy|auto` 같은 backend 선택 옵션은 만들지 않는다. legacy 자동 fallback은 만들지 않는다. legacy 방식 복구는 git 이력과 직전 data baseline 커밋으로 처리한다."

코드 확인 결과 `storage_state`, `sync_playwright` 관련 코드가 전부 제거됐다(grep 결과 0건). 파일은 536줄 → 771줄로 전면 재작성됐다.

## 균형 비교: 기존 방식 vs OpenCLI

| 항목 | 기존 방식 (Playwright + storage_state) | OpenCLI (Chrome bind) |
|---|---|---|
| **실측 실패율** | ✅ 0회 / 18회+ (2개월) | ❌ 5회 / 18회 (3주) |
| **최근 가동 상태** | ✅ 마지막까지 정상 | ❌ 16일째 중단 |
| **수집 속도** | ✅ 41초 (조기 종료) | ⚠️ 전량 훑기 → 후속 개선으로 완화 |
| **수집 완전성** | 604건 (7/7 오전) | 605건 (7/7 저녁) |
| **데이터 정확도** | 오류 기록 없음 | ✅ 중복 0·파싱 실패 0 (13회 명시적 검증) |
| **로그인 관리** | ❌ 세션 파일 갱신 필요 (5/5 1회 만료) | ✅ 평소 Chrome 그대로, 관리 불필요 |
| **차단 내성** | ⚠️ 5/5에 실제로 깨진 이력 | ✅ 전환 후 차단 실패 0회 |
| **실행 중 컴퓨터 사용** | ✅ 자유 | ❌ Chrome 조작 시 실패 위험 |
| **화면 방해** | ✅ 없음 (백그라운드) | ❌ 전용 창이 전면에 노출 |
| **실패 원인 진단** | ✅ 명확 (인증 만료) | ❌ 매번 다른 창, 재현 불규칙 |
| **검증 기간** | ✅ 2개월 | ⚠️ 3주 |
| **되돌리기 용이성** | — | ❌ 스위치 없음, git 복원 필요 |
| **종합 체감 안정감** | █████░ | ██░░░░ |

> 정렬 기준: 수집 도구의 존재 이유인 "실제로 수집되는가"를 최상단에, 성능·품질 지표를 중간에, 일상 사용 부담과 유지보수성을 하단에 배치했다.

### 비교표에서 읽어야 할 것

**OpenCLI가 실제로 우월한 항목은 2개다** — 로그인 관리 불필요, 차단 내성. 데이터 정확도는 명시적 검증 로그를 남긴다는 점에서 우위지만, 기존 방식에 파싱 오류 기록이 없으므로 실질 차이는 미확인이다.

**그러나 그 2개의 이득이 실현되는 조건은 "bind에 성공했을 때"다.** 3주간 5회 실패는 그 전제 자체가 불안정함을 보여준다. 차단을 막으려다 차단보다 잦은 실패를 얻었다.

**비교 조건의 불공정성도 명시한다** — 기존은 2개월, OpenCLI는 3주다. 기존 방식도 3주 단위로 끊어 보면 어땠을지는 알 수 없다. 다만 2개월 무실패라는 기록 자체는 유효한 근거다.

B안의 목적은 "개선 로직 유실 방지"였으나, **유실될 개선이 실질적으로 없다.**

| 커밋 | 내용 | 기존 코드 보유 여부 |
|---|---|---|
