### 1.2 「로컬수집순」의 원래 약속

실측 #7이 관례를 확정한다. 저장글은 **"수집한 배치가 최근일수록 위, 같은 배치 안에서는 최신 글이 위"** 다. 사용자가 「로컬수집순」에서 기대하는 화면도 이것이다.

내 글만 이 약속을 어긴다. 이유는 수집 방식의 차이다. 저장글은 북마크/피드를 훑으므로 수집 순서와 저장 순서가 대체로 같지만, 내 글은 내 프로필을 **최신에서 과거로** 스크롤하며 읽는다. 그 진행 방향이 그대로 번호와 시각에 새겨져 화면에서 뒤집힌다.

## 2. 문제

### P1 — 내 글 정렬이 역순이다 (두 플랫폼, 두 경로)

같은 증상인데 원인이 다르다. **한쪽만 고치면 다른 쪽이 남는다.**

| 대상 | 1차 키(`crawled_at`) | 실제로 순서를 정하는 것 | 결과 |
|---|---|---|---|
| 내 LinkedIn 글 36건 | 36건 전부 동일 (실측 #3) | 2차 키 `platform_sequence_id` — 최신 글이 1번(실측 #4) | 최신이 맨 아래 |
| 내 Threads 글 32건 | 24개로 갈림 (실측 #6) | **1차 키가 지배** — 최신 글을 먼저 수집해 시각이 이름 | 최신이 맨 아래 |

즉 수집기에서 번호 매기는 방향(`reverse=True`)만 뒤집으면 **LinkedIn 쪽만 고쳐지고 Threads 쪽은 그대로다.** 1차 키가 이미 역순을 담고 있기 때문이다.

일상어로: 두 수집기 모두 "최신 글부터 훑는다"는 사실이 서로 다른 칸(번호 / 시각)에 기록되고, 통합 단계가 그 칸들을 순서대로 읽어서 화면이 뒤집힌다.

### P2 — MY 버튼에 불필요한 아이콘이 있다

`person` 아이콘은 "MY" 라는 글자와 같은 말을 두 번 한다. 옆의 플랫폼 칩들은 아이콘만 있는 원형 버튼이라 시각적 계열도 다르다.

### P3 — ALL 에서 내 글이 섞인다

내 글 68건(LinkedIn 36 + Threads 32)이 저장글 사이에 섞여 있다. 스크랩 뷰어의 본래 목적은 **남의 글 모음**이고, 내 글은 성과 비교용으로 붙은 것이다. 끄고 켜는 스위치가 없다.

### P4 — 고쳐도 화면에 반영할 방법이 없다

정렬은 통합본 파일(`total_full_YYYYMMDD.json`)에 **저장 시점에 확정**된다. 코드를 고쳐도 그 파일을 다시 만들지 않으면 화면은 그대로다. 그런데 재생성 전용 CLI가 없어서(실측 #22) 전체 재수집(수십 분, 로그인 필요)밖에 길이 없다.

### P5 — 상단 건수 표기가 상시 필터 상태처럼 보인다

P3 토글을 켜면 `2454 / 2522 건` 이 항상 떠 있게 된다. 사용자가 아무 필터도 안 걸었는데 걸린 것처럼 보인다.

### 3.2 T1 — 통합 정렬에 내 글 분기를 넣는다 (P1 해소)

`total_scrap.py` 한 파일만 고친다. 수집기와 원본 파일은 건드리지 않는다.

**두 가지를 함께 해야 한다.**

**(a) 1차 키를 배치 대표값으로 통일** — 내 글은 "저장"한 적이 없다. `crawled_at` 은 저장 시각이 아니라 스크롤이 지나간 시각이라 순서 정보로 쓰면 안 된다. 플랫폼별 내 글 묶음의 `crawled_at` **최솟값**을 그 묶음 전체의 대표값으로 삼는다. 이러면 내 글이 통합본에서 **연속 블록을 유지**하고(실측 #2 의 성질 보존), 블록이 놓이는 위치는 "그 수집을 한 시점"이 된다.

**(b) 2차 키를 작성일 오름차순으로 다시 매김** — 블록 내부 순서를 `platform_sequence_id` 재계산으로 정한다. 오래된 글 = 작은 번호. 저장글 관례(실측 #7)와 같아진다.

```python
# (1) total_scrap.py, merge_results() 안 플랫폼 정규화 직후

for group in (own_posts, threads_own_posts):
    if not group:
        continue
    # 내 글은 프로필을 최신→과거로 훑는다. 그 진행 방향이 crawled_at 과
    # sequence_id 양쪽에 역순으로 새겨져 뷰어에서 뒤집힌다(계획 2절 P1).
    # 묶음 전체를 한 시각으로 묶어 블록을 유지하고, 내부 순서는 작성일로 다시 정한다.
    batch_key = min(_normalize_ts(p.get('crawled_at')) for p in group)
    ordered = sorted(group, key=lambda q: str(q.get('created_at') or ''))
    for rank, p in enumerate(ordered, start=1):
        p['platform_sequence_id'] = rank
        p['_own_batch_key'] = batch_key


# (2) total_scrap.py, _saved_at_key() 안 - 유튜브 분기와 같은 자리

    own_batch = post.get('_own_batch_key')
    if own_batch:
        return own_batch


# (3) total_scrap.py, save_total() 안 - new_posts.sort() 직후, reorder_post() 루프 직전

    # 정렬에만 쓰는 임시 필드다. reorder_post() 가 미등재 필드를 지우지 않고
    # 뒤에 붙여 저장하므로(실측 #12) 여기서 걷어내지 않으면 통합본 스키마가 오염된다.
    for p in new_posts:
        p.pop('_own_batch_key', None)
```

**임시 필드를 post dict 에 직접 심는다.** 초안은 별도 맵(`own_batch_keys`)으로 들고 다니려 했으나 실행 불가다(실측 #27) — `merge_results()` 의 지역 변수를 모듈 레벨 `_saved_at_key()` 도, `save_total()` 내부 중첩 `sort_key()` 도 볼 수 없고, `merge_results()` 반환값은 5-튜플이라 맵을 실을 자리도 없다. 스키마 오염은 저장 직전 `pop()` (3) 으로 막는다. 제거 지점은 실측 #28 로 확인했다.

`sort_key` 는 2차 키 타입을 `int` 로 유지한다(문자열과 섞이면 1차 키 동률에서 `TypeError`).

### 3.4 T3 — 설정에 「표시」 탭과 토글 추가 (P3 해소)

기존 탭 구조를 그대로 따른다. `.tab-btn[data-target="tabDisplay"]` 버튼 + `.tab-pane#tabDisplay` 를 추가하면 `switchTab()` 이 자동으로 처리한다(실측 #16). `switchTab()` 에 특별 분기는 필요 없다.

토글 1개: **「ALL·플랫폼 목록에서 내 글 숨기기」**

DOM 식별자를 여기서 확정한다 — E2E 가 아이디로 잡아야 마크업 변경에 안 깨진다.

| 요소 | 아이디 |
|---|---|
| 탭 버튼 | `data-target="tabDisplay"` |
| 탭 콘텐츠 | `tabDisplay` |
| 토글 입력 | `hideOwnPostsToggle` (`<input type="checkbox">`) |

동작 규칙:

| 상황 | 결과 |
|---|---|
| 토글 ON + MY 버튼 OFF | 내 글이 모든 목록에서 빠진다 |
| 토글 ON + MY 버튼 ON | **내 글만** 보인다 (MY 버튼이 우선) |
| 토글 OFF | 지금과 동일 |

구현은 `getFilteredPosts()` 의 `matchesOwn` 한 줄 확장이다.

```javascript
// script.js:2125 부근
// MY 버튼이 켜져 있으면 그게 우선이다 - 숨김 토글과 동시에 켜져도 내 글만 남는다.
const matchesOwn = showOwnPostsOnly
    ? isOwnPost(post)
    : !(hideOwnPostsInAll && isOwnPost(post));
```

저장 위치는 정렬 순서·MY 버튼 상태와 같은 `localStorage` 를 쓴다(키: `sns_hide_own_posts`). AGENTS.md 의 "의미 있는 뷰어 상태는 file-backed JSON" 규칙은 **게시글에 붙는 상태**(별표·숨김·메모)를 가리키고, 이건 브라우저 화면 설정이라 기존 `sns_sort_order`·`sns_own_posts_only` 와 같은 계열이다.

### 3.5 T3-b — 상단 건수 표기 (P5 해소)

토글이 켜졌을 때 **전체수(분모)에서도 내 글을 뺀다.** 그러면 필터 없는 상태에서 `2454 건` 으로 깔끔하게 뜬다.

🚨 실측 #19 을 반드시 지켜야 한다. E2E 가 `label.split("/")[0]` 로 앞 숫자를 읽는다. MY 버튼을 켠 상태에서는 `보이는수 / 전체수` 형태가 **유지되어야** 테스트가 통과한다. 위 방식은 MY ON 일 때 `68 / 2454 건` 이 되어 형태가 보존되므로 안전하지만, **V4 에서 반드시 실측 확인한다.**

### 3.6 T4 — 통합본 재생성 스크립트 (P4 해소)

`scripts/rebuild_total.py` 를 새로 만든다. 수집을 건너뛰고 이미 저장된 플랫폼 파일들만 다시 합친다(실측 #23).

```python
# 수집 없이 통합본만 다시 만든다. 정렬 키·병합 규칙 변경을 검증할 때 쓴다.
# 이미지 재다운로드를 피하려고 mode='update' 경로의 기존 상태 보존을 그대로 탄다.
existing_post_keys, existing_local_images = collect_existing_post_state()
posts, tc, lc, xc, yc = merge_results()
preserve_existing_local_images(posts, existing_local_images)
image_posts = select_image_download_posts(posts, 'update', existing_post_keys)
download_images(image_posts)
save_total(posts, tc, lc, xc, yc, local_image_link_posts=image_posts)
```

`--dry-run` 을 붙여 저장 없이 순서만 출력하는 모드를 둔다. T1 검증에 쓴다.

이 스크립트는 이번 계획을 넘어 **정렬·병합 규칙을 손볼 때마다 재사용**된다.

## 6. 기각한 옵션과 사유

| 옵션 | 내용 | 기각 사유 |
|---|---|---|
| **A** | 수집기 두 곳의 `reverse=True` 제거 | **P1 의 절반만 고친다.** 내 Threads 글은 `crawled_at` 이 1차 키로 이미 역순을 담고 있어(실측 #6) 번호를 뒤집어도 순서가 안 바뀐다. 게다가 원본 파일 `sequence_id` 가 통째로 재배치돼 되돌리려면 재수집이 필요하다 |
| **B** | `_saved_at_key` 에서 내 글은 `created_at` 을 반환 | 순서는 고쳐지지만 **내 글 블록이 해체되어** 저장글 사이 작성일 위치로 흩어진다. 「로컬수집순」이라는 정렬 이름과 어긋나고, 사용자가 지적한 것은 "블록 안이 뒤집혔다" 이지 "블록을 없애달라" 가 아니다 |
| **C** | 수집기에서 `crawled_at` 을 배치 단일값으로 통일 | 방향은 맞지만 **수집기 2개 + 원본 파일 2개**를 건드려야 하고, `crawled_at` 은 다른 판정에 쓰일 여지가 있는 수집 사실 기록이다. 통합 단계에서 "순서로 쓰지 않는다"고 정하는 편이 부작용 범위가 좁다 |
| **D** | 뷰어 `sortPosts()` 에서 내 글만 역순 처리 | 원인이 데이터에 있는데 화면에서 되돌리는 것이다. `query-sns.mjs`·API 등 뷰어를 안 거치는 경로는 계속 역순으로 남는다 |
| **E** | 임시 키를 post 밖 별도 맵(`{id(p): key}`)으로 들고 정렬 | **실행 불가.** 실측 #27 — `merge_results()` 의 지역 변수를 `_saved_at_key()`(모듈 레벨)도 `sort_key()`(`save_total` 내부 중첩)도 볼 수 없고, 반환 튜플에 실을 자리도 없다. 계획 1차 초안의 설계였고 계획 게이트 1회차에서 폐기했다 |
| **F** | 전체 재수집으로 통합본 갱신 | 수십 분 + 로그인 필요. 정렬 키 하나 검증하려고 매번 치를 비용이 아니다. T4 로 1분 내로 줄인다 |
| **G** | 뷰어 검증을 사람 육안 + 수동 캡처로 처리 | done-check 가 증거로 판정할 수 없다. 창을 띄우면 사용자 포커스도 뺏는다. 실측 #29 의 headless 인프라가 이미 있어 자동화 비용이 낮다. 계획 게이트 1회차에서 폐기했다 |

### 11.3 계획과 달라진 점

1. **V5 판정 기준을 정밀화했다.** 계획은 "Threads·X 변경 0"을 기준으로 삼았으나, 내 Threads 글이 통합본에 들어오면서 `check_platform_order_regression.py` 가 threads 도 CHANGED 로 보고했다. 이 스크립트는 `is_own_post` 를 구분하지 않고 `sns_platform` 으로만 묶기 때문이다. **저장글만 추려 대조하는 검증을 따로 돌려** 상대 순서 보존을 확인했다.

2. **V8·V8b 를 「보이는 수」가 아니라 「모집단(분모)」으로 판정하도록 고쳤다.** 사용자가 숨긴 글 3건이 있어 보이는 수가 모집단보다 항상 작다(`2483 / 2486 건`). 숨김 토글이 바꾸는 것은 모집단이므로 그쪽을 본다.

3. **V12 를 플랫폼별 2건으로 쪼갰다.** MY 필터만 걸면 화면 맨 위가 마지막 수집 묶음(Threads)의 최신 글이라, 작성일이 3분 빠른 LinkedIn 글을 기대한 초안이 실패했다. 「로컬수집순」은 작성일 전체 정렬이 아니라 묶음 단위 정렬이므로 **플랫폼을 고정해야** "블록 안에서 최신이 위"를 판정할 수 있다. 정렬 자체는 정상이었다.

4. **`rebuild_total.py` 의 콘솔 UTF-8 처리 방식을 바꿨다.** 레포 관례인 `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, ...)` 를 그대로 쓰면 원래 stdout 이 GC 되며 buffer 를 닫아, 출력이 파이프로 넘어가는 순간 `ValueError: I/O operation on closed file` 로 죽었다(실측). `reconfigure()` 로 교체했다.

5. **`.gitignore` 수정이 추가로 필요했다.** `scripts/*` 가 통째로 무시되고 개별 예외를 등록하는 구조라, 신규 스크립트가 커밋되지 않는다. 계획에 없던 항목이다.
