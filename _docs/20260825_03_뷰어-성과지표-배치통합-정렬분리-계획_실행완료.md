## 1. 상황 (Situation)

### 1.1 사용자 제보

웹 뷰어 카드에서 조회수만 작성자 이름·날짜 아래(헤더 왼쪽)에 표시되고, 좋아요·댓글 등 나머지 지표는 카드 맨 아래 별도 행에 있어 성과 지표가 두 군데로 갈라져 있다. "성과는 성과끼리 모아서" 보고 싶다는 요구.

### 1.2 현재 구현

| 지표 | 렌더 위치 | 코드 |
|---|---|---|
| `view_count` | 헤더 왼쪽 컬럼, 날짜 `<p>` 바로 뒤에 `insertAdjacentHTML('afterend')` | `web_viewer/script.js:2811-2820` |
| `like_count` 외 5개 | 카드 하단 `metricsDiv` (상단 경계선 `border-t` 포함) | `web_viewer/script.js:2790-2810`, append는 `:3020-3022` |

### 1.3 설계 이력

선행 계획서 `_docs/20260824_04_SNS-참여지표-반영-계획.md` 236행에 명시된 결정:

> `view_count`는 지표 행과 별도로, 값이 있을 때만 헤더 우측에 작게 표시(2단계에서 X만 해당될 가능성이 높음).

즉 분리는 실수가 아니라 의도된 설계였다. 다만 두 가지가 어긋났다.

1. 계획은 "헤더 **우측**"인데 실제 구현은 작성자명 아래 **왼쪽 세로 스택**에 들어갔다.
2. "X만 해당될 것"이라는 전제가 이후 유튜브 수집 반영으로 무너졌다.

### 1.4 실측 데이터 (`output_total/total_full_20260825.json`, 2,079건)

| 플랫폼 | 게시글 | 조회수 | 좋아요 | 댓글 | 공유 | 인용 | 북마크 |
|---|---|---|---|---|---|---|---|
| threads | 1,243 | 0 | 1,184 | 1,098 | 1,064 | 633 | 0 |
| linkedin | 660 | 0 | 654 | 577 | 119 | 0 | 0 |
| x | 95 | 20 | 20 | 19 | 20 | 18 | 20 |
| youtube | 81 | 81 | 79 | 67 | 0 | 0 | 0 |
| **합계** | **2,079** | **101** | 1,937 | 1,761 | 1,203 | 651 | 20 |

핵심 수치 세 가지.

- 조회수 보유 101건 중 **81건(80%)이 유튜브**. 선행 계획의 "X만 해당" 전제는 이미 사실이 아니다.
- 조회수가 없는 플랫폼(threads + linkedin)이 **1,903건, 전체의 92%**.
- 조회수만 있고 반응 지표가 전혀 없는 카드가 **2건** (디자인씽킹랩, 601회·246회).

## 2. 문제 (Complication)

### P1. 성과 지표가 카드 안에서 두 군데로 분산

유튜브는 조회수가 가장 중요한 지표인데, 그 조회수만 반응 지표와 떨어진 위치에 있다. 유튜브 81건 전부가 이 상태다.

### P2. 접힘 상태에서 표시 규칙이 어긋남

`metricsDiv`는 `isFolded`일 때 `hidden-content` 클래스로 숨겨지지만(`script.js:2803`), 조회수는 헤더에 있어 접힌 카드에서도 계속 보인다. 접힌 카드에 조회수만 남는다.

### P3. 성과순 정렬이 조회수를 무시

`getEngagementScore()`는 `like_count`, `comment_count`, `share_count` 3개만 합산한다(`script.js:186`, `:196-202`). 주석은 "view_count는 X만 제공하므로"라고 적혀 있으나 1.4절대로 사실과 다르다. 결과적으로 조회수 4,374회 유튜브 글이 정렬 점수 268점(좋아요 220 + 댓글 48)으로만 평가된다.

### P4. (신규 발견) 성과순 정렬이 새로고침 시 유지되지 않음

`VALID_SORT_ORDERS = new Set(['date', 'saved', 'favorites'])` (`script.js:89`)에 `'engagement'`가 빠져 있다.

동작 경로:

1. 사용자가 "성과순" 선택 → `localStorage['sns_sort_order'] = 'engagement'` 저장 (`script.js:307-308`)
2. 새로고침 → `getInitialSortOrder()`가 `VALID_SORT_ORDERS.has('engagement')` → `false`
3. `DEFAULT_SORT_ORDER`인 `'saved'`(로컬수집순)로 덮어쓰고 반환 (`script.js:94-98`)

즉 성과순은 선택해도 새로고침하면 매번 로컬수집순으로 리셋된다. 이번 작업에서 정렬 값을 추가하면 같은 함정을 그대로 밟게 되므로 반드시 함께 고친다.

## 3. 해결 (Resolution)

### 3.1 채택안 요약

| 번호 | 변경 | 해결하는 문제 |
|---|---|---|
| R1 | 조회수를 하단 지표 행 **맨 앞**으로 이동. 구분선 없음 | P1, P2 |
| R2 | 지표 행 생성 조건에 `view_count` 포함 | R1의 부작용 방지 |
| R3 | 정렬 "성과순"을 **반응순** / **조회수순** 둘로 분리 | P3 |
| R4 | `VALID_SORT_ORDERS`에 정렬 값 3종 반영 | P4 |
| R5 | `script.js:196` 주석을 실측 기준으로 갱신 | 문서 정확성 |

### 3.2 R1 — 조회수를 지표 행 맨 앞으로

`METRIC_DEFS` 배열(`script.js:2791-2797`) 맨 앞에 `{ field: 'view_count', icon: 'visibility' }`를 추가하고, 헤더 삽입 블록(`script.js:2811-2820`)을 제거한다.

배지 순서: `조회수 → 좋아요 → 댓글 → 공유 → 인용 → 북마크` (도달 → 반응)

**구분선은 넣지 않는다.** 미리보기 위젯으로 대조 확인한 결과와 근거:

| 근거 | 내용 |
|---|---|
| 노출 빈도 | 구분선이 나타나는 카드는 조회수 보유 101건(5%)뿐. 나머지 95%에는 앞에 붙일 값이 없어 선이 안 생긴다. 카드마다 있다 없다 하면 규칙이 아니라 오류로 읽힌다 |
| 중복성 | 눈 아이콘 하나만 도달, 나머지는 반응. 아이콘이 이미 그룹을 구분한다 |
| 실효 범위 | 선이 실제로 도움되는 건 지표 6개가 한 줄에 늘어서는 X 카드뿐인데, X는 20건이다 |

### 3.3 R2 — 지표 행 생성 조건

현재 `visibleMetrics.length > 0` 조건(`script.js:2799-2800`)은 `METRIC_DEFS` 기준으로 판정하므로, R1로 `view_count`를 배열에 넣으면 조건이 자동으로 따라온다. 별도 수정 없이 조회수만 있는 2건도 지표 행을 얻는다.

**검증 필수**: 이 2건(디자인씽킹랩 601·246)이 변경 후에도 조회수를 표시하는지 확인. 배열에 넣지 않고 헤더만 제거하면 이 2건의 조회수가 화면에서 사라진다 — 헤더 삽입 방식이 원래 채택된 실질적 이유가 이것으로 추정된다.

### 3.4 R3 — 정렬 분리

| 현재 | 변경 후 | `data-sort` 값 |
|---|---|---|
| 성과순 | 반응순 | `engagement` (유지) |
| — | 조회수순 (신규) | `views` |

- 라벨을 "성과순(조회수) / 성과순(반응순)"이 아니라 한 단어씩으로 하는 이유: 드롭다운에서 두 항목이 같은 접두사로 시작하면 괄호까지 읽어야 구분된다. 또한 현재 "성과순"에는 *조회수는 빼고 계산한다*는 숨은 규칙이 있는데, "반응순"으로 개명하면 그 규칙이 이름에 드러나 항목 수는 4→5로 늘어도 이해할 것은 줄어든다.
- `engagement`의 점수 계산식(`METRIC_SORT_FIELDS` 3개 합산)은 **그대로 둔다**. 플랫폼별 정규화는 도입하지 않는다(4절 기각 근거 참조).
- `views` 정렬 로직은 `engagement`와 동일 구조: 값 보유 카드를 앞으로, 그 안에서 `view_count` 내림차순, 동점은 날짜 내림차순.
- 값 보유 판정은 `hasMetricValue(post.view_count)`를 쓴다(`-1`을 값 없음으로 취급하는 기존 규칙 승계).

### 3.5 R4 — 정렬 값 유효성 목록

```
VALID_SORT_ORDERS = new Set(['date', 'saved', 'favorites', 'engagement', 'views'])
```

`'engagement'` 누락은 이번 변경과 무관하게 이미 존재하던 버그이며, 여기서 함께 고친다.

### 3.6 R5 — 주석 갱신

`script.js:196`의 "view_count는 X만 제공하므로 플랫폼 간 비교를 왜곡시켜 합산에서 제외한다"를 실측 기준으로 수정한다. 합산에서 제외한다는 결론 자체는 유지된다(근거는 "X만 제공"이 아니라 "플랫폼 간 조회수 스케일 차이"로 바뀐다).

## 6. 검증 계획

### 6.1 판정 기준 — headless 자동 검증

완료 판정의 유일한 근거는 **pytest 종료코드**다. 사람의 눈이나 화면 캡처를 판정 기준으로 쓰지 않는다.

기존 e2e 인프라를 그대로 사용한다. [tests/e2e/test_core_ui.py:31-53](tests/e2e/test_core_ui.py)의 `server_url` fixture가 빈 포트에 Flask 앱을 띄우고, pytest-playwright의 `page` fixture는 **기본값이 headless**다. 브라우저 창이 뜨지 않으므로 사용자 포커스를 빼앗지 않는다.

신규 파일 `tests/e2e/test_metric_layout_ui.py`에 아래 케이스를 `@pytest.mark.e2e`로 작성한다. 실행 명령:

```
pytest tests/e2e/test_metric_layout_ui.py -v
```

| # | 항목 | assert 대상 (DOM) | 기대 결과 |
|---|---|---|---|

| V10 | 상단 총건수 | `#totalPostsCount` 텍스트 | `/api/posts` 응답의 `posts` 길이와 일치 |

**기댓값은 변경 전 상태에 의존하지 않는다.** V6·V7·V10의 기준값은 테스트 실행 시점에 `/api/posts`([scrap_sns_server.py:1336](scrap_sns_server.py:1336))를 호출해 계산하고, V9는 "표시된 모든 카드가 지표 행을 가진다"는 논리 조건이다. 따라서 코드 변경 이후에 테스트를 작성해도 기준값을 얻을 수 있다.

V1~V5의 대상 카드는 검색창에 작성자명을 입력해 특정한다(예: `땡스큐레이터`, `karpathy`, `디자인씽킹랩`). 게시글 총 건수나 특정 지표값을 상수로 하드코딩하지 않는다 — 수집이 진행되면 값이 바뀐다. 표의 `4.4천`·`220`·`601` 같은 숫자는 2026-08-25 시점 실측 예시이며, 테스트는 해당 게시글의 API 값을 읽어 `formatMetricCount` 규칙(1천 이상 `천`, 1만 이상 `만`)으로 기대 문자열을 생성해 대조한다.

### 9.2 계획과 달랐던 사실 3가지

계획 수립 시점의 진단 중 세 가지가 구현·검증 과정에서 사실과 다른 것으로 확인됐다.

**(1) P2의 실제 원인은 조회수 위치가 아니라 fold 핸들러 누락이었다.**

계획 2절 P2는 "`metricsDiv`는 `isFolded`일 때 숨겨지지만 조회수는 헤더라 계속 보인다"고 적었다. 실제로는 fold 버튼 클릭 핸들러의 `elementsToToggle` 배열(`script.js:3084`)에 `metricsDiv`가 아예 빠져 있어, **클릭으로 접으면 지표 행 전체가 숨겨지지 않았다.** 최초 렌더 경로(`if (isFolded) metricsDiv.classList.add(...)`)에만 처리가 있었던 탓이다. V5 테스트가 이 누락을 잡아냈고, `metricsDiv`를 토글 대상에 추가해 해소했다. 이 역시 이번 변경과 무관하게 이미 존재하던 결함이다.

**(2) "조회수만 있고 반응 지표가 없는 카드 2건"은 뷰어 기준으로 존재하지 않는다.**

계획 1.4절의 "2건"은 집계 시 `0`을 값 없음으로 취급해 나온 수치다. 뷰어의 `hasMetricValue`는 `null`·`undefined`·`-1`·`''`만 무효로 보고 **`0`은 유효값으로 표시한다.** 해당 2건은 `comment_count: 0`을 갖고 있어 실제로는 조회수와 댓글 0 배지가 함께 뜬다. 따라서 "조회수만 있는 카드"는 현재 데이터에 없다.

R2(지표 행 생성 조건에 조회수 포함)의 필요성 자체는 유지된다 — 향후 반응 지표가 전혀 없는 조회수 보유 글이 들어오면 배지 행이 통째로 사라지기 때문이다. V4는 이 조건을 데이터에 실재하는 형태로 바꿔 "조회수를 가진 글은 예외 없이 지표 행을 갖고, 조회수가 첫 배지다"를 검증한다.

**(3) e2e는 자체 서버를 띄우지 못한다.**

계획 6.1절은 `tests/e2e/test_core_ui.py`의 `server_url` fixture 재사용을 전제했으나, [tests/e2e/test_author_filter_ui.py:19-22](tests/e2e/test_author_filter_ui.py)에 기록된 대로 **playwright와 flask가 서로 다른 인터프리터에 설치돼 한 프로세스에서 함께 import할 수 없다.** 따라서 외부 5000번 서버를 전제하는 `test_author_filter_ui.py` 패턴을 따랐다. headless 고정(`chromium.launch(headless=True)`)은 그대로 지켰다.
