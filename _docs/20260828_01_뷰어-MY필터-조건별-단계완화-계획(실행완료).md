## 1. 상황 (Situation)

### 1.1 뷰어의 필터는 전부 AND 로 곱해진다

[`getFilteredPosts()`](../web_viewer/script.js) `script.js:2206-2229` 에서 여섯 개 조건이 동시에 걸린다.

| 조건 | 상태 변수 | 화면에서 켜는 곳 |
|---|---|---|
| 플랫폼 (All·★·in·@·X·▶) | `currentFilter` | 상단 칩 줄 |
| 태그 | `currentTag` | 칩 줄 아래 태그 칩 |
| 작성자 | `currentAuthor` | 카드의 작성자 이름 클릭 |
| 내 글만 (`MY`) | `showOwnPostsOnly` | 상단 `MY` 버튼 |
| 숨김 제외 | `userMetadata[key].hidden` | 카드 메뉴 |
| 검색어 | `searchQuery` | 검색창 |

이 중 서로를 자동으로 풀어주는 관계는 **단 하나**다. 선행 계획 `20260827_05` 의 T2 로 넣은
「플랫폼 칩을 누르면 `MY` 가 풀린다」(`script.js:357-360`).

### 1.2 사용자가 보고한 현상

> 상단 매체별 필터에서 **유튜브를 선택한 상태에서 `MY` 를 선택하면 하나도 결과가 안 나온다.**

## 2. 문제 (Complication)

### 2.1 P1 — 해제가 한 방향뿐이다 (근본 원인)

| 조작 순서 | 코드 | 결과 |
|---|---|---|
| `MY` 켬 → 플랫폼 클릭 | `script.js:357-360` `showOwnPostsOnly = false` | `MY` 자동 해제 ✅ |
| 플랫폼 클릭 → `MY` 켬 | `script.js:385-394` MY 핸들러 | `currentFilter` 유지 → **AND 결과 0건** ❌ |

선행 계획이 반대 방향을 기각한 근거는 이랬다.

> 반대 방향(`MY` 를 누르면 플랫폼 선택을 `All` 로 되돌릴지)은 **바꾸지 않는다.** 현재대로 두면
> "쓰레드 보다가 `MY` 를 누르면 쓰레드 중 내 글"이 되는데, 이건 오작동이 아니라 의도된 조합이고
> `MY` 가 보라색으로 켜져 있으므로 사용자가 인지할 수 있다.
> — `20260827_05` 3.2 절 T2

**이 근거는 절반만 맞다.** "쓰레드 중 내 글"은 실제로 쓸 만한 조합이고 32건이 나온다.
그러나 **내 글이 애초에 0건인 조건**(X·YouTube·즐겨찾기·태그 5개)에서는 인지해 봐야 나갈 정보가 없다.
게다가 이 기능은 지금 **순서에 따라 결과가 다르다** — `LinkedIn → MY` 는 36건, `MY → LinkedIn` 은
`MY` 가 풀려 699건. 같은 두 버튼을 누르는데 순서로 갈린다. 발견할 수 없는 기능이다.

### 2.2 P2 — 0건이 되는 조합 전수 (실측)

**플랫폼 칩 → `MY`** (칩 6개 전부 실행)

| 먼저 누른 칩 | `MY` 켜기 전 | `MY` 켠 후 | 판정 |
|---|---|---|---|
| All | 2,487건 | 45편 · 68건 | 정상 |
| **즐겨찾기 ★** | 8건 | **0 건** | 결함 |
| LinkedIn | 663건 | 36건 | 정상 |
| Threads | 1,269건 | 32건 | 정상 |
| **X** | 95건 | **0 건** | 결함 |
| **YouTube** | 460건 | **0 건** | 결함 (사용자 보고 건) |

**태그 칩 → `MY`** (태그 21개 전부 실행): 5개가 0건 — 나노바나나 · 노션 · 옵시디언 · 카드뉴스 · 하네스.

**작성자 → `MY`**: 남의 작성자를 걸면 `platform + username` 쌍이 내 계정과 다르므로
**구조적으로 항상 0건**이다 (`script.js:2216-2219`).

**검색어 → `MY`**: 검색 결과에 내 글이 없으면 0건. 다만 검색창에 글자가 남아 원인 추적이 가능하다.

즉 **플랫폼 3개 + 태그 5개 + 작성자 필터 전체**가 같은 원인으로 조용히 빈 화면을 만든다.

### 2.3 P3 — 빈 화면이 이유를 말하지 않는다

`index.html:397-405` 의 `#noResults` 는 영어 한 줄뿐이다.

```
search_off
No posts found matching your criteria.
```

어떤 조건이 걸려 있는지, 무엇을 풀면 되는지 아무것도 알려주지 않는다.
사용자가 스스로 빠져나올 단서가 화면에 없다.

### 2.4 P4 — 조건을 따로따로 검사하면 교집합 함정을 놓친다

"플랫폼에 내 글이 있는가", "태그에 내 글이 있는가" 를 **각각** 확인하는 방식은 이 경우를 통과시킨다.

> 신규 태그를 **내 LinkedIn 글에만** 붙인다 → 그 태그의 내 글은 1건 이상(통과).
> 그 상태에서 **Threads 칩**을 켠다 → Threads 내 글 32건(통과).
> 그런데 **둘을 겹치면 0건.**

현재 데이터로 전수 조사한 결과 이런 조합은 **0개**다(1.3 절). 하지만 그건 교차 게시가 많아서 생긴
우연이고, 한 플랫폼에만 올린 새 주제 태그가 하나 생기는 순간 깨진다.
**개별 판정 방식은 오늘만 맞는 설계다.**

## 3. 해결 방안 (Resolution)

### 3.1 옵션 비교 및 기각 근거

| 옵션 | 내용 | 기각 / 채택 근거 |
|---|---|---|
| **옵션 A** | `MY` 를 누르면 플랫폼·태그·작성자를 **전부** `All` 로 리셋 | **기각.** 결함은 사라지지만 "LinkedIn 중 내 글 36건", "코덱스 태그 중 내 글 6건" 같은 **멀쩡히 동작하는 조합까지 같이 버린다.** 2.2 표에서 정상이던 두 줄을 없애는 대가가 필요 없다 |
| **옵션 B** | 조건별로 **따로** 검사해서 내 글 0건인 것만 해제 (+ 그래도 0이면 남은 것 마저 해제) | **기각.** 결과는 옵션 C 와 거의 같은데 2.4 의 교집합 함정에서 **"남은 것 마저 해제"가 발동해 플랫폼까지 풀린다.** 지킬 수 있었던 조건을 버린다. 코드도 2단 구조라 더 길다 |
| **옵션 C (채택)** | **내 글이 나올 때까지 조건을 하나씩 푼다.** 순서는 작성자 → 태그 → 플랫폼 | 결함이 전부 사라지고, **지킬 수 있는 조건은 최대한 지킨다.** 규칙이 한 문장이고 코드는 루프 하나다. 앞으로 조건이 늘어도 배열에 한 줄 추가로 끝난다 |
| **옵션 D** | 데이터에 내 글이 없는 칩을 `MY` 켜진 동안 회색 비활성화 | **기각.** `MY` 를 **먼저** 켜는 순서에서만 도움이 되고, 사용자가 보고한 순서(플랫폼 먼저)를 못 잡는다. 태그·작성자에는 적용할 수도 없다 |
| **옵션 E** | 아무것도 하지 않는다 | **기각.** 2.2 의 조합이 지금 재현되고, 원인이 화면에 드러나지 않아 사용자가 스스로 빠져나올 수 없다 |

**채택 규칙 (한 문장)**

> `MY` 를 **켤 때**, 내 글이 나올 때까지 조건을 하나씩 푼다.
> 푸는 순서는 **작성자 → 태그 → 플랫폼**. 첫 조합부터 내 글이 있으면 아무것도 풀지 않는다.
> `MY` 를 **끌 때**는 아무것도 건드리지 않는다.

**푸는 순서의 근거**

| 순위 | 조건 | 왜 이 자리인가 |
|---|---|---|
| 1 | 작성자 | 남의 작성자면 `MY` 와의 교집합이 **구조적으로 항상 0**이다. 가장 먼저 버려야 한다. 내 계정이면 첫 계산에서 이미 0이 아니므로 애초에 이 단계에 오지 않는다 |
| 2 | 태그 | 플랫폼보다 좁고, 사용자가 방금 누른 것일 가능성이 낮다 |
| 3 | 플랫폼 | 상단 칩 줄은 항상 보이고 사용자가 가장 의식하는 조건이다. **가장 오래 지킨다** |

이 순서 덕분에 2.4 의 함정에서 **태그만 풀리고 Threads 32건이 살아남는다.** 옵션 B 는 여기서 플랫폼까지 푼다.

### 3.2 상세 변경 계획

#### T1. `MY` 를 켤 때 조건을 단계적으로 완화한다 (P1·P2·P4)

- **정본**: `web_viewer/script.js:385-394` (MY 버튼 클릭 핸들러)
- `showOwnPostsOnly` 를 `true` 로 바꾼 **직후**, 렌더 전에 완화 절차를 돌린다.
  `showOwnPostsOnly` 가 이미 `true` 이므로 기존 `getFilteredPosts()` 를 그대로 세면 된다 — 별도 계산기가 필요 없다.

```javascript
// MY 를 켤 때만 부른다. 끌 때는 아무것도 하지 않는다.
// 내 글이 나올 때까지 조건을 하나씩 푼다. 지킬 수 있는 조건은 지킨다.
// 순서 근거: 계획 _docs/20260828_01 (3.1)
function relaxFiltersForOwnPosts() {
    const releases = [
        () => { currentAuthor = null; },
        () => { currentTag = null; },
        () => { setPlatformFilter('all'); },
    ];
    for (const release of releases) {
        if (countOwnPostsUnderCurrentFilters() > 0) return;
        release();
    }
    // 여기까지 왔는데도 0이면 남은 원인은 검색어뿐이다. 검색어는 풀지 않는다(3.3 T4).
}
```

- **T1-a. 플랫폼 칩의 켜짐 표시도 함께 옮긴다.**
  `currentFilter` 만 바꾸면 YouTube 칩이 보라색인 채로 남는다.
  기존 위임 핸들러(`script.js:352-355`)가 하던 `.filter-chip` 활성 전환을 **작은 함수로 빼서 양쪽이 같이 쓴다**.
  `MY` 버튼의 `.active` 는 여기서 끄지 않는다 — `syncMyPostsButtonState()`(`script.js:376-380`)가 맡는다.

- **T1-b. 태그 칩과 작성자 배지는 손대지 않아도 된다.**
  `renderPosts()` 첫 줄이 `updateGlobalTags()` 를 부르고(`script.js:2674-2675`),
  그 안에서 `currentTag` 기준으로 칩 활성이, `currentAuthor` 기준으로 배지 유무가 다시 그려진다(`script.js:3290-3330`).

- **T1-c. 검색 중일 때는 `allPosts` 기준으로 완화를 판정한다.**
  서버 검색은 `platform` 파라미터를 함께 보내므로(`script.js:2172`) `searchResults` 자체가 이미 플랫폼으로
  좁혀져 있다. 그 배열로 "플랫폼을 풀면 내 글이 나오는가"를 판정할 수 없다.
  → 검색 중이면 **`allPosts` 를 모집단으로 완화 판정을 끝내고**, 확정된 `currentFilter` 로 `runServerSearch()` 를 부른다.
  검색어 때문에 여전히 0건일 수는 있다. 그건 T3 문구가 설명한다.

#### T2. 즐겨찾기 ★ 칩도 같은 규칙 대상이다 (P2)

- 별도 코드가 필요 없다. `favorites` 는 `currentFilter` 값 중 하나라(`script.js:2211`)
  T1 의 플랫폼 단계가 그대로 처리한다.
- **지금은 내 글 즐겨찾기가 0건이라 자동으로 풀리고**, 나중에 내 글에 별표를 달면 **자동으로 유지된다.**
  데이터를 따라가는 규칙이라 별표를 달 때마다 코드를 고칠 일이 없다.

#### T3. 빈 화면 문구를 한국어로 바꾸고 걸린 조건을 적는다 (P3)

- **정본**: `index.html:397-405` (`#noResults` 마크업), `web_viewer/script.js:2689-2694` (표시 지점)
- 현재: `No posts found matching your criteria.`
- 변경 후 예: `YouTube · 검색어 "옵시디언" · MY 조건에 맞는 글이 없습니다.`
- 조건 이름은 현재 상태 변수에서 만든다. 걸린 것이 없으면(전체가 0건인 이상 상황) 기존과 같은 일반 문구를 쓴다.
- **플랫폼 이름은 매핑 테이블을 새로 만들지 않는다.** 칩마다 `title` 속성이 이미 있다 —
  `Favorites`·`LinkedIn`·`Threads`·`X (Twitter)`·`YouTube` (`index.html:87-157`).
  활성 칩의 `title || textContent` 를 그대로 쓴다. 이름이 두 곳에 갈라지지 않는다.
- 태그는 `currentTag`, 작성자는 `currentAuthor.label`, 검색어는 `searchQuery`, `MY` 는 고정 문자열을 쓴다.
- **이건 알림이 아니라 안내판이다.** 막다른 길에서만 보이고, 평상시에는 화면에 나타나지 않는다.

### 3.3 이번 범위에서 명시적으로 빼는 것
