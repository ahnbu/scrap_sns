### 1.2 두 수집 경로는 경쟁이 아니라 상호보완이다

실측 #5~#8이 드러낸 구조다. 같은 글에 대해 두 경로가 **서로 다른 칸을 채운다.**

| 필드 | 비로그인 `linkedin_metric_single.py` | 로그인 `recent-activity` |
|---|---|---|
| 노출수(impressions) | ❌ 반환값에 없음 | ✅ 36/36 |
| 반응수 | ✅ 2/2 (최신값) | ❌ 5/36 |
| 댓글수 | ✅ 2/2 | ⚠️ 일부만 |
| 인증 | ✅ 불필요 | ⚠️ `storage_state` 필요 |
| 전수 비용 | ██████ 6초/건 미만 | ████░░ 39초 |

> **핵심**: 노출수는 "추가 비용"이 아니라 비로그인 경로가 채우지 못하는 나머지 절반이다. 두 경로를 **필드 단위로 합성**해야 지표가 완성된다.

### 1.3 이 접근의 트레이드오프

| 얻는 것 | 잃는 것 |
|---|---|
| 노출수 커버리지 100%(36/36) — 비로그인 경로로는 0% | 매 업데이트에 **고정 39초** 로그인 수집이 추가된다 |
| 저장글과 내 글을 같은 스키마·같은 CLI로 대조 | LinkedIn **로그인 세션 사용 지점이 하나 늘어난다**(계정 리스크 증가) |
| `storage_state` 만료를 즉시 발견(P5) | 표준 스키마에 필드가 하나 늘고 통합본 전량 재생성이 필요하다 |
| 외부 레포 수집기를 재구현하지 않음 | 레포 간 경로 의존(`sys.path`)이 생긴다 |

39초는 병렬 웨이브에 흡수되지만(3.2), **계정 리스크는 흡수되지 않는다.** 3.4의 배치 결정이 그것을 다룬다.

### 1.4 왜 지금 하는가

내 글 수집기는 별도 레포 + 수동 스킬 호출 모델이었고, **한 달간 실행되지 않았다**(#3). 사용자가 "헤비하게 스킬로 호출하지 않아도 되게" 하자고 한 것은 이 실패에 대한 정확한 진단이다. 별도 스케줄러를 새로 만드는 것은 같은 실패를 반복한다 — 이미 매일 돌고 있는 파이프라인에 얹는 것이 옳다.

## 2. 문제

### P1 — 내 글이 통합본에 없어 비교분석이 원천 불가능하다

저장글 2,112건은 "남이 잘 쓴 글" 표본이고, 내 글 36건은 "내 성과" 표본이다. 두 표본이 다른 레포·다른 스키마에 있어 **같은 질의로 대조할 수 없다.**

⚠️ **통합본에 넣는 것만으로는 부족하다. 화이트리스트가 두 겹이다.**

| 관문 | 위치 | 통과 못 하면 |
|---|---|---|
| CLI 조회 | `utils/query-sns.mjs:305` `postToResult()` — 13개 키만 반환(#20) | `node utils/query-sns.mjs`가 내 글을 구분하지 못한다 |
| 뷰어 API | `utils/post_meta.py:6` `META_FIELDS` → `scrap_sns_server.py:805`(#26) | **프런트로 데이터가 내려가지 않아 T5의 `MY` 필터가 통째로 동작하지 않는다** |

두 관문을 모두 열어야 P1이 해소된다. 스키마에 필드를 추가하는 것만으로는 어느 쪽도 열리지 않는다.

### P1-b — 내 글 파일을 어디에 쓰든 하류가 읽지 못한다

`merge_results()`는 플랫폼당 파일 **1개**만 읽는다(`total_scrap.py:501-504`, #28). 비로그인 갱신기도 `linkedin_py_full_*.json`만 본다(`scripts/linkedin_metric_backfill.py:51`, #27).

| 내 글 저장 위치 | 결과 |
|---|---|
| 저장글과 같은 `linkedin_py_full_*.json` | `linkedin_metric_single.py`가 같은 파일을 read-modify-write 하므로 **동시 실행 시 쓰기 경합** |
| 별도 파일 | `merge_results()`가 읽지 않아 **통합본에서 영구 누락**. 비로그인 갱신 대상에도 안 들어가 P2가 재발 |

어느 쪽도 그대로는 성립하지 않는다. 3.4가 이것을 푼다.

### P2 — 내 글을 그냥 넣으면 지표가 한 번 채워지고 영구 동결된다

`classify_target`의 판정 순서(`utils/metric_refresh.py:79`):

```
지표 없음                    → 1순위 "missing-metrics" (채운다)
지표 있음 + 작성 fresh 초과   → None, "settled"        (영구 제외)
```

LinkedIn 정책의 `fresh_post_days`는 30일이다(#15). 내 글 36건은 대부분 작성 30일이 지났다. 어댑터가 insight의 7/25 값을 채워 넣으면 **"지표 있음 + 30일 초과" → 다시는 갱신되지 않는다.**

이 정책 자체는 저장글에 대해 옳다(남의 글은 과거 스냅샷으로 충분하고, 662건을 매번 재조회하면 예산이 터진다). **내 글은 성과 추적 대상이라 전제가 다르다.**

### P3 — 통째 덮어쓰기는 최신 반응수를 파괴한다

1.2의 구조 때문이다. 로그인 수집 결과로 레코드를 통째 덮어쓰면, 비로그인이 채운 최신 반응수(350)가 로그인 값(`None` 또는 5건 중 하나)으로 날아간다. **필드 단위 병합이 아니면 지표가 오히려 나빠진다.**

### P4 — 저장글과 내 글이 섞이면 뷰어 UX가 오염된다

내 글은 "스크랩한 남의 글"이 아니다. 검색·태그·별표·숨김의 의미가 다르다. 구분자와 필터가 없으면 2,112건 속에 36건이 무표시로 섞인다.

### P5 — 조용한 실패를 감지할 장치가 없다

현행 insight 레포는 인증이 만료돼도 아무도 모른다(#3이 그 결과다). scrap_sns에는 `utils/auth_status.py:exit_auth_required`와 뷰어 인증 안내 UI가 이미 있는데, 별도 레포는 그 경로를 타지 않는다.

### P6 — 스키마 정의가 두 곳에 갈라져 있다

`utils/common.py:85`에 `STANDARD_FIELD_ORDER`의 **낡은 사본**이 있다(#19). 지표 7개 필드(`like_count`·`comment_count`·`share_count`·`quote_count`·`bookmark_count`·`view_count`·`metrics_updated_at`)가 빠져 있고, `reorder_post()`가 이 사본을 쓴다. `thread_scrap.py`·`linkedin_scrap.py`가 호출한다.

데이터 유실은 없다 — 말미의 "누락된 나머지 필드 추가" 루프가 미등재 필드를 꼬리에 붙인다. 하지만 `is_own_post`를 `post_schema.py`에만 추가하면 **경로에 따라 필드 순서가 달라진다.** `AGENTS.md`의 "데이터 순서·타입은 `utils/post_schema.py` 기준으로 유지"에 어긋난다.

## 3. 해결

### 3.1 범위

| 포함 | 제외 |
|---|---|
| LinkedIn 내 게시물 수집·병합·갱신 | Threads 내 게시물 노출수 → **`BL-0826-01`** |
| 노출수(`view_count`) 로그인 경로 | insight 수집기의 scrap_sns 내부 재구현 |
| 반응·댓글 비로그인 갱신 정책 확장 | `master_index` 크로스플랫폼 매칭 이관 |
| 뷰어 `MY` 필터 + CLI 노출 | `sns-insight-update` 스킬 재작성 (별도 후속) |

**수집기는 이관하지 않는다.** `sns_insight_update`를 그대로 호출하고 산출물만 받는다. 근거는 6절 기각안 #3.

### 3.2 주기 설계 — 지표별로 갈린다

| 지표 | 경로 | 주기 | 근거 |
|---|---|---|---|
| 노출수 | 로그인 `recent-activity` | **매 업데이트** | 3.2.1의 소요 분석 |
| 반응·댓글 | 비로그인 permalink | **주 1회** (`refresh_after_days=7` 현행) | 기존 갱신기가 그대로 처리 |

매 업데이트마다 로그인 경로를 타는 데는 부수 이득이 있다. **`storage_state` 만료를 즉시 발견한다.** 주 1회면 만료를 최대 6일 늦게 안다. P5가 이것으로 해소되므로, 별도의 "마지막 갱신 N일 전" 표시 장치를 만들 필요가 없다.

내 글은 36건 전량이 39초이므로 `--limit`을 나누지 않는다. 상시/전수 구분 없이 매번 전수다.

#### 3.2.1 소요 증가 — "≈ 0초"는 부정확했다

초안은 8/26 단일 관측(95초)만 근거로 "증가 ≈ 0초"라 단정했다. 관측을 5회로 늘려 다시 쓴다.

| 실행일 | 웨이브 소요 | MyPosts(39초) 추가 시 |
|---|---|---|
| 5/11 | 42초 (**최소**) | 42초 (증가 0) |
| 8/24 | 75초 | 75초 (증가 0) |
| 8/26 | 95초 | 95초 (증가 0) |
| 8/21 | 109초 | 109초 (증가 0) |
| 8/18 | 147초+ | 147초+ (증가 0) |

**관측 5회 전부에서 증가 0초다.** 웨이브는 병렬이므로 소요 = 가장 느린 프로세스이고, 39초는 관측된 최소 웨이브(42초)보다도 짧다.

**반례 검토** — "Threads 신규가 없는 날엔 MyPosts가 병목이 되지 않는가":

- 5/11이 정확히 그 날이다. `Threads 상세 수집 대상 0건`인데도 **목록 스캔에 41초**가 걸렸다(#14). Threads 목록 순회는 신규 유무와 무관하게 기존 글과 대조해야 하므로 시간이 든다.
- 추가로 LinkedIn 목록 단독이 항상 29~51초다(#13). 이것이 웨이브의 **하한**을 만든다.

따라서 **최악 상한은 `39 - 29 = 약 +10초`**다(모든 플랫폼이 동시에 최속으로 끝나는 가정). 관측 범위에서는 0초, 이론 상한 +10초로 서술한다.

⚠️ 이 분석은 **소요 시간에만** 해당한다. 계정 리스크는 3.4에서 별도로 다룬다.

### 3.4 T1 — 수집 진입점은 **consumer 웨이브**에 둔다

초안은 producer 웨이브에 배치했다. **변경한다.**

#### 배치를 바꾼 이유

producer 웨이브에는 `linkedin_scrap.py`(저장글, **로그인 세션**)가 있다. MyPosts를 같은 웨이브에 넣으면 **같은 LinkedIn 계정의 로그인 세션 2개가 동시에** LinkedIn에 접속한다. 세션 갱신이 수동 로그인이라 비싼 자산인데, 동시 접속이 탐지·제한을 유발하는지는 **검증하지 않았다**(8절 #2).

파일 경합은 문제가 아니다 — `linkedin_scrap.py:268`의 `storage_state` 쓰기는 수동 로그인 분기 전용이고, 오케스트레이션 실행에서는 `:256` `exit_auth_required()`가 먼저 종료시켜 도달하지 않는다(#24). **남는 위험은 동시 인증 세션 하나뿐이다.**

consumer 웨이브의 LinkedIn 자리는 `linkedin_metric_single.py`(비로그인)이므로 충돌하지 않는다. 웨이브는 배리어로 분리되어 있어(`total_scrap.py:432`) producer가 전부 끝난 뒤 시작한다.

| | producer 배치 | **consumer 배치 (채택)** |
|---|---|---|
| 동시 로그인 세션 | ❌ 2개 | ✅ 1개 |
| 소요 증가 | ✅ 0초 (관측 5회) | ⚠️ consumer 웨이브가 39초로 늘 수 있음 |
| 의미 정합 | 수집 단계 | ✅ 지표 단계 — `linkedin_metric_single.py`와 같은 자리 |

8/26 consumer 웨이브는 30초였다(01:37→02:07). MyPosts 39초를 넣으면 **약 +9초**다. 계정 리스크를 9초와 맞바꾼다.

   - 레포 경로는 상수로 두되 **미존재 시 즉시 종료**하고 사유를 로그에 남긴다(placeholder 금지).

#### 3.4.1 출력 경로 — 전용 파일을 쓰고 하류 3곳을 연다 (P1-b 해소)

consumer 웨이브는 **병렬**이다(`total_scrap.py:432`). 같은 웨이브의 `linkedin_metric_single.py`가 `linkedin_py_full_*.json`을 read-modify-write 하므로(`scripts/linkedin_metric_backfill.py:220`·`:246` `save_full()`), 내 글을 같은 파일에 쓰면 **쓰기 경합**이 난다.

### 3.7 T3 — 갱신 정책 파라미터 (P2 해소)

**`utils/metric_refresh.py`는 이미 존재한다**(#16). 병행 계획 W5가 구현을 마쳤다. 이 계획은 기존 dict에 항목 하나를 더하는 것으로 끝난다.

```python
PLATFORM_POLICIES = {
    "linkedin": {"fresh_post_days": 30,   "refresh_after_days": 7, "run_limit": 120},
    "threads":  {"fresh_post_days": 14,   "refresh_after_days": 5, "run_limit": 50},
    "youtube":  {"fresh_post_days": 30,   "refresh_after_days": 7, "run_limit": None},
    "linkedin_own": {"fresh_post_days": None, "refresh_after_days": 7, "run_limit": 20},  # 신규
}
```

| 대상 | 신선도 | 갱신 주기 | 1회 상한 |
|---|---|---|---|
| LinkedIn 저장글 | 30일 | 7일 | 120건 |
| **LinkedIn 내 글** | **제한 없음(`None`)** | **7일** | **20건 (전용 슬롯)** |

`fresh_post_days=None`을 `classify_target`이 "신선도 검사 생략"으로 해석하도록 분기를 추가한다. 현재 시그니처가 `fresh_post_days`를 필수 키워드로 받으므로(`utils/metric_refresh.py:79`) `None` 처리만 넣으면 된다.

**전용 슬롯이 필요한 이유.** 상한이 저장글과 공유되면, 내 글이 신선도 제한 없이 항상 후보에 올라 매 실행 120건 예산의 앞자리를 잠식한다. 저장글 갱신이 굶는다. 내 글 36건에 슬롯 20건이면 2회 실행에 전량이 돌고, 주기 게이트(7일)가 걸리므로 실제로는 훨씬 여유롭다.

⚠️ **병행 세션이 `utils/linkedin_metrics.py`를 아직 수정 중이다**(워킹트리 `M`). `select_targets` 호출 규약이 확정된 뒤 착수한다(4절).

### 3.9 T7·T9 — 화이트리스트 두 겹을 연다 (P1 해소의 나머지 절반)

#### T7 — CLI

`utils/query-sns.mjs:305 postToResult()`와 `postToExportResult()`는 반환 키를 명시 나열하는 화이트리스트다(#20). 두 함수 모두에 `is_own_post: post.is_own_post === true`를 추가한다.

추가로 조회 필터 옵션(`--own` 또는 `--mine`)을 넣을지는 착수 시점에 판단한다. **최소 요건은 반환 노출**이다 — 그것만 있어도 호출자가 필터링할 수 있다.

`node utils/query-sns.mjs --help`와 관련 unit test를 함께 확인한다(`AGENTS.md` 규칙).

#### T9 — 뷰어 API (T5의 전제)

`utils/post_meta.py:6 META_FIELDS`에 `is_own_post`를 등재한다. `scrap_sns_server.py:805`가 `{field: meta.get(field) for field in META_FIELDS}`로 응답을 만들므로(#26), **등재하지 않으면 프런트가 필드를 아예 받지 못하고 T5의 `post.is_own_post === true` 판정이 항상 거짓이 된다.**

`build_post_meta()`(`utils/post_meta.py:113`)도 같은 리스트로 반환을 자른다. 한 곳만 고치면 경로에 따라 결과가 갈린다 — **리스트 하나만 고치면 두 곳이 함께 열린다**는 점을 확인하고 진행한다.

⚠️ **T9는 T5보다 먼저 끝나야 한다.** 순서가 뒤집히면 필터가 조용히 아무것도 안 하는 상태로 "구현 완료"가 된다.

### 10.3 계획과 달라진 점

- **`merge_results()` 반환 arity를 유지했다.** 내 글 건수를 6번째 값으로 늘리면 모든 호출자가 깨진다. 내 글도 LinkedIn 글이므로 `linkedin_count`에 합산하고 로그로만 분리 표기한다.
- **내 글을 `all_posts` 맨 앞에 뒀다.** 중복 제거가 먼저 나온 쪽을 남기는데, 내 글 레코드가 노출수와 `is_own_post`를 갖고 있어 더 풍부하다. 뒤에 두면 그 정보가 조용히 버려진다.
- **`_force_utf8_console()`을 `__main__` 전용으로 뺐다.** 모듈 수준에서 `sys.stdout`을 갈아끼우면 이 모듈을 import 하는 pytest의 출력 캡처가 통째로 망가진다(실측: 375 errors). 다른 수집기들도 모듈 수준에서 같은 일을 하지만 테스트가 import 하지 않아 드러나지 않았다.
