## 1. 상황 (Situation)

### 1-1. 증상

### 1-2. 원인 확정

## 2. 문제 (Complication)

### 2-1. 옛 구조를 지우면 기존 데이터 경로가 끊긴다

통합본의 Threads 1,244건은 대부분 옛 경로로 수집됐고, 골든 픽스처 `tests/fixtures/golden/threads/thread_items_braces.html` 도 옛 구조다. 단위 테스트 3개 파일이 옛 경로를 검증한다. **옛 경로를 대체가 아니라 병행으로 두어야 한다.**

### 2-2. 블록을 순서로 고르면 저자·본문 오염이 재발한다

본문 블록의 index가 0·1·2로 흔들리므로 "첫 블록 채택"은 틀린 글을 집을 수 있다. 같은 세션에서 X(Twitter)에 발생했던 저자·본문 오염 36건이 정확히 이 유형이었고, 그래서 `utils/twitter_cli_adapter.py:select_focal_tweet()` 을 fail-safe로 바꿨다. **Threads에 같은 실수를 반복하면 안 된다.**

### 2-3. 요청 username으로 저자 일관성을 검사할 수 없다

`extract_posts_from_node()` 는 `master_pk`(요청 username에서 역추적한 사용자 pk)로 남의 글을 걸러낸다. 리다이렉트 건에서는 요청 username이 응답에 없어 `master_pk` 가 `None` 이 되고, **필터가 무력화된다.** 새 경로에서는 기준점을 바꿔야 한다.

### 2-4. `fail_count>=3` 35건은 정상 실행으로 복구되지 않는다

`main()` 은 `fail_count>=3` 을 대상 선정 단계에서 제외한다(`thread_scrap_single.py:491`). 파서를 고쳐도 이 35건은 영원히 시도되지 않는다.

### 2-5. 복구 스크립트는 단일 글을 건너뛴다

`scripts/recover_threads_detail_failures.py` 의 `recover_failures()` 는 `item_count > 1` 일 때만 `recoverable` 로 판정한다. 프로토타입 기준 **42건 중 17건(40%)이 단일 글**이라 `skipped` 로 떨어진다.

- 검증 시 `--dry-run` 결과에 `skipped 17` 이 나오는데, 이건 파서 실패가 아니다. **오독하면 안 된다.**
- 그리고 이 스크립트로는 단일 글을 실제 복구할 수 없다.

### 2-6. 스냅샷을 그대로 골든으로 올릴 수 없다

`AGENTS.md` 는 "테스트는 `tests/fixtures/snapshots/` 자동 생성 파일을 직접 참조하지 않고, 필요한 샘플은 `tests/fixtures/golden/<platform>/` 으로 승격해 git에 포함"하라고 정한다. 그런데 원본 스냅샷은 건당 770KB~1MB다. 4건이면 약 4MB가 레포에 들어간다. **축약이 필요하다.**

### 2-7. 재수집이 통합본을 재생성한다

병행 세션(저자 필터)의 화면 검증 캡처가 이 재생성으로 무효화될 수 있다. 순서 조율이 필요하다(6장).

### 2-8. 수집기가 원천 JSON을 제자리 덮어쓴다 — 되돌릴 수 없다

`thread_scrap_single.py` 는 읽어들인 내용을 **같은 경로에 다시 쓴다.**

| 위치 | 대상 |
| --- | --- |
| `thread_scrap_single.py:259-260` | `output_threads/python/threads_py_full_YYYYMMDD.json` (`open(..., "w")`) |
| `thread_scrap_single.py:162-163` | `output_threads/python/threads_py_simple_*.json` |

`scripts/merge_total_only.py` 에도 백업 코드가 없다(`bak`·`backup`·`shutil` 검색 0건). 즉 **새 파서가 잘못된 저자·본문을 쓰면 원천 데이터가 그 자리에서 덮이고 복구 경로가 없다.** 통합본(`output_total/`)은 원천에서 재생성되므로 원천이 오염되면 함께 오염된다.

`AGENTS.md` 의 "수집 데이터 수정 규칙"도 통합본이 downstream 산출물이며 durable 변경은 upstream full 파일부터 맞춰야 한다고 정한다. 되돌릴 지점은 upstream이다.

### 2-9. 뷰어 검증이 사람 눈에만 의존하면 완료 판정이 불가능하다

`AGENTS.md:84` 는 수집·병합 변경의 완료 기준을 이렇게 정한다.

> `merge_results()` → `download_images()` → `validate_local_image_links()` 통과, 대상 ID가 최신 `output_total/total_full_YYYYMMDD.json` 에 존재, 웹 뷰어 상단 총건수와 최신 JSON 게시글 수가 일치, 그리고 **실제 뷰어 화면에서 대상 게시글이 확인되는 것**

앞의 세 항목은 기계 판정이 가능한데 계획 초안은 이를 창을 띄우는 확인에 뭉뚱그려 놓았다. 창을 띄우면 사용자 포커스를 뺏고, 캡처 외에 증거가 남지 않아 done-check가 사람 눈 없이 판정할 수 없다.

레포에 이미 `scripts/verify_viewer_total_count_headless.mjs` 가 있다. 파일 상단 주석이 "no visible window so it never steals focus, and exits 0/1 so a completion gate can judge it without anyone looking at a screenshot" 라고 밝히고 `--shot <png>` 옵션도 지원한다. **이걸 쓰지 않을 이유가 없다.**

다만 마지막 항목(실제 화면 확인)은 프로젝트 규칙이 명시적으로 요구하므로 제거 대상이 아니라 **사유를 적어야 하는 필수 예외**다.
