### 2.3 왜 이렇게 됐나 (SPEC 세션 `a86f18e9` 전문 대조)

| 순서 | 대화 내용 |
|---|---|
| ① | AI: *"즉시 긁을 수 있는 것이 17개(전부 YouTube), 핸들 조사가 필요한 것이 9개"* |
| ② | AI 정정: *"LinkedIn은 계정 단위 수집기가 이미 있고… **slug만 찾으면 YouTube와 같은 조건**"* |
| ③ | AI: A4(9계정 핸들 조사)를 *"2차로"* 제안 |
| ④ | **AI: *"A4는 순서일 뿐입니다. 1차 수집 결과를 바꾸지 않습니다"*** |
| ⑤ | 사용자: *"지금 해보면 어떨까?"* |
| ⑥ | AI: *"A4 해소 — 9명 전원 주소 확보"* |
| ⑦ | AI: *"D8 교체 \| 대상 12 + 후보 13. 9명 주소 전부 기입"* — **대상은 여전히 12, 전부 YouTube** |

②의 전제("slug만 찾으면 같은 조건")가 ⑥에서 충족됐는데 ⑦에서 재평가되지 않았다. **④에서 결정을 「조사 순서」로 축소해 제시한 것이 직접 원인이다** — 사용자는 "1차 범위에 넣을까"를 물을 기회를 받지 못했다.

「조사 필요 → 2차」가 한 덩어리로 굳어, 조사가 끝나자 꼬리표만 떨어지고 결론이 남았다.

**계획서에 「안 한다」고 적힌 것은 검수를 통과한다.** done-check는 계획 대비 이행을 보므로, R-2에 *"2차에서 붙인다"*고 적힌 순간 그것은 결함이 아니라 계획이 된다. 사슬 어디에도 **원천 문서와 대조하는 단계가 없다.**

### 2.5 🔴 SPEC 제약 정정 — Threads는 긁힌다 (2026-09-06 실측)

SPEC §64가 *"계정 단위 수집기 부재 — LinkedIn만 있다. **YouTube·Threads·X는 없다**"*로 적었고, 이것이 Threads를 1차에서 뺀 근거였다. **이 제약은 사실이 아니다.**

**실측(2026-09-06 21:52 KST, 지피타쿠 `@gptaku_ai` 계정 페이지, 비로그인)**

```bash
node ~/.claude/skills/scrap-my/scripts/run-scrapling-extract.mjs \
  --fetcher stealthy-fetch --url "https://www.threads.com/@gptaku_ai" \
  --selector "div[data-pressable-container]" \
  --output "%TEMP%/threads_acct_test.txt"
```

| 확인 항목 | 결과 |
|---|---|
| HTTP 응답 | **200 OK** (로그인 없음) |
| 본문 | ✅ 전문 확보 |
| 게시 시각 | ✅ (`03/01/26`·`1m`·`2h` 형태) |
| 참여지표 | ✅ 4개 값 (`2.6K` / `259` / `847` / `883`) |
| **글 고유 주소(permalink)** | ✅ **8건 확보** (`/@gptaku_ai/post/Dc8MT_8k65v` 형태) |

permalink가 나오므로 **중복 제거 키를 만들 수 있다** — 계정 단위 수집의 최소 조건이 충족된다.

**이미 있는 부품**

| 부품 | 위치 | 상태 |
|---|---|---|
| Threads 도메인 라우팅 | `~/.claude/skills/scrap-my` — 화이트리스트, `stealthy-fetch`, selector `div[data-pressable-container]` | ✅ 동작 확인 |
| Threads 파서 | `utils/threads_parser.py` | ✅ 레포 내 존재 |
| Threads HTTP 어댑터 | `utils/threads_http_adapter.py` | ✅ 존재(쿠키 경로) |

**따라서 W4는 「수집기 신규 개발」이 아니라 「기존 수집 경로를 계정 단위로 묶는 연결부」다.** 앞선 「크다」는 규모 판단을 철회한다.

**남은 미확인 2건** (W4에서 확인한다)

1. 한 번 요청에 첫 화면 8편이 온다. **이 8편은 상한이 아니라 하한이다** — 스크롤 없이 얻은 값이라 더 받을 수 있는지는 아직 모른다. 본 계획의 상한은 5편이므로 **W4 성립에는 영향이 없고**, 2차(30편) 확대 때 재확인 대상이다
2. 지표 4개 값이 각각 좋아요·댓글·리포스트·인용 중 무엇인지 **매핑 미확정**

**스크롤이 필요할 경우의 대체 경로** (2차 확대 조건, W4 범위 밖)

`stealthy-fetch`는 1회 응답만 받는다. 30편이 한 응답에 안 담기면 아래 순서로 올린다.

| 순서 | 수단 | 비용 |
|---|---|---|
| 1 | `scrap-my`의 Playwright fetcher(`run-with-phases.mjs` 경로)로 전환해 스크롤 후 추출 | 실행 시간 증가 |
| 2 | `utils/threads_http_adapter.py`(쿠키 경로)로 페이지네이션 | 인증 의존이 생긴다 — 비로그인 이점을 잃으므로 1이 실패할 때만 |

**5편 상한에서는 둘 다 불필요하다.** 2차 확대를 결정할 때 이 표로 돌아온다.

## 4. 검증 공통 규칙

### 판정은 종료코드로만 한다

**모든 완료 기준은 스크립트가 assert하고 `process.exit(failed ? 1 : 0)`으로 판정한다.** 캡처는 증거이지 판정 기준이 아니다 — done-check가 사람 눈 없이 판정할 수 있어야 한다. 기존 `scripts/verify_benchmark_mainview.mjs:187`·`verify_benchmark_ui_design.mjs:231`이 이미 이 형태이므로 그 구조를 그대로 확장한다.

「화면에서 확인한다」·「보인다」 같은 서술을 완료 기준에 쓰지 않는다.

### 서버

| 대상 | 방법 |
|---|---|
| 일반 뷰어 검증 | `npm run restart`로 5000번 재시작 후 검증 |
| **계정 파일을 건드리는 검증**(`verify_benchmark_*.mjs` 5종) | **W2의 전용 spawn 경로**(17601 + `SNS_BENCHMARK_ACCOUNTS_PATH`). `npm run restart`는 환경변수를 주입하지 않으므로 쓰지 않는다 |

**창을 띄우지 않는다** — `~/.claude/skills/_shared/hidden-browser-verify-runner.mjs`를 쓴다(기존 스크립트가 이미 사용).

### 데이터

수집·병합 변경은 `merge_results()` → `download_images()` → `validate_local_image_links()` 통과 + 최신 `output_total/total_full_YYYYMMDD.json`에 대상 존재 + 뷰어 상단 총건수와 렌더 카드 수 일치를 **스크립트가 assert**한다.

### 테스트

각 웨이브 종료 시 `pytest tests/unit`. `BL-0901-02`의 상시 실패 4건은 기존 결함이므로 그 4건 외 신규 실패만 본다.

### 산출물 처리

캡처는 `_docs/evidence/20260906_03/`에 남기고 **커밋에 포함한다.** 이 레포의 관례이고(`_docs/evidence/` 아래 98개 파일이 git 추적 중, 1차분 `20260906_01/`만 20개), `.gitignore:182-183`의 `_docs/evidence/*.png`·`*.log`는 **루트 직속만** 제외해 하위 폴더는 추적된다. `.gitignore`를 고치지 않는다.

검증 중 생기는 임시 계정 파일은 스크래치패드에 두고 레포에 남기지 않는다.
